В каталоге `examples/security-policies/` находятся две политики OPA с узкой областью проверки, примеры конфигураций JSON и 64 сценария допуска и отказа. Они показывают, как превратить проверенное требование в исполняемую статическую проверку. Примеры не развертывают облачные ресурсы и не устанавливают контроллер допуска Kubernetes.

## Область проверки и локальные допущения

| Политика | Допустимая конфигурация | Явная граница |
| --- | --- | --- |
| `pod` | Один Pod `v1/Pod` для Linux без сохраняемого состояния в пространстве имен `payments`, с ServiceAccount `payments-app`, без автоматического подключения токена API, томов и доступа к ресурсам узла; образы фиксированы по дайджесту, запуск от непривилегированного пользователя, seccomp `RuntimeDefault`, без повышения привилегий, корневая файловая система только для чтения, все привилегии Linux (capabilities) удалены | Строгий список разрешенных полей охватывает обычные и инициализирующие контейнеры. Неизвестные поля отклоняются. Это локальный профиль, а не полная схема Kubernetes или реализация всех Pod Security Standards |
| `aws_trust` | Один элемент политики доверия роли AWS с настроенным поставщиком OIDC GitHub, действием `sts:AssumeRoleWithWebIdentity`, точной аудиторией `sts.amazonaws.com` и точным субъектом `repo:example/payments:ref:refs/heads/main` | Принимается только эта структура доверия к ветке. Субъекты окружений, шаблоны субъекта, дополнительные элементы, другие операторы и дополнительные действия отклоняются. Права роли и реальный обмен токенов не проверяются |

Имена, учетная запись AWS `123456789012`, реестр `registry.example.com` и дайджест образа с повторяющимся символом служат условными значениями. Ссылка на образ содержит дайджест в допустимом формате, но не указывает на проверенный или доступный для загрузки артефакт релиза. Перед адаптацией замените условные значения на проверенные. Создание пространства имен и ServiceAccount, разрешения роли IAM, политики ресурсов и защита ветки релиза остаются отдельными предварительными условиями.

Этот профиль проверяет документ создания Pod и отклоняет поле `ephemeralContainers`, включая пустой список. Временные контейнеры добавляются через отдельный подресурс API; для диагностики работающих Pod нужны отдельная политика, контроль прав и проверка допуска этой операции.

Строгий профиль Pod намеренно не включает порты, переменные окружения, проверки работоспособности, тома и другие настройки приложения. Для расширения профиля нужны проверка новых полей и сценарии допуска и отказа. Отклонение неподдерживаемой конфигурации предпочтительнее незаметного допуска поля, которое политика никогда не оценивала.

## Файлы и запуск

Файлы примеров:

- `configuration.json` задает ожидаемые пространство имен, ServiceAccount, поставщика OIDC и субъекта GitHub.
- `manifests/pod.json` содержит манифест Pod в JSON: API Kubernetes принимает такое представление манифеста.
- `manifests/aws-trust.json` содержит политику доверия роли AWS, а не политику ее разрешений на ресурсы.
- `policies/pod.rego` и `policies/aws_trust.rego` по умолчанию отклоняют конфигурацию и реализуют два профиля.
- `fixtures.json` содержит полный набор сценариев; `policies/fixtures_test.rego` проверяет каждый сценарий с помощью соответствующей политики OPA.

Запускайте из корня репозитория при наличии Python 3 и Docker:

```sh
python3 -m unittest discover -s scripts/tests -v
python3 scripts/test_security_policies.py
python3 scripts/test_security_policies.py --policy pod --input examples/security-policies/manifests/pod.json
python3 scripts/test_security_policies.py --policy aws_trust --input examples/security-policies/manifests/aws-trust.json
```

Первая команда выполняет восемь тестов программы запуска и две проверки воспроизводимости генерации сайта. Тесты программы запуска проверяют отказы при отрицательных и неопределенных решениях, неполных результатах и пропущенных тестах, некорректном JSON, ошибке движка и очистку контейнера при тайм-ауте или прерывании. Вторая команда проверяет структуру сценариев, уникальность имен, наличие допуска и отказа для каждой политики и соответствие разрешенных сценариев опубликованным манифестам. Затем запускает строгую проверку и тесты OPA и проверяет выполнение каждого ожидаемого сценария. Пустой набор, неизвестная политика, ошибка движка, неполный отчет и провал сценария приводят к ненулевому коду завершения.

Команды отдельной проверки принимают один документ JSON и требуют явного логического решения `true`. Повторяющиеся ключи JSON, числовые значения, не предусмотренные форматом JSON, некорректный ввод, ошибки, неопределенное решение и `false` приводят к отказу. Перед проверкой данные повторно сериализуются в JSON и записываются во временный файл. Формат ввода задан явно: программа не разделяет потоки YAML, не формирует манифесты из шаблонов Helm и не извлекает Pod из манифестов контроллеров.

На один вызов движка отведено 120 секунд как локальное эксплуатационное ограничение этих небольших примеров. При тайм-ауте или прерывании программа отдельно удаляет свой контейнер по уникальному имени; завершение клиента Docker само по себе не гарантирует остановку контейнера.

OPA 1.21.1 зафиксирован в программе запуска по дайджесту образа. Контейнер работает без сети, с файловой системой только для чтения, отключенными привилегиями Linux (capabilities) и каталогами, подключенными только для чтения. До запуска Docker может понадобиться сеть для получения фиксированного образа. Команды запускаются локально. Их также можно вызвать из существующего конвейера CI с Python 3 и Docker; автоматический запуск в этом репозитории не настроен.

## Что проверяют сценарии

Для Pod проверяются доступ к сети, пространствам PID и IPC узла и томам узла, неверные идентичность и пространство имен, а также автоматическое подключение токена. Отдельные сценарии охватывают изменяемые или некорректные ссылки на образ, отсутствие контейнеров, повышение привилегий, запись в корневую файловую систему, добавление привилегий Linux, отсутствие их удаления, запуск от root и переопределение seccomp. Проверяются также неподдерживаемые поля, конфигурация для Windows, некорректные инициализирующие контейнеры, отсутствие полей в обычных и инициализирующих контейнерах и наличие временных контейнеров в документе создания Pod. Сценарии допуска включают обычные и инициализирующие контейнеры. Обе политики отклоняют некорректные входные данные верхнего уровня.

Для IAM проверяются неверные репозиторий, ветка, аудитория и поставщик; субъекты запросов на слияние и окружений; шаблоны субъекта или доверенной стороны; дополнительные действия и элементы; `StringLike`; `NotAction`; `NotPrincipal`; отсутствие обязательных элементов политики доверия и неверная структура элементов. Сценарий допуска представляет точный проверенный профиль ветки.

При подключении к существующему конвейеру CI эти тесты оценивают реализацию политики из запроса на слияние. Это проверка на регрессии, а не независимое согласование изменения политики. Защищайте код политик, ожидаемую конфигурацию, сценарии, программу запуска и описания процессов по тем же правилам проверки ответственными владельцами, что и реализуемые ими меры. Если результат участвует в решении о слиянии, настройте соответствующую проверку как обязательную в параметрах репозитория.

## Учитывайте ограничения проверки

Успешная проверка Pod не доказывает авторизацию вызывающей стороны, происхождение и доступность образа, применение seccomp, сетевую изоляцию и изоляцию облачных идентичностей. Для проверки этих ограничений нужны действующий контроль допуска и испытания во время исполнения. Успешная проверка политики доверия не доказывает, что AWS примет роль, выдаст нужную сессию и ограничит ее эффективные разрешения на ресурсы.

Перед использованием в рабочей среде проверяйте итоговую конфигурацию по схеме целевой платформы, выполняйте разрешенные и запрещенные операции в изолированной среде и убеждайтесь, что процедура развертывания не позволяет пропустить проверку политики или заменить проверенный артефакт. Для полной проверки используйте [безопасность CI/CD](/ru/supply-chain/ci-cd-security/playbook/), [Cloud IAM и доступ рабочих нагрузок](/ru/platform-security/cloud-iam-workload-identity/playbook/) и [безопасность Pod](/ru/platform-security/kubernetes/pod-security/playbook/).
