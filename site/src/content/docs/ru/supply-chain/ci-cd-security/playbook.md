Используйте этот плейбук при проверке pipeline CI/CD, который выполняет код участников проекта, публикует пакеты, получает облачные учетные данные или развертывает релиз. Проверка охватывает весь путь доставки: исходный код, описание pipeline CI/CD, исполнитель, зависимости, артефакт, идентичность и решение о развертывании.

## 1. Определите границы доверия

Зафиксируйте владельца репозитория, разрешенные события запуска, ревизию pipeline CI/CD, группу исполнителей, доступные сетевые ресурсы, учетные данные, хранилища артефактов и роли развертывания. Различайте код из ответвления внешнего участника, код сотрудника и проверенную ревизию релиза. Принадлежность к организации сама по себе не делает исполняемый код безопасным.

Для рабочей среды разделяйте контексты проверки запросов на слияние, доверенной сборки и развертывания. Код из запроса на слияние может выполнять произвольные обработчики установки зависимостей, тесты, сценарии сборки и локальные actions. В этом контексте разрешайте только чтение репозитория, без секретов рабочей среды, обмена токенов на облачные полномочия и доступа к системам развертывания. Отключайте сохранение учетных данных при получении исходного кода, если последующим шагам не нужен доступ к Git с аутентификацией.

Изменения pipeline CI/CD, повторно используемых компонентов автоматизации (в GitHub Actions: reusable workflows и actions), образов исполнителей, файлов политик и файлов фиксации зависимостей меняют границу безопасности доставки. Требуйте проверки ответственными владельцами и защищайте ветку от обхода правил. Обязательная проверка полезна, только если атакующий не может заменить ее реализацию, выдать другую проверку с тем же именем за нужную или обойти правило через альтернативный путь публикации.

## 2. Проверьте события запуска и разрешения

В GitHub Actions начинайте с `permissions: {}` и выдавайте каждому заданию только необходимые разрешения. Для обмена токеном OIDC заданию нужно `id-token: write`: это разрешает выпуск токена, а не облачную операцию. Условия получения облачных полномочий и доступные операции определяют политика доверия облака и разрешения роли. Учитывайте, что action может обращаться к `github.token`, даже если токен не передан отдельным входным параметром.

`pull_request_target` выполняется в привилегированном контексте базового репозитория. Не получайте в нем исходный код запроса на слияние и не выполняйте его сценарии, локальные actions, зависимости или собранные программы. Аналогично разделяйте доверие для `workflow_run`: успешное завершение workflow с недоверенным кодом не делает его код, кеш или артефакты доверенными. Привилегированный потребитель может разбирать ограниченные по размеру данные безопасным парсером, но не должен выполнять загруженное содержимое или использовать заданный атакующим путь артефакта как команду.

Передавайте поля события в команды через переменные окружения с корректным заключением в кавычки или структурированные аргументы. Не подставляйте заголовки запросов на слияние, имена веток, текст задач и сообщения коммитов в генерируемый код оболочки. Кавычки вокруг выражения GitHub Actions внутри строки оболочки не устраняют возможность внедрения кода.

Для GitHub Actions выбирайте фиксацию зависимостей с учетом используемой платформы. [Workflow dependency lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles) находятся в public preview; официальное объявление от 14 октября 2026 года указывает GitHub Enterprise Cloud, вариант с резидентностью данных, Team и Free. Проверьте поддержку в используемой платформе и подключение конкретного workflow. В поддерживаемых репозиториях для подключенных workflows проверяйте `.github/workflows/actions.lock`, зафиксированные коммиты и идентичности исходных репозиториев. Файл охватывает транзитивные зависимости actions; зависимости внутри вызываемого reusable workflow определяет файл фиксации его собственного репозитория. Для workflows без поддержки или подключения сохраняйте фиксацию сторонних actions и reusable workflows полными проверенными SHA из ожидаемого исходного репозитория.

При внедрении или обновлении проверяйте весь сгенерированный diff: генератор также меняет ссылки в workflows и actions. Сверяйте политику разрешенных actions с зафиксированными коммитами. Изменения файла фиксации проходят ревью; не создавайте его заново автоматически при выпуске. Образы фиксируйте по дайджесту, зависимости устанавливайте без изменения согласованных версий там, где это поддерживается; обновляйте фиксации через проверенные изменения.

## 3. Изолируйте исполнителей и учетные данные сборки

Используйте новые среды исполнения для недоверенных заданий. Для собственной инфраструктуры после задания уничтожайте вычислительный экземпляр либо полностью пересоздавайте среду, обеспечивающую эквивалентную изоляцию: повторная регистрация и очистка рабочего каталога не удаляют закрепившееся вредоносное ПО. Не используйте недоверенный исполнитель повторно для подписи или развертывания.

Контейнер на общем привилегированном узле такой изоляции не дает. Проверяйте подключение сокета Docker, привилегированные контейнеры, каталоги узла, учетные данные узла, сервисные учетные записи Kubernetes, агенты управления и доступ к соседним заданиям. Разделяйте группы исполнителей и сетевой доступ для внешних запросов на слияние, доверенных сборок и развертывания. Даже одноразовому исполнителю нужны изолированный узел и ограниченный доступ к сети.

Ограничивайте права учетных данных сборки нужными операциями в конкретном реестре или сервисе зависимостей. Используйте механизмы передачи секретов сборки вместо аргументов сборки, слоев образа и конфигурации в репозитории. Не давайте коду установки зависимостей роль развертывания рабочей среды. Если требуется загрузка зависимостей, разрешайте необходимые адреса через контролируемый канал исходящего трафика и проверяйте недоступность сервисов метаданных и внутренних интерфейсов администрирования.

Не считайте маскирование журналов средством ограничения доступа. Проверяйте обычные сценарии и ошибки на синтетическом секрете, включая отладочный вывод, преобразованные значения, выгруженные артефакты, отчеты тестов и диагностику исполнителя. Сохраняйте только необходимые для расследования данные и ограничивайте доступ к ним.

## 4. Защитите кеши и передачу артефактов

Определите, кто может записывать каждый кеш и какие контексты могут его восстанавливать. Разделяйте кеши по уровню доверия, владельцу репозитория, ОС, выбранным версиям зависимостей и ревизиям инструментов. Имя ветки или хеш коммита в ключе не подтверждают подлинность автора записи; широкие префиксы восстановления могут пересекать нужную границу.

Не переносите кеш запроса на слияние в привилегированную сборку без независимой проверки содержимого по ожидаемым неизменяемым входным данным. Если такой проверки нет, выполняйте сборку заново в доверенном контексте. Считайте загруженные архивы враждебными: ограничивайте размер, отклоняйте пути и ссылки, ведущие за пределы каталога распаковки, не исполняйте конфигурации и программы, полученные из недоверенного запуска.

При каждой передаче связывайте дайджест артефакта с ревизией исходного кода, идентичностью сборки, ожидаемым pipeline CI/CD и результатом проверки политик. Имени, тега, успешного завершения запуска и разрешения на загрузку недостаточно. Не считайте отчет сборки подтверждением, пока доверенный проверяющий компонент не проверит provenance артефакта и указанный в отчете дайджест.

## 5. Ограничьте федерацию и развертывание

Привязывайте политику облачной федерации к ожидаемым издателю, аудитории и субъекту. Для федерации GitHub с AWS проверяйте поддерживаемые условия `aud` и `sub`; не предполагайте, что произвольные поля (claims) токена GitHub доступны как ключи условий IAM. Значение `sub` с именем окружения привязано к окружению, а не к ветке, поэтому дополнительно ограничивайте ветки или теги развертывания в настройках окружения.

Используйте разные роли для публикации артефактов сборки и развертывания. Ограничивайте каждую роль конкретными репозиториями, реестрами, ресурсами и средами. Роль развертывания не должна редактировать свою политику доверия, расширять права IAM, менять правила согласования релиза или заменять проверяющий компонент. Если идентичность процесса позволяет получить учетные данные, не допускайте выполнения непроверенного кода участника в этом задании ни до, ни после обмена токеном.

При согласовании развертывания в защищенное окружение фиксируйте проверенную ревизию и точный дайджест артефакта. При развертывании повторно проверьте дайджест полученного артефакта; не пересобирайте артефакт после согласования и не определяйте согласованный артефакт по изменяемому тегу. Для отката применяйте те же проверки идентичности и целостности, с документированным порядком исключений для аварийных релизов.

## 6. Проверяйте подпись и provenance при использовании

Подпись не доказывает безопасность артефакта. До продвижения или развертывания проверяйте дайджест, разрешенную идентичность подписанта и издателя OIDC, доверенную систему сборки, объект, указанный в provenance, и ожидаемую ревизию исходного кода. Отклоняйте подписи идентичностей, которых нет в списке доверенных. Выносите формирование provenance за пределы управляемых атакующим шагов сборки в объеме, необходимом выбранному уровню гарантий.

Для многоплатформенных образов определите, охватывает ли согласование индекс и его манифесты, и проверяйте объекты, которые среда исполнения фактически может загрузить. Убедитесь, что продвижение между реестрами сохраняет нужные дайджесты и свидетельства. Ошибки проверки, отсутствие свидетельств, неподдерживаемые форматы и недоступность проверяющих сервисов должны останавливать защищенный путь релиза или запускать явно зарегистрированную процедуру исключения.

Используйте [SLSA и build provenance](/ru/supply-chain/slsa-provenance/overview/) и [безопасность образов контейнеров](/ru/supply-chain/container-image-security/playbook/) для форматов свидетельств и работы с образами. Не заменяйте проверку подписи меткой или логическим значением, которое производитель добавил в свой артефакт.

## 7. Выполните отрицательные проверки

Используйте одноразовый репозиторий и роли вне рабочей среды. Фиксируйте событие запуска, эффективные разрешения, идентичность исполнителя, дайджест артефакта, событие облачного аудита и результат развертывания.

| Сценарий | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Внешний участник меняет тест или обработчик установки для чтения учетных данных | Нет учетных данных рабочей среды и доступа к метаданным | Эффективные права токена и отказ сетевого запроса |
| Задание с привилегиями загружает артефакт запроса на слияние с исполняемым файлом или путями за пределы каталога распаковки | Код не выполняется; опасный архив отклоняется | Журналы потребителя и результат распаковки |
| Недоверенное задание записывает кеш, который затем запрашивает задание выпуска | Задание выпуска не использует этот кеш как источник доверенного кода | Контекст задания, записавшего кеш, и выбор кеша заданием выпуска |
| Другой репозиторий, ветка, окружение или аудитория запрашивает роль релиза | Федерация отклоняется согласно настроенным условиям доверия | Отказ поставщика и декодированные поля тестового токена |
| Согласованный артефакт заменен под тем же тегом | Развертывание отклоняется или использует согласованный дайджест | Запрошенный дайджест и решение проверяющего компонента |
| Подписанный образ имеет другого подписанта или ревизию исходного кода | Развертывание отклоняется | Проверенная идентичность и несоответствие provenance |
| Исполнитель повторно используется после недоверенного задания | Политика группы исключает повторное использование | Жизненный цикл исполнителя и уничтожение узла |
| Подключенный workflow получает несогласованный коммит зависимости или другую идентичность исходного репозитория | Проверка фиксации отклоняет подмену; согласованный граф выполняется в разрешенном контрольном случае | Выбранные коммит и идентичность репозитория, ревизия файла фиксации и решение исполнителя |

Статические [примеры политик безопасности](/ru/reference/security-policy-examples/overview/) проверяют отдельные свойства конфигурации. Они не проверяют эти границы во время исполнения.

## 8. Подготовьте реагирование на компрометацию

Остановите затронутые задания и запретите новый обмен учетных данных до восстановления инфраструктуры доставки. Сохраните с ограниченным доступом данные об исполнителях, процессах и артефактах, а также журналы облачного аудита. Отзовите раскрытые статические учетные данные и ограничьте временные сессии с учетом того, как поставщик фактически отзывает доступ: изменение доверия федерации само по себе не аннулирует уже выданные учетные данные.

Пересоздайте скомпрометированные узлы исполнителей и проверьте релизы, записи в реестры, кеши и изменения процессов за период компрометации. Пересоберите артефакты из проверенной ревизии в доверенном контексте. Повторная подпись артефакта скомпрометированной сборки не восстанавливает доверие.

Для каждого пути релиза, включая ручную публикацию и откат, определите владельца и проверку восстановления. Работа завершена, когда несанкционированный релиз блокируется, корректный проходит, а подтверждающие данные связывают дайджест развернутого артефакта с проверенным кодом и решением о выпуске. Порядок назначения владельцев исключений и критерии релиза описаны в плейбуке [управления выпуском](/ru/review/release-governance/playbook/).
