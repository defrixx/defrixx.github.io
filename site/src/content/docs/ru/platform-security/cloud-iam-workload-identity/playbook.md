Используйте этот плейбук для проверки облачных ролей приложений, нагрузок Kubernetes и заданий CI/CD. Федерация позволяет получать учетные данные по подтвержденной идентичности вместо хранения постоянных секретов. При этом нужно защищать издателя, вызывающую сторону и выданные ей полномочия.

## 1. Свяжите идентичности с ресурсами

Для каждой нагрузки зафиксируйте владельца, среду, облачную учетную запись или проект, издателя, субъекта, аудиторию, механизм федерации, роль, доступные ресурсы и источник, из которого SDK получает учетные данные. Учитывайте получение других ролей с помощью уже выданных учетных данных, действия от имени другой идентичности, политики ресурсов, ограничения организации, границы разрешений и делегированное администрирование.

Разделяйте идентичности нагрузок по приложению и среде. Назначайте приложению рабочей среды отдельную идентичность вместо роли узла, общей сервисной учетной записи по умолчанию или идентичности администратора развертывания. Разрешайте необходимые действия над конкретными ресурсами; отдельно проверяйте запись и административные операции.

Моделируйте весь путь повышения привилегий. Чтение секрета не единственный способ получить учетные данные: создание Pod, изменение шаблона Pod контроллера, выполнение кода в контейнере и запрос токена сервисной учетной записи могут позволить действовать от имени нагрузки. В облачном IAM изменение доверия, передача роли сервису, действия от имени другой идентичности и редактирование политики ресурса могут давать больше полномочий, чем отдельное разрешение на доступ к данным.

## 2. Настройте границу доверия конкретного поставщика

| Механизм | Проверяемая привязка идентичности | Эксплуатационное ограничение |
| --- | --- | --- |
| AWS IRSA | Ожидаемый поставщик OIDC кластера; точный `sub` для пространства имен и ServiceAccount; `aud` со значением `sts.amazonaws.com` | Проверьте использование проецируемого токена и поддержку этого механизма версией SDK; исключите незапланированное использование роли узла |
| EKS Pod Identity | Связь кластера, пространства имен, ServiceAccount и роли; доверие к `pods.eks.amazonaws.com` с `sts:AssumeRole` и `sts:TagSession` | Использует EKS Auth и Pod Identity Agent вместо поставщика OIDC для IRSA; проверьте совместимость вычислительной среды и SDK, а также задержку применения привязки |
| Workload Identity Federation for GKE | Ожидаемый пул идентичностей и субъект IAM либо привязка для действий от имени облачной сервисной учетной записи | Одинаковые имена пространства имен и ServiceAccount могут давать одну идентичность в разных кластерах общего пула; ограничивайте доступ конкретным кластером, где это поддерживается, или разделяйте пулы и проекты |
| Microsoft Entra Workload ID for AKS | Точные значения издателя OIDC, субъекта `system:serviceaccount:<namespace>:<name>` и аудитории `api://AzureADTokenExchange` в федеративных учетных данных | Включите необходимую интеграцию кластера и метку Pod `azure.workload.identity/use: "true"`; проверьте, что используемая библиотека приложения поддерживает этот механизм |
| Федерация CI/CD | Ожидаемые значения издателя платформы, аудитории, репозитория и субъекта релиза, которые принимает поставщик | Проверяйте правила веток и окружений там, где облако напрямую не оценивает эти атрибуты |

Не копируйте политики доверия между механизмами. Проверяйте поддерживаемые ключи условий, формат издателя, аудиторию, обработку ключей подписи и модель авторизации поставщика. Проверяйте токены через поставщика или нужный API аутентификации: декодирование JWT не проверяет подпись и аудиторию.

Избегайте широких шаблонов субъекта для ролей рабочей среды. Для федерации GitHub с AWS используйте поддерживаемые точные условия `aud` и `sub` нужной ветки или окружения. Если субъект содержит имя окружения, ограничения веток задаются в настройках защищенного окружения. Назначьте владельца, который отслеживает жизненный цикл привязок по имени: при удалении и пересоздании пространства имен, ServiceAccount, репозитория или проекта доверенное имя может использоваться повторно. Удаляйте устаревшие привязки и проверяйте повторное использование идентичности перед пересозданием.

Для AKS таблица описывает прямую федерацию. Функция identity bindings, доступная в предварительной версии, использует аудиторию `api://AKSIdentityBinding`; для прямого обмена нужен отдельный проецируемый токен с `api://AzureADTokenExchange`. Не используйте один файл токена для обоих механизмов без проверки аудитории.

## 3. Защитите выбор идентичности Kubernetes

Право развертывать нагрузки с защищенной ServiceAccount означает возможность действовать от имени связанной с ней облачной роли. RBAC сам по себе не ограничивает выбор `serviceAccountName`, если у вызывающей стороны нет права читать эту ServiceAccount. Изолируйте нагрузки в отдельном пространстве имен с ограниченными правами развертывания либо используйте контроль допуска, который проверяет аутентифицированную вызывающую сторону и выбранную идентичность.

Проверка должна охватывать прямое создание Pod, создание и изменение объектов контроллеров нагрузок, операции с подресурсами, а также Pod, которые создают контроллеры. Если идентичности контроллера разрешено создавать Pod, не позволяйте недоверенной стороне выбрать защищенную идентичность в родительской нагрузке. Защищайте политики допуска, привязки, метки исключений и управляющие ими идентичности платформы. Проверяйте обработку ошибок и исключенные пространства имен наряду со штатным применением политики к подходящим запросам.

Проверяйте `serviceaccounts/token`, `pods/exec`, `pods/attach` и `pods/ephemeralcontainers`, а также права изменения шаблонов Pod, облачных привязок и аннотаций идентичности. Ограничивайте эти операции для привилегированных нагрузок и фиксируйте необходимые исключения для диагностики. Отключайте автоматическое подключение токена сервисной учетной записи, если токен API Kubernetes не нужен, но проверяйте работу явно настроенной проекции токена для поставщика там, где она нужна федерации.

[Примеры политик](/ru/reference/security-policy-examples/overview/) проверяют конфигурацию одного Pod до развертывания. Они не аутентифицируют автора и не обеспечивают контроль допуска Kubernetes, поэтому не заменяют границу выбора идентичности.

## 4. Проверьте источник учетных данных и сетевую границу

Проверьте порядок выбора источников учетных данных в используемой версии SDK. Удалите статические ключи доступа и переменные окружения, из-за которых SDK выбирает другие учетные данные вместо федерации. На тестовом экземпляре средствами диагностики поставщика определите, от имени какого субъекта фактически выполняются запросы. Сопоставьте полученные сведения с безопасным запросом к ресурсу и событием аудита. Сведения об идентичности сами по себе не доказывают права на ресурсы.

Не позволяйте обычным нагрузкам получать учетные данные узла. Проверяйте реальный сетевой путь во время исполнения, включая Pod с сетью узла, прокси, IPv6 и SSRF приложения. IMDSv2 полезен в AWS, но не заменяет изоляцию узла и ограничения доступа. В EKS сервис IMDS доступен из Pod, использующих сеть узла; назначение Pod Identity или IRSA не устраняет этот путь.

Сохраняйте доступ к предназначенному нагрузке интерфейсу учетных данных. GKE использует интеграцию с метаданными для федерации, а EKS Pod Identity интерфейс своего агента. Полный запрет трафика к адресам локального сегмента может нарушить штатную выдачу учетных данных, но сам по себе не доказывает изоляцию. Проверяйте, что назначенная идентичность работает, а идентичность узла и учетные данные соседних нагрузок недоступны.

Федерация не защищает от компрометации ядра узла или привилегированного контейнера. Размещайте нагрузки с существенно разными требованиями доверия в вычислительных средах, обеспечивающих необходимую изоляцию и минимизируйте права самого узла. Работа сетевой политики зависит от CNI и пути к метаданным; проверяйте фактическое применение, а не только наличие манифеста.

## 5. Проверьте эффективную авторизацию

Оценивайте полный набор разрешений, включая политики ресурсов и ограничения организации. Ищите слишком широкие шаблоны ресурсов, права получения произвольных ролей, действия от имени других идентичностей, создание учетных данных, администрирование политик и права развернуть более привилегированную нагрузку. Разделяйте доступ к бизнес-данным, управление идентичностями и полномочия релиза.

Используйте анализ и моделирование политик поставщика для поиска ошибок, затем выполните контролируемый разрешенный запрос и запрещенные запросы к реальным ресурсам вне рабочей среды. Моделирование не воспроизводит все политики ресурсов, ограничения организации, условия сервисов и задержки распространения изменений. Фиксируйте субъекта, ресурс, операцию, результат и соответствующее событие аудита.

Выбирайте срок действия учетных данных и сессий в пределах ограничений поставщика с учетом того, как нагрузка обновляет учетные данные и как долго раскрытые данные могут оставаться пригодными для использования. Документируйте это эксплуатационное допущение вместо универсального срока для всех систем. Проверяйте обновление, смену издателя и ключей, временные отказы поставщика и восстановление приложения без резервных статических учетных данных. Уже открытые соединения с ресурсами и последующие сессии могут пережить истечение учетных данных; для них нужна отдельная процедура завершения.

## 6. Ограничьте уже выданные учетные данные

Подготовьте две отдельные операции: прекращение новой выдачи и ограничение уже выданных учетных данных или доступа. Удаление привязки или доверия федерации обычно решает первую задачу; не объявляйте вследствие этого все активные сессии отозванными.

Для обычных сессий ролей AWS IAM механизм отзыва добавляет явный запрет с условием `aws:TokenIssueTime`. Он затрагивает все сессии роли, соответствующие условию запрета, включая легитимные нагрузки. Сохраняйте запрет до истечения срока действия затронутых учетных данных, запретите атакующему получать новые сессии роли и отдельно ограничьте сессии других ролей, полученные далее по цепочке. Для IAM Identity Center и ролей, связанных с сервисами действуют другие поддерживаемые процедуры. Проверяйте результат безопасной операцией над ресурсом с заранее полученной тестовой сессией: `GetCallerIdentity` не проверяет отзыв авторизации.

Для интеграций Google Cloud и Microsoft Entra определите фактический тип выданного токена, срок действия, поведение авторизации ресурса и применимый механизм отзыва. Не предполагайте, что удаление федеративных учетных данных сразу аннулирует токен доступа к ресурсу. Проверяйте выбранное удаление прав, запрет на стороне ресурса, остановку нагрузки или поддерживаемый отзыв с ранее полученной сессией; фиксируйте время распространения и остаточный доступ. Остановка нагрузки прекращает запросы новых учетных данных этим экземпляром, но не аннулирует токен доступа, скопированный атакующим.

Отдельно ограничивайте открытые сессии БД, подписанные URL, скопированные секреты и производные учетные данные. Не восстанавливайте доступ удалением временного запрета, пока раскрытые учетные данные еще можно использовать. Для восстановления нужны чистые экземпляры нагрузки, проверенные настройки доверия и разрешений, а также подтверждение, что разрешенный запрос проходит, а запрещенный отклоняется.

## 7. Выполните сценарии проверки

Используйте одноразовые ресурсы и синтетические данные. Проверяйте от имени приложения и участника с меньшим уровнем доверия, имеющего права развертывания; успешный запрос администратора не доказывает доступ нагрузки.

| Сценарий | Требуемый результат | Подтверждение результата |
| --- | --- | --- |
| Неверные издатель, аудитория, пространство имен или ServiceAccount | Нет обмена на учетные данные рабочей среды | Отказ поставщика и выбранная идентичность |
| Менее доверенный участник выбирает защищенную ServiceAccount напрямую или в контроллере | Отказ до получения нагрузкой учетных данных | Решение API или допуска и отсутствие облачного доступа |
| Pod обращается к метаданным узла или интерфейсу другой идентичности | Нельзя получить пригодные для использования учетные данные узла или соседней нагрузки | Результат сетевого запроса из работающего Pod и фактический субъект |
| SDK случайно использует статические учетные данные вместо федерации | Проверка развертывания обнаруживает неверного субъекта | Диагностика источника учетных данных и облачный аудит |
| Нагрузка обращается к постороннему ресурсу или получает постороннюю роль | Отказ | Операция ресурса и аудит авторизации |
| Доверенное имя удалено и создано заново | Устаревшая привязка не дает неожиданного доступа | Запись жизненного цикла идентичности и попытка обмена |
| Выдача отключена при уже активной сессии | Существующий доступ проверен и ограничен отдельно | Отказ запроса к ресурсу с ранее выданной сессией |
| Поставщик или агент временно недоступен | Предусмотренное восстановление без перехода к учетным данным с более широкими полномочиями | Ошибка обновления, поведение приложения и восстановление |

Результат проверки включает карту идентичностей и ресурсов, проверенные условия доверия, пути повышения привилегий и процедуры ограничения с владельцами. Для проверки границ доверия конвейера используйте [безопасность CI/CD](/ru/supply-chain/ci-cd-security/playbook/), для отдельного сервиса секретов или динамических учетных данных [Vault](/ru/platform-security/secrets/vault/playbook/).
