## 1. Область

Эта заметка объясняет две связанные, но разные зоны риска в безопасности контейнеров:
- **Выход из контейнера (container escape)**: атакующий пересекает границу изоляции и получает доступ к ресурсам хоста, его пространствам имен или путям выполнения на хосте.
- **Злоупотребление capabilities (capability abuse)**: атакующий остается внутри пространств имен контейнера, но злоупотребляет избыточными привилегиями Linux для доступа к чувствительным данным и устройствам хоста или опасным функциям ядра.

---

## 2. Почему контейнеры уязвимы

Обычные контейнеры Linux, запускаемые через `runc` или аналогичную среду выполнения, используют ядро узла. Их изоляция зависит от механизмов этого ядра и конфигурации среды выполнения:
- пространства имен (namespaces)
- контрольные группы (cgroups)
- Linux capabilities
- seccomp / LSM
- ограничения файловой системы и среды выполнения
Атака успешна, когда одна или несколько из этих мер неправильно настроены, допускают обход, предоставляют избыточные разрешения или не работают из-за уязвимости ядра или среды выполнения.

---

Среды выполнения с дополнительной изоляцией, например Kata Containers с легковесной виртуальной машиной, используют другую границу доверия. При ревью подтвердите фактически выбранный обработчик `RuntimeClass` и его конфигурацию на узле; имя класса само по себе не доказывает наличие отдельного ядра или требуемой защиты. Для такой среды отдельно проверяйте гипервизор, гостевое ядро и каналы взаимодействия с узлом.

## 3. Что считается выходом из контейнера

Выходом из контейнера считается любое действие атакующего, которое пересекает границы изоляции и достигает контекста хоста. Частые примеры:
- подключение к пространствам имен хоста
- доступ к файловым системам хоста через привилегированные точки монтирования
- использование интерфейсов управления средой выполнения контейнеров для выполнения кода на уровне хоста
- злоупотребление файлами управления cgroup так, чтобы ядро хоста выполнило код, контролируемый атакующим
- эксплуатация уязвимостей ядра для получения привилегий, эквивалентных хосту

---

## 4. Основные векторы атак для выхода из контейнера

### 4.1 Переход в пространства имен хоста

При наличии необходимых прав и доступа к дескрипторам атакующий может использовать `setns` или `nsenter` для перехода в доступные пространства имен хоста. Для каждого типа пространства имен действуют отдельные ограничения: например, из дочернего пространства имен PID нельзя перейти в родительское через `setns`. Вызовы `unshare` и `clone` с флагами `CLONE_NEW*` создают новые пространства имен, а не присоединяют процесс к существующим пространствам имен хоста.

### Типичные предпосылки
- привилегированный контейнер
- доступ к файловым дескрипторам пространств имен хоста
- опасные флаги среды выполнения, такие как `--pid=host`
- слабость ядра или среды выполнения, позволяющая переход между пространствами имен

### Типичные последствия
- видимость процессов хоста
- видимость файловой системы хоста
- видимость сети хоста
- упрощение дальнейшего повышения привилегий и закрепления

---

### 4.2 Злоупотребление cgroup release_agent

Классическая атака на выход из контейнера через ошибку конфигурации: злоупотребление механизмом cgroup v1 `release_agent`.

Этот вектор привязан именно к cgroup v1. В cgroup v1 у иерархии может быть файл `release_agent`: если для cgroup включен `notify_on_release`, ядро запускает указанную вспомогательную программу после освобождения cgroup. При ошибочной выдаче `CAP_SYS_ADMIN`, возможности монтировать файловую систему cgroup или менять файлы управления атакующий может подставить путь к контролируемой им вредоносной нагрузке и добиться выполнения на хосте.

В cgroup v2 используется другой API с единой иерархией и более безопасной моделью делегирования; прямого аналога v1 `release_agent` для этого сценария там нет. Это не означает, что cgroup v2 является полноценной границей безопасности или что ошибки среды выполнения больше невозможны, но конкретный выход через `release_agent` нужно проверять как риск, специфичный для v1.

Для Kubernetes в рабочих средах предпочитайте cgroup v2 на поддерживаемой ОС: Kubernetes считает cgroup v2 стабильным с `v1.25`, а cgroup v1 устаревшим с `v1.35`. Для cgroup v2 используйте поддерживаемое ядро Linux `5.8+`, совместимую с вашей версией Kubernetes поддерживаемую среду выполнения с поддержкой cgroup v2, драйвер cgroup systemd и дистрибутив, где cgroup v2 включен по умолчанию. На узле проверяйте версию командой `stat -fc %T /sys/fs/cgroup/`: `cgroup2fs` означает v2, `tmpfs` обычно указывает на v1.

### Сценарий атаки
Атакующий монтирует cgroup v1, создает дочернюю cgroup, записывает в файлы управления, такие как:
- `notify_on_release`
- `release_agent`
- `cgroup.procs`
После этого ядро хоста выполняет код, контролируемый атакующим, когда cgroup освобождается.

### Типичные предпосылки
- узел работает на cgroup v1 или гибридной конфигурации, где доступен контроллер v1 с `release_agent`
- возможность монтировать или изменять файлы cgroup
- обычно избыточные привилегии, такие как `CAP_SYS_ADMIN`
- возможны ошибки, специфичные для ядра

### Типичные последствия
- выполнение команд на хосте
- путь к полной компрометации хоста

### Сигналы для проверки
- `stat -fc %T /sys/fs/cgroup/` на узле возвращает не `cgroup2fs`
- внутри рабочей нагрузки видны доступные для записи точки монтирования cgroup v1 или файлы `release_agent`
- рабочая нагрузка имеет `privileged: true`, `CAP_SYS_ADMIN` или монтирует `/sys/fs/cgroup` с хоста
- kubelet на Kubernetes `v1.35+` явно запускается с отключенным `failCgroupV1`

---

### 4.3 Злоупотребление сокетом Docker или API среды выполнения

Если контейнер может обращаться к `docker.sock` или открытому API среды выполнения контейнеров, он часто может поручить среде выполнения создать новый привилегированный контейнер или примонтировать файловую систему хоста.

### Сценарий атаки
Атакующий использует API среды выполнения, чтобы запустить дочерний контейнер с:
- повышенными привилегиями
- корнем файловой системы хоста, примонтированным в контейнер
- широким доступом к устройствам
- ослабленными мерами безопасности

### Типичные предпосылки
- примонтирован `docker.sock`
- доступен Docker API
- аналогичным образом открыт канал управления средой выполнения

### Типичные последствия
- быстрое получение доступа к файловой системе хоста
- создание последующих привилегированных контейнеров
- закрепление через рабочие нагрузки, управляемые средой выполнения

---

### 4.4 Доступ к `/proc` хоста из привилегированных контейнеров

Привилегированный контейнер или контейнер с избыточными разрешениями может читать информацию хоста через `/proc`, включая:
- `/proc/1/root/*`
- `/proc/1/environ`
- `/proc/1/maps`
- параметры ядра, такие как `core_pattern`

Доступ к `/proc` хоста опасен тем, что дает атакующему источник разведывательной информации и учетных данных. `hostPID: true` делает процессы узла видимыми внутри контейнера; монтирование `/proc` с хоста или доступ через `/proc/<pid>/root` может показать файловую систему в представлении выбранного процесса хоста; `CAP_SYS_PTRACE` и сходные права помогают пройти проверки доступа на основе ptrace к файлам proc, например `environ` и `maps`.

Что это дает атакующему на практике:
- чтение исходного окружения процессов, где часто остаются облачные учетные данные, токены API, учетные данные прокси и внутренние эндпоинты;
- просмотр файловой системы хоста через `/proc/<pid>/root`, если выбранный процесс находится в нужном пространстве имен монтирования;
- определение запущенных агентов, путей kubelet и среды выполнения контейнеров, сокетов среды выполнения, средств защиты и конфигурационных файлов;
- получение схемы памяти и путей к исполняемым файлам и библиотекам из `maps`, что помогает выбирать дальнейший способ эксплуатации;
- поиск учетных данных kubelet, данных cloud-init, учетных данных узла и других артефактов, которые можно использовать против Kubernetes API или облачных API.

### Типичные предпосылки
- `--privileged`
- `--pid=host`
- `CAP_SYS_PTRACE`
- видимость `/proc` хоста
- слабая изоляция среды выполнения

### Типичные последствия
- сбор учетных данных
- обнаружение токенов
- разведка процессов хоста
- подготовка закрепления или продвижения атакующего внутри инфраструктуры

### Сигналы для проверки
- pod использует `hostPID: true` или монтирует `/proc`, `/sys`, `/run`, `/var/lib/kubelet`, `/var/run` хоста через `hostPath`
- `securityContext` контейнера содержит `privileged: true`, `CAP_SYS_PTRACE` или `CAP_SYS_ADMIN`
- телеметрия среды выполнения фиксирует чтение `/proc/*/environ`, `/proc/*/root`, `/proc/*/maps`, `/proc/sys/kernel/core_pattern`
- события аудита или среды выполнения показывают запуск `nsenter`, `chroot`, `find`/`grep` по путям хоста или обращение к сокетам среды выполнения после чтения `/proc`

---

### 4.5 Эксплуатация уязвимостей ядра и среды выполнения

Атакующий может эксплуатировать доступные из контейнера ошибки ядра или среды выполнения. В зависимости от конкретной уязвимости точками входа могут быть:
- `splice`
- `fsopen` / `fsconfig`
- пути netfilter / netlink
- условия гонки при работе с символическими ссылками
- попытки перезаписи среды выполнения, например через `/proc/self/exe`

### Типичные предпосылки
- уязвимое ядро или среда выполнения
- доступный набор системных вызовов
- часто дополнительные условия по привилегиям или пространствам имен в зависимости от CVE

### Типичные последствия
- повышение привилегий
- выход из пространств имен
- компрометация учетных данных
- выполнение на уровне хоста

---

## 5. Что такое злоупотребление capabilities

Злоупотребление capabilities отличается от полного выхода:
- Атакующий может оставаться внутри пространств имен контейнера, но все равно выполнять опасные действия, потому что контейнеру выданы избыточные Linux capabilities или широкие привилегии среды выполнения.
Во многих средах это более реалистично, чем «чистый» выход, потому что привилегии часто выдаются с избытком ради удобства.

### 5.1 Наборы capabilities: почему `drop`/`add` не описывают всю модель

Linux capabilities не являются одним плоским списком. У процесса есть несколько наборов capabilities, а у исполняемого файла могут быть файловые capabilities. Ядро проверяет фактическое состояние capabilities конкретного потока выполнения, которое не обязательно совпадает с ожидаемым по Kubernetes YAML.

Упрощенная модель:

```text
Effective входит в Permitted
Ambient входит одновременно в Permitted и Inheritable
Bounding ограничивает вклад File Permitted при execve
```

Основные наборы:
- `Effective` - capabilities, которые прямо участвуют в текущих проверках прав ядром.
- `Permitted` - верхняя граница capabilities, которые поток может перевести в `Effective`.
- `Bounding`: ограничивает вклад файлового набора `Permitted` при `execve` и добавление новых capabilities в `Inheritable`. Это не обязательный наднабор текущего `Permitted`: удаление capability из `Bounding` само по себе не удаляет ее из остальных наборов. Уже сохраненная capability в `Inheritable` может участвовать в получении прав через файловый набор `Inheritable`.
- `Inheritable`: набор для передачи capabilities через `execve`; сам по себе не дает прав.
- `Ambient`: способ сохранить capabilities после `execve` для непривилегированных файлов; очищается при запуске привилегированного файла, например с setuid или файловыми capabilities.

Файловые capabilities хранятся на исполняемом файле, обычно в расширенном атрибуте `security.capability`. При `execve` ядро пересчитывает наборы capabilities нового процесса на основе наборов текущего потока и файловых capabilities. Поэтому две конфигурации, которые выглядят одинаково на уровне `capabilities.add/drop`, могут вести себя по-разному после запуска точки входа, `setuid`, `su-exec`, сценариев-оберток или исполняемого файла с файловыми capabilities.

Практический вывод для Kubernetes:
- `securityContext.capabilities.drop/add` является абстракцией CRI и среды выполнения над несколькими наборами Linux capabilities; проверяйте фактическое поведение во время выполнения, а не только в YAML.
- `drop: ["ALL"]` должен убирать capability из Effective/Permitted/Bounding; если capability остается в Bounding или возвращается через файловую capability, принцип минимально необходимых привилегий не соблюден.
- `allowPrivilegeEscalation: false` включает `no_new_privs` и блокирует получение новых привилегий через `execve`, включая setuid и файловые capabilities. Это не заменяет `drop: ["ALL"]`, но закрывает важный класс способов возврата capabilities.
- Kubernetes обычно не задает Ambient capabilities. Если приложение сначала запускается с capability, затем выполняет `setuid` или сбрасывает привилегии и ожидает сохранить capability после `execve`, его работа может нарушиться. Это не повод выдавать широкие capabilities; нужно изменить модель запуска или явно документировать исключение.

Проверка внутри Pod:

```bash
kubectl exec -n <ns> <pod> -- sh -c "grep -E 'Cap(Inh|Prm|Eff|Bnd|Amb)|NoNewPrivs' /proc/1/status"
```

Что должно попасть в подтверждение:
- `CapInh`, `CapEff`, `CapPrm`, `CapBnd`, `CapAmb` для основного процесса;
- подтверждение `NoNewPrivs: 1`, если политика требует `allowPrivilegeEscalation: false`;
- список файловых capabilities внутри образа для исполняемых файлов, которым они действительно нужны;
- объяснение, почему capability нельзя заменить непривилегированным портом, подготовкой при инициализации, томом Kubernetes или CSI, sidecar, агентом либо отдельной изолированной рабочей нагрузкой.

## 6. Основные векторы атак при злоупотреблении capabilities

### 6.1 Избыточная `CAP_SYS_ADMIN`

### Что это позволяет
В зависимости от контекста может позволять:
- монтирование файловых систем
- управление пространствами имен
- взаимодействие с чувствительными интерфейсами ядра
- широкие административные действия, которые никогда не должны быть нормой для большинства рабочих нагрузок

### Примеры злоупотребления
- монтирование файловых систем, связанных с хостом
- манипуляции со структурами cgroup
- создание путей доступа к чувствительным ресурсам ядра или хоста

### Последствия
Даже без пересечения границ пространств имен это может дать доступ к данным хоста или прямые пути к дальнейшему повышению привилегий.

---

### 6.2 `CAP_SYS_PTRACE` при видимости PID хоста

### Примеры злоупотребления
- чтение `/proc/1/environ`
- чтение `/proc/1/maps`
- исследование состояния процессов и схемы памяти
- подключение к процессу хоста или чтение файлов proc, доступ к которым регулируется проверками ptrace

### Почему это важно
Переменные окружения часто содержат:
- облачные учетные данные
- токены API
- секреты сервисов
- внутренние эндпоинты

`/proc/<pid>/maps` обычно не раскрывает секреты напрямую, но показывает отображения памяти, пути к исполняемым файлам и библиотекам, области кучи и стека, а также отображения удаленных файлов. Для атакующего это снижает неопределенность после эксплуатации: проще понять, какие процессы важны, какие версии библиотек используются и где искать следующую слабую меру защиты.

### Последствия
Это один из самых ценных векторов кражи учетных данных и существенный фактор продвижения атакующего внутри инфраструктуры.

---

### 6.3 `CAP_NET_RAW` и доступ к сырым сокетам

### Примеры злоупотребления
- захват пакетов
- ARP и разведка интерфейсов
- низкоуровневое сетевое взаимодействие, не ожидаемое для обычных контейнеров приложений

### Последствия
- сетевая разведка
- возможности перехвата учетных данных
- помощь в продвижении атакующего внутри инфраструктуры или злоупотреблениях, связанных с подменой сетевых данных

---

### 6.4 Контейнеры `--privileged`

### Типичные свойства
- все capabilities
- широкий доступ к устройствам
- более слабые ограничения seccomp
- более слабая изоляция AppArmor/LSM в зависимости от конфигурации

### Примеры злоупотребления
- монтирование блочных устройств хоста, таких как `/dev/sda1`
- чтение `/dev/kmsg`
- использование `keyctl`
- взаимодействие с путями, связанными с BPF
- попытки прохода путей загрузки модулей

### Последствия
Привилегированному контейнеру часто не нужен классический выход. У него уже может быть достаточно возможностей для фактической компрометации узла.

---

### 6.5 Доступ к устройствам хоста и чувствительным интерфейсам ядра

### Цели злоупотребления
- блочные устройства
- `/dev/kmsg`
- связки ключей ядра
- интерфейсы BPF
- пути загрузки модулей

### Последствия
- разведка хоста
- подготовка закрепления
- возможности несанкционированного изменения
- развитие атаки после эксплуатации

---

## 7. Разница между выходом и злоупотреблением capabilities

### Выход из контейнера
Атакующий пересекает границы изоляции.

Примеры:
- присоединение к пространствам имен хоста
- использование API среды выполнения для создания привилегированных контейнеров с монтированием ресурсов хоста
- эксплуатация ошибок ядра для получения контекста хоста

### Злоупотребление capabilities
Атакующий остается в назначенном контейнерном контексте, но этот контекст уже предоставляет избыточные права.

Примеры:
- чтение `/proc/1/environ`
- монтирование чувствительных файловых систем
- использование сырых сокетов
- доступ к `/dev/kmsg`
- злоупотребление связками ключей или механизмами BPF

### Почему это различие важно
Ревью безопасности, которое ищет только «выход», может пропустить более частую практическую ситуацию: контейнер формально не вышел наружу, но все равно раскрыл секреты хоста или дал возможность компрометации узла.

---

## 8. Пользовательские пространства имен как мера снижения риска

Пользовательские пространства имен не устраняют все векторы выхода и не превращают контейнер в полноценную границу безопасности, но меняют последствия компрометации. При `hostUsers: false` root и capabilities внутри контейнера сопоставляются с непривилегированным диапазоном UID/GID хоста, поэтому UID `0` в контейнере не равен UID `0` на узле.

Это особенно важно для рабочих нагрузок, которым исторически требовались root или отдельные capabilities. В Kubernetes `v1.36+` пользовательские пространства имен доступны для общего применения (GA) для рабочих нагрузок Linux, поэтому `hostUsers: false` становится практической мерой снижения масштаба ущерба в рабочих средах, а не экспериментальной настройкой.

Применимость при эксплуатации стала выше благодаря ID-mapped mounts: kubelet больше не должен массово выполнять рекурсивный `chown` данных тома только ради смены представления UID/GID внутри контейнера. Сопоставление идентификаторов ядром при монтировании делает эту меру реалистичнее для рабочих нагрузок с состоянием или интенсивным использованием томов, но внедрение в рабочей среде все равно требует подтверждения совместимости узла и среды выполнения: Linux `6.3+` или поддерживаемое поставщиком ядро с поддержкой ID-mapped mounts для всех файловых систем рабочей нагрузки, containerd `2.0+` или CRI-O `1.25+`, а также среда выполнения OCI с поддержкой пользовательских пространств имен, например `runc` `1.2+` или `crun` `1.9+`. При `hostUsers: false` Kubernetes запрещает `hostNetwork: true`, `hostIPC: true`, `hostPID: true` и `volumeDevices` во всех типах контейнеров pod. Это ограничения API, которые нельзя обойти подтверждением совместимости хранилища. Тома NFS также не поддерживаются: клиент NFS в Linux пока не поддерживает необходимые ID-mapped mounts. Во время внедрения отслеживайте счетчики kubelet `started_user_namespaced_pods_total` и `started_user_namespaced_pods_errors_total`: первый считает попытки создания, второй ошибки. Успешное прохождение контроля допуска само по себе не подтверждает запуск pod.

Указанные минимальные версии описывают поддержку функции, а не безопасный выбор версии для рабочей среды. Используйте поддерживаемые поставщиком версии ядра и сред выполнения с актуальными исправлениями безопасности, совместимые с вашей версией Kubernetes.

Даже с пользовательскими пространствами имен продолжайте запрещать `privileged: true`, минимизировать capabilities, применять seccomp/LSM и контролировать пространства имен хоста, `hostPath` и сокеты среды выполнения. Этот слой снижает последствия, но не заменяет остальные меры защиты среды выполнения.

## 9. Путь повышения привилегий в Kubernetes

В Kubernetes выход из контейнера или злоупотребление capabilities часто становится инцидентом, выходящим за пределы узла. Типовая цепочка выглядит так:
- рабочая нагрузка получает доступ к хосту через `privileged`, пространство имен хоста, чувствительный `hostPath` или сокет среды выполнения;
- атакующий читает конфигурации kubelet или администратора, учетные данные ServiceAccount, метаданные среды выполнения или файловую систему хоста;
- полученные учетные данные используются против Kubernetes API;
- последствия расширяются до чтения Secret, создания рабочих нагрузок, продвижения атакующего внутри инфраструктуры или закрепления через дрейф конфигурации RBAC и контроля допуска.

При ревью фиксируйте не только факт доступа к хосту, но и следующий доступный шаг атаки на плоскость управления: какие kubeconfig, токены и учетные данные доступны, какие действия через API они позволяют и какие события аудита или среды выполнения должны возникнуть. Для безопасной проверки пути атаки используйте отдельный плейбук: [kubernetes/adversarial-validation/playbook.ru.md](/Product-security-playbook/ru/platform-security/kubernetes/adversarial-validation/playbook/).

## 10. Типичные первопричины

Большинство этих векторов атак зависят от одного или нескольких следующих сбоев:
- запуск контейнеров с `--privileged`
- монтирование `docker.sock`
- использование `hostPID`, `hostNetwork` или монтирования файловой системы хоста без строгого обоснования
- выдача опасных capabilities, таких как `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_NET_RAW`
- слабая конфигурация seccomp / AppArmor / SELinux
- уязвимые версии ядра или среды выполнения
- слабый контроль создания DaemonSet и pod в Kubernetes
- предположение, что контейнеры являются жесткой границей безопасности (то есть уже дают достаточную изоляцию)

## 11. Вопросы для ревью безопасности

При ревью рабочей нагрузки задайте вопросы:
- Может ли контейнер получить доступ к пространствам имен хоста?
- Может ли он обращаться к интерфейсам управления средой выполнения, например `docker.sock`?
- Может ли он читать пути хоста в `/proc`?
- Есть ли у него опасные capabilities?
- Является ли он привилегированным?
- Может ли он монтировать файловые системы или получать доступ к блочным устройствам?
- Может ли он создавать сырые сокеты?
- Может ли он обращаться к интерфейсам ядра, таким как связки ключей, BPF или механизмы загрузки модулей?
- Включен ли `hostUsers: false`, если рабочая нагрузка работает на Linux и совместима с пользовательскими пространствами имен?
- Подвержены ли версии ПО узла, ядра или среды выполнения известным способам выхода из контейнера?
- Приведет ли компрометация этого контейнера к раскрытию учетных данных хоста или позволит привилегированные последующие действия?
- Какие действия через Kubernetes API станут возможны после получения доступа к узлу?
