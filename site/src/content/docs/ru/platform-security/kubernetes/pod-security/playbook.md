## 1. Область и цель

Фокус строго на **безопасности среды выполнения pod и контейнеров**:
- Охватывает только **меры на уровне рабочей нагрузки**
- Исключает **сетевое взаимодействие, входящий трафик и политики уровня кластера**
- Цель: **минимизировать влияние в случае компрометации контейнера**

---

## 2. Модель угроз (кратко)

Фокус: **что защищается и от кого**

**Активы:**
- Узел и его операционная система
- Плоскость управления Kubernetes (косвенный доступ)
- Секреты и токены ServiceAccount
- Другие pod на том же узле

**Атакующий:**
- Компрометированное приложение внутри контейнера
- Вредоносный или уязвимый образ контейнера (цепочка поставки)

---

## 3. Векторы атак на уровне pod

### Повышение привилегий

- Исполняемые файлы с setuid/setgid
- Опасные Linux capabilities (например, `CAP_SYS_ADMIN`)
- Запуск контейнеров от root
- Неправильное использование режима `privileged`

### Выход из контейнера

- Доступ к пространствам имен хоста
- Доступность `/proc`, `/sys`
- Эксплуатация небезопасных системных вызовов
- Доступ к файловой системе хоста через небезопасные точки монтирования

### Продвижение атакующего внутри инфраструктуры

- Злоупотребление токенами ServiceAccount
- Неавторизованный доступ к Kubernetes API
- Доступ к общим или чувствительным томам
- Повторное использование учетных записей по умолчанию с избыточными правами

---

## 4. Базовые меры безопасности

Меры контроля сгруппированы по областям безопасности.

Где релевантно, различайте:
- **Меры уровня pod:** влияют на весь pod
- **Меры уровня контейнера:** должны применяться к каждому контейнеру

---

### 4.1 Учетные данные процесса и привилегии

**Меры уровня контейнера:**
- `runAsNonRoot: true`
- `runAsUser` (фиксированный, ненулевой UID)
- `runAsGroup` (фиксированный, ненулевой GID)
- `allowPrivilegeEscalation: false`
- `privileged: false`

**Меры уровня pod:**
- `hostUsers: false`

**Область действия мер:** `runAsNonRoot` запрещает запуск процесса контейнера с UID `0`; `hostUsers: false` задает отдельное пользовательское пространство имен для Pod. Запуск компонентов узла в режиме rootless ограничивает привилегии самого kubelet и среды выполнения относительно хоста и требует отдельной настройки. Значение `hostUsers: false` не подтверждает, что узел работает в режиме rootless. Проверки этого режима описаны в [ревью безопасности кластера, §3.8](/Product-security-playbook/ru/platform-security/kubernetes/cluster-security-review/playbook/#38-компоненты-узла-без-root-привилегий-rootless).

**User namespaces в Kubernetes `v1.36+`:**
- User Namespaces общедоступны (GA) для рабочих нагрузок Linux; включение на уровне pod выполняется через `hostUsers: false`.
- Для рабочих сред используйте `hostUsers: false` как стандартную рекомендацию по изоляции рабочих нагрузок там, где это совместимо со средой выполнения контейнеров, ядром и стеком хранения данных.
- При включенном user namespace UID `0` внутри контейнера не является UID `0` на хосте: root и GID/UID контейнера сопоставляются с непривилегированным диапазоном идентификаторов на узле.
- Это снижает масштаб ущерба при выходе из контейнера, ошибках монтирования и уязвимостях, зависящих от UID/GID хоста, но не заменяет `runAsNonRoot`, `seccompProfile.type: RuntimeDefault`, `capabilities.drop: ["ALL"]` и запрет `privileged: true`.
- Capabilities при `hostUsers: false` ограничиваются пространством имен: например, `CAP_NET_ADMIN` может разрешать административные действия над локальными ресурсами контейнера, но не хоста. Даже в таком режиме выдавайте capabilities только по явному обоснованию, с владельцем и сроком действия.

**Совместимость и сценарии отказа для `hostUsers: false`:**
- Не считайте `hostUsers: false` простым YAML-флагом. Проверяйте его на той же минорной версии Kubernetes, с теми же ядром, средой выполнения, CSI, стеком хранения данных и политикой допуска, которые используются в рабочей среде.
- Минимальное подтверждение среды выполнения: Linux `6.3+` или поддерживаемое поставщиком ядро с ID-mapped mounts для всех файловых систем рабочей нагрузки, containerd `2.0+` или CRI-O `1.25+`, среда выполнения OCI с поддержкой пользовательских namespaces, например `runc` `1.2+` или `crun` `1.9+`, и события или метрики kubelet, подтверждающие успешное создание Pod с пользовательским namespace.
- Развертывание выполняйте поэтапно: сначала рабочие нагрузки без состояния, `hostNetwork`, `hostPID`, `hostIPC`, блочных `volumeDevices` и специальных требований к хранилищу; затем нагрузки с состоянием и интенсивным использованием хранилища: только после проверки совместимости CSI и хранилища; платформенные нагрузки: после отдельного архитектурного ревью.
- Для образов, которым действительно требуется поведение, аналогичное root внутри контейнера, используйте отдельный процесс исключения: укажите владельца, срок действия, причину несовместимости с `runAsNonRoot`, подтверждение того, что UID/GID на хосте остаются непривилегированными, и компенсирующие меры (`seccomp`, удаление capabilities, корневая файловая система только для чтения, ограниченные тома).
- Pod с user namespaces не могут использовать пространства имен хоста: `hostNetwork: true`, `hostPID: true` и `hostIPC: true` несовместимы и должны отклоняться при контроле допуска или проверке развертывания.
- Блочные устройства `volumeDevices` несовместимы с pod, использующими user namespaces. Рабочие нагрузки с состоянием или интенсивным использованием хранилища требуют отдельного теста совместимости хранилища перед внедрением этой меры.
- Тома NFS несовместимы с pod, использующими user namespaces, пока клиент NFS в Linux не поддерживает idmapped mounts; считайте рабочие нагрузки на NFS несовместимыми, если платформенная команда не подтвердила поддержку на конкретном ядре и используемом пути доступа к хранилищу.
- Pod Security Standards ослабляют проверки `runAsNonRoot` и `runAsUser` для pod с user namespaces, потому что UID `0` контейнера сопоставляется с непривилегированным UID хоста. Это не означает, что «root безопасен по умолчанию»; для обычных рабочих нагрузок приложений сохраняйте `runAsNonRoot: true`, если нет документированной причины запускаться от root внутри user namespace.
- Обязательные проверки: тест контроля допуска для запрещенных комбинаций пространств имен хоста, тест развертывания с реальными томами рабочей нагрузки, подтверждение совместимости узла и среды выполнения, мониторинг метрик kubelet `started_user_namespaced_pods_total` / `started_user_namespaced_pods_errors_total` и тест PSS, показывающий, что результат применения политики namespace понятен команде.

**Важная семантика `securityContext` (Kubernetes):**
- Если одно и то же поле задано и на уровне Pod, и на уровне Container, значение из `container.securityContext` перекрывает значение из `pod.spec.securityContext`.
- `allowPrivilegeEscalation` напрямую управляет флагом Linux `no_new_privs` для процесса контейнера.
- `allowPrivilegeEscalation: false` фактически не дает ожидаемого эффекта, если контейнер запускается как `privileged: true` или имеет `CAP_SYS_ADMIN`.

**Назначение:**
- Предотвратить повышение привилегий через исполняемые файлы с setuid/setgid
- Убрать неявные root-привилегии
- Предотвратить выполнение в контейнере почти на уровне хоста

### 4.2 Linux Capabilities

**Меры уровня контейнера:**
- `capabilities.drop: ["ALL"]`
- Возвращайте только явно необходимые capabilities

**Критично:**
- Избегайте `CAP_SYS_ADMIN`
- Избегайте `CAP_NET_ADMIN`
- Избегайте выдачи capabilities без документированного обоснования

**Назначение:**
- Минимизировать доступные привилегированные операции ядра
- Снизить возможности повышения привилегий и выхода из контейнера

Для ревью не ограничивайтесь YAML. `capabilities.drop/add` управляет несколькими наборами Linux capabilities через CRI и среду выполнения, а итоговое состояние зависит от точки входа, `execve`, файловых capabilities и `allowPrivilegeEscalation`. Для спорных рабочих нагрузок проверяйте `CapEff`, `CapPrm`, `CapBnd`, `CapAmb` и `NoNewPrivs` во время выполнения; подробная модель описана в [обзоре выхода из контейнера и злоупотребления capabilities](/Product-security-playbook/ru/platform-security/kubernetes/container-escape-capability-abuse/overview/).

### 4.3 Усиление защиты файловой системы

**Меры уровня контейнера:**
- `readOnlyRootFilesystem: true`

**Почему это важно:**
- `readOnlyRootFilesystem: false` оставляет корневую файловую систему контейнера доступной для записи. После компрометации процесса атакующий может записывать полезную нагрузку, менять файлы приложения или конфигурацию, размещать загрузчики и web-shell, а также усложнять расследование за счет локальных изменений внутри контейнера.
- Доступные для записи пути должны быть явными и ограниченными: `/tmp`, кеш или каталоги журналов выносите в отдельные точки монтирования с понятным назначением, жизненным циклом и лимитами, а не оставляйте всю корневую файловую систему доступной для записи.

**Дополнительные рекомендации:**
- Предоставляйте явные точки монтирования с доступом на запись только там, где они нужны приложению
- Для рабочих нагрузок с `readOnlyRootFilesystem: true` используйте выделенные тома `emptyDir` для необходимых путей с доступом на запись (например, `/tmp` и каталогов журналов приложения)
- Используйте `emptyDir` только когда это необходимо
- Избегайте хранения постоянных или чувствительных данных в доступных для записи путях контейнера

### 4.4 Меры контроля томов

**Ограничения:**
- Избегайте `hostPath`, если это не строго необходимо
- Используйте `readOnly: true`, где возможно
- Минимизируйте количество примонтированных томов
- Монтируйте только пути, необходимые приложению
- Избегайте совместного использования чувствительных томов несвязанными рабочими нагрузками

**Точки монтирования с высоким риском:**
- `/var/run/docker.sock`
- `/proc`
- `/sys`
- Любой путь, примонтированный с хоста
- Сокеты среды выполнения или пути устройств, доступные с хоста

**Назначение:**
- Предотвратить прямое взаимодействие с хостом
- Снизить риск компрометации узла и раскрытия учетных данных

**Проверки атакующих сценариев:**
- проверьте, что рабочие нагрузки приложений не монтируют `docker.sock`, `containerd.sock`, сокеты CRI, `/proc`, `/sys` и чувствительные пути хоста;
- запрещайте монтирование сокетов среды выполнения через политику допуска; исключения допускайте только для доверенных рабочих нагрузок платформы или сборки с владельцем, сроком действия и компенсирующими мерами;
- после устранения повторите тот же запрос или тест политики, чтобы подтвердить, что развертывание с небезопасной точкой монтирования больше не проходит.

### 4.5 Изоляция на уровне ядра

**Меры уровня контейнера:**
- `seccompProfile.type: RuntimeDefault`
- `appArmorProfile.type: RuntimeDefault` на узлах Linux с AppArmor
- `procMount: Default`
- Для собственного профиля разрешайте только обоснованные системные вызовы; вызовы с высоким риском и комбинации для обхода ограничений проверяйте отдельно

**Важное подтверждение seccomp:**
- Актуальный профиль Pod Security Standards `restricted` требует явно заданного `seccompProfile.type: RuntimeDefault` или `Localhost` на уровне pod или контейнера; `baseline` только блокирует явный `Unconfined`.
- Рабочие нагрузки вне принудительно применяемого `restricted`, устаревшие namespace и случаи исключений все еще могут запускаться без явно указанного профиля seccomp. Если на узле не включен kubelet `--seccomp-default` / `seccompDefault`, такой профиль может фактически выполняться как `Unconfined`.
- Подтверждение для рабочей среды должно показывать принудительное применение `restricted` при допуске с явными полями seccomp, эквивалентную собственную политику допуска либо выбор `RuntimeDefault` по умолчанию на узле, а также проверку фактического поведения среды выполнения там, где это возможно.

**AppArmor и SELinux:**
- Если узлы поддерживают AppArmor, явно задавайте `appArmorProfile.type: RuntimeDefault` для рабочих нагрузок приложений. Не полагайтесь только на неявное значение по умолчанию: если AppArmor выключен на узле, неуказанный профиль может не обеспечить ограничений во время выполнения.
- `appArmorProfile.type: Unconfined` запрещайте через политику допуска. `Localhost` допускайте только для заранее загруженных профилей на всех подходящих узлах, с владельцем, процессом развертывания и регрессионным тестом.
- `seLinuxOptions` используйте только в кластерах с включенным SELinux, где метками, поведением хранилища и политикой среды выполнения управляет платформенная команда. Собственные метки SELinux без модели ответственности часто нарушают совместимость томов и затрудняют расследование.
- При использовании `SELinuxChangePolicy` или `SELinuxMount` в кластерах с включенным SELinux перед развертыванием проверяйте события pod и платформенные метрики на конфликты меток томов, особенно для общих томов и разных меток SELinux.

**Sysctls:**
- По умолчанию запрещайте рабочим нагрузкам задавать `spec.securityContext.sysctls`, кроме явно разрешенного безопасного подмножества из Pod Security Standards для вашей минорной версии Kubernetes.
- Небезопасные sysctl допускайте только для специальных сценариев с требованиями к производительности или работе в реальном времени: отдельный пул узлов, taints/tolerations, владелец, срок действия, нагрузочный тест и план отката. Не размещайте обычные рабочие нагрузки приложений на узлах с расширенным `allowed-unsafe-sysctls`.

Подробное ревью seccomp (опасные системные вызовы, `io_uring`/`bpf`, проверки комбинаций и контроль в CI): [kubernetes/seccomp/checklist.ru.md](/Product-security-playbook/ru/platform-security/kubernetes/seccomp/checklist/)

### 4.6 ServiceAccount и доступ к API

**Меры уровня pod:**
- `automountServiceAccountToken: false` по умолчанию
- Используйте выделенный ServiceAccount только когда требуется доступ к Kubernetes API
- Применяйте RBAC по принципу минимально необходимых привилегий
- Не используйте ServiceAccount `default` соответствующего namespace для рабочих нагрузок приложений

**Закрываемый риск:**
- Продвижение атакующего через Kubernetes API
- Злоупотребление токенами после компрометации контейнера
- Неконтролируемое повторное использование привилегий между рабочими нагрузками

**Обязательные проверки политик допуска (предотвращение обхода на уровне namespace):**
- Отклоняйте pod, которые не задают `automountServiceAccountToken: false`, если они явно не аннотированы как рабочие нагрузки, вызывающие API.
- Отклоняйте pod, использующие `serviceAccountName: default`.
- Требуйте явно указанный ServiceAccount для каждой рабочей нагрузки.
- Применяйте эти проверки через политику допуска (Kyverno/Gatekeeper/ValidatingAdmissionPolicy), а не только через ревью документации.
- Требуйте объекты исключений с владельцем и сроком действия для любого обхода политики.

### 4.7 Изоляция хоста и пространств имен

**Меры уровня pod:**
- `hostNetwork: false`
- `hostPID: false`
- `hostIPC: false`
- `shareProcessNamespace: false`

**Критично для `shareProcessNamespace`:**
- Если `shareProcessNamespace: true`, процессы становятся видимыми между контейнерами Pod, включая данные из `/proc`.
- Контейнеры могут посылать сигналы процессам в соседних контейнерах.
- Через `/proc/<pid>/root` может открываться доступ к файловой системе соседнего контейнера.
- Для рабочих нагрузок запрещайте `shareProcessNamespace: true` по умолчанию; исключения допускайте только по явно оформленной процедуре аварийного доступа с владельцем и сроком действия.

**Обязательная проверка политики допуска:**
- Отклоняйте pod с `shareProcessNamespace: true` через политику допуска (Kyverno/Gatekeeper/ValidatingAdmissionPolicy), кроме явно зарегистрированных исключений.

**Назначение:**
- Предотвратить доступ к процессам хоста
- Предотвратить доступ к сетевому пространству имен хоста
- Сохранить границы изоляции рабочих нагрузок

### 4.8 Ограничения ресурсов

**Меры среды выполнения на уровне pod и контейнера:**
- Определяйте `resources.requests` для CPU и памяти, чтобы планировщик принимал решения на основе реальных потребностей рабочей нагрузки.
- Определяйте лимиты памяти для рабочих нагрузок, чтобы ограничивать отказ в обслуживании на уровне узла и влияние соседних нагрузок, потребляющих слишком много ресурсов.
- Определяйте requests и limits для `ephemeral-storage` у рабочих нагрузок, которые записывают временные файлы, кеш, журналы, загруженные файлы или сгенерированные артефакты.
- Рассматривайте лимиты CPU как решение для конкретной рабочей нагрузки, а не универсальную настройку безопасности по умолчанию. Лимиты CPU могут вызывать принудительное ограничение процессорного времени и увеличивать задержки у сервисов с пиками нагрузки или чувствительных к задержкам; применяйте их, когда риск отказа в обслуживании или влияния соседних нагрузок выше риска ограничения CPU либо когда этого требует политика платформы.
- Для рабочих нагрузок, доступных из интернета, обслуживающих нескольких арендаторов, выполняющих пакетную обработку, сборку, задачи ИИ или инференс, а также недоверенный код, явно документируйте модель злоупотребления ресурсами и выбирайте ограничения CPU, памяти и временного хранилища.
- Для критичных сервисов подтверждайте лимиты нагрузочным тестированием, а не копируйте типовые значения.

**Меры уровня namespace:**
- применяйте `ResourceQuota` и, где нужно, `LimitRange` для общих защищенных namespace;
- запрещайте pod класса BestEffort в защищенных namespace, если нет явно принятого исключения;
- требуйте, чтобы квоты namespace покрывали CPU, память, количество pod и временное хранилище там, где это поддерживается платформой;
- проверки отказа в обслуживании и `stress-ng` выполняйте только в изолированной среде нагрузочного тестирования или подготовки к выпуску, не в действующем защищенном namespace.

---

### 4.9 Поверхности отладки

**Что контролировать:**
- `pods/exec`
- `pods/attach`
- `pods/portforward`
- `pods/ephemeralcontainers`
- процедуры отладки на уровне узла

**Рекомендация для рабочих сред:**
- ограничьте `exec` и эфемерные контейнеры в чувствительных namespace отдельными ролями поддержки или SRE;
- журналируйте и создавайте оповещения о `exec`, attach/port-forward и добавлении эфемерных контейнеров;
- используйте политику допуска для запрета средств отладки в namespace с особо ценными данными или нагрузками, где это допустимо по условиям эксплуатации.

---

### 4.10 Группы процессов и владение томами

**Меры уровня pod:**
- `runAsGroup` задает основной GID процессов контейнера; используйте фиксированный ненулевой GID вместо неявных значений из образа.
- `fsGroup` применяйте только когда рабочей нагрузке действительно нужен доступ к тому на основе группы. Не используйте его как универсальный способ «починить права» без понимания поведения хранилища.
- Выдавайте минимально необходимые `supplementalGroups`: каждый дополнительный GID расширяет доступ процесса к файлам и примонтированному хранилищу.
- Для Kubernetes `v1.33+` используйте `supplementalGroupsPolicy: Strict` в чувствительных рабочих нагрузках, чтобы группы из `/etc/group` внутри образа не добавлялись неявно к процессу контейнера.
- Для больших PVC и рабочих нагрузок с состоянием используйте `fsGroupChangePolicy: OnRootMismatch`, если драйвер хранилища и модель прав это поддерживают; это снижает задержки запуска из-за рекурсивного изменения владельца.

**Операционные оговорки:**
- `fsGroup` и `fsGroupChangePolicy` работают только для типов томов и CSI-драйверов, которые поддерживают управление владельцем и правами. Для CSI-томов драйвер может брать изменение прав на себя; проверяйте фактические UID/GID владельца и группы внутри запущенного Pod.
- Не назначайте один GID с широкими правами несвязанным рабочим нагрузкам ради удобного доступа к общему хранилищу. Это превращает группу доступа к хранилищу в неявный способ обхода границ namespace и RBAC.
- Если `supplementalGroupsPolicy: Strict` недоступен на части узлов, в Kubernetes `v1.33+` такой pod должен быть отклонен kubelet; в `v1.31-v1.32` поведение альфа-версии могло незаметно переключиться на `Merge`. Проверяйте поддержку функции в пуле узлов и подтверждения из среды выполнения через `id` внутри контейнера или `.status.containerStatuses[].user.linux`, где поле доступно.
- Для pod с несколькими контейнерами и общим `emptyDir` или PVC фиксируйте правила владения: какой контейнер пишет, какой читает, какие пути доступны на запись, какой GID нужен и кто владеет исключением.

**Проверки:**
```bash
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" runAsGroup="}{.spec.securityContext.runAsGroup}{" fsGroup="}{.spec.securityContext.fsGroup}{" supplementalGroups="}{.spec.securityContext.supplementalGroups}{" supplementalGroupsPolicy="}{.spec.securityContext.supplementalGroupsPolicy}{"\n"}{end}'
kubectl exec -n <ns> <pod> -- id
kubectl exec -n <ns> <pod> -- stat -c '%u:%g %a %n' <mounted-path>
```

## 5. Pod Security Standards (PSS)

Согласование базового уровня защиты:
- Целевой уровень: **профиль Restricted**

**Назначение:**
- Использовать базовые требования Kubernetes для усиления защиты pod
- Избежать ситуативных или несогласованных правил безопасности рабочих нагрузок
- Обеспечить минимально приемлемый уровень безопасности Pod

**Важное ограничение:**

Pod Security Standards помогают обеспечивать безопасные значения по умолчанию для спецификаций Pod, но **не** заменяют:
- Доверие к образу и меры контроля цепочки поставки
- Проектирование RBAC и архитектуру учетных записей
- Обнаружение угроз во время выполнения
- Сетевую изоляцию
- Усиление защиты на уровне кластера
- Проверку фактически применяемого seccomp вне принудительного `restricted`: namespace с `baseline`, устаревшими исключениями или собственными политиками все равно должны подтверждать явный `RuntimeDefault` или утвержденный `Localhost` либо настройку seccomp по умолчанию на уровне узла.

### 5.1 Базовое применение

- `pod-security.kubernetes.io/enforce: restricted` во всех защищенных namespace.
- Закрепляйте версию политики для всех режимов на утвержденной минорной версии Kubernetes:
  - `pod-security.kubernetes.io/enforce-version: v<minor>`
  - `pod-security.kubernetes.io/audit-version: v<minor>`
  - `pod-security.kubernetes.io/warn-version: v<minor>`
- Используйте `latest` только в явно назначенных тестовых namespace для поэтапного внедрения или в namespace вне защищенной области, где изменения поведения политики намеренно проверяются перед распространением на весь кластер.
- Разделяйте `warn`/`audit` и `enforce`; рабочая среда не должна опираться только на режим `warn`.
- Считайте seccomp отдельным требованием к подтверждениям среды выполнения: контроль допуска с `restricted` должен отклонять рабочую нагрузку без явного `RuntimeDefault` или утвержденного `Localhost`, эквивалентные собственные политики должны делать то же самое, либо конфигурация узла должна подтверждать, что kubelet `--seccomp-default` / `seccompDefault` включен для namespace, где профили без явного указания временно допускаются.
- Проверяйте дрейф политики namespace каждые `24h`.
- Блокируйте развертывание, если метки namespace ослаблены или удалены.
- При обновлении Kubernetes выполняйте пробную оценку следующей версии PSS без применения изменений до изменения меток namespace, фиксируйте нарушения по владельцам рабочих нагрузок, устраняйте их или утверждайте ограниченные по сроку исключения, затем обновляйте `enforce-version`, `audit-version` и `warn-version` вместе.
- Считайте изменение версии PSS изменением политики: нужны согласование владельца, окно внедрения, план отката и подтверждение после изменений, что в защищенных namespace по-прежнему принудительно применяется `restricted`.

## 6. Антипаттерны

Каждый антипаттерн напрямую увеличивает риск из модели угроз:

- Запуск контейнеров от root
  -> Позволяет повысить привилегии и увеличивает последствия выхода из контейнера

- `privileged: true`
  -> Дает доступ почти на уровне хоста и ломает допущения изоляции

- Добавление широких Linux capabilities без строгой необходимости
  -> Расширяет поверхность атаки ядра и границу привилегий

- Неконтролируемое использование `hostPath`
  -> Позволяет прямой доступ к файловой системе хоста и возможную компрометацию узла

- Монтирование чувствительных интерфейсов хоста, таких как сокеты среды выполнения контейнеров
  -> Может привести к захвату хоста или контролю над другими контейнерами

- Отсутствие профиля seccomp
  -> Открывает более широкий набор системных вызовов и упрощает эксплуатацию уязвимостей ядра

- Использование `procMount`, отличного от значения по умолчанию
  -> Ослабляет изоляцию информации о процессах

- Использование `shareProcessNamespace: true`
  -> Нарушает границы изоляции между контейнерами одного pod и упрощает продвижение атакующего между ними

- Неявные дополнительные группы из образа контейнера
  -> Могут дать процессу доступ к общему хранилищу или файлам, который не виден в манифесте без проверки среды выполнения

- Широкие `fsGroup`/`supplementalGroups` без модели ответственности
  -> Превращают групповой доступ к томам в обходной канал между рабочими нагрузками

- `appArmorProfile.type: Unconfined` или отсутствие подтверждений работы AppArmor на поддерживаемых узлах
  -> Убирает ожидаемый слой защиты LSM и делает выводы PSS и аудита неполными

- Небезопасные sysctl в обычных namespace приложений
  -> Могут влиять на узел или соседние рабочие нагрузки и должны оставаться исключением для изолированных пулов узлов

- Доступная для записи корневая файловая система (`readOnlyRootFilesystem: false`)
  -> Позволяет закрепление, хранение вредоносной нагрузки во время выполнения и изменение файлов приложения или конфигурации внутри контейнера

- Автоматическое монтирование токенов ServiceAccount по умолчанию
  -> Повышает риск злоупотребления Kubernetes API после компрометации

- Использование ServiceAccount `default` соответствующего namespace
  -> Поощряет повторное использование привилегий и слабое разделение учетных записей между рабочими нагрузками
