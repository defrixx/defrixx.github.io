## 1. Область и цель

Этот плейбук описывает **практическое ревью безопасности Kubernetes-кластера** на уровне:
- субъектов развертывания (пользователей и машинных учетных записей);
- цепочки поставки и развертывания;
- внешних и внутренних сервисных границ;
- наблюдаемости для реагирования на инциденты;
- границ контроля допуска, RBAC и ServiceAccount;
- движения секретов от источника до среды выполнения.

Перед проверкой мер, зависящих от версии, зафиксируйте версию Kubernetes вплоть до номера патч-релиза, дистрибутив, поставщика поддержки и даты ее окончания. Используйте поддерживаемый выпуск с актуальными исправлениями безопасности; соответствие минимальной версии, в которой доступна нужная функция, например `v1.30+`, не подтверждает наличие поддержки. Для управляемого сервиса отдельно проверьте условия поддержки поставщика и статус поддержки в исходном проекте.

Приведенные ниже интервалы ревью и сроки реагирования рассчитаны на рабочие среды с назначенными ответственными за платформу и безопасность. Это локальные значения для планирования, а не требования Kubernetes; зафиксируйте утвержденные сроки, владельцев и подтверждение того, что команда способна их соблюдать.

**Цель:**
- сократить вероятность несанкционированного развертывания и скрытого повышения привилегий;
- уменьшить масштаб ущерба при компрометации рабочей нагрузки или CI/CD;
- обеспечить воспроизводимое расследование инцидентов по данным кластера.

## 2. Модель угроз для ревью безопасности кластера

**Что защищаем:**
- права на развертывание и изменение конфигурации кластера;
- цепочку `source -> build -> registry -> deploy`;
- доступ к Kubernetes API, конфигурациям контроля допуска и политикам namespace;
- токены ServiceAccount, секреты приложений, доступ к внешнему хранилищу секретов;
- журнал аудита для расследований.

**Типовой путь атакующего:**
- компрометация учетной записи разработчика или CI;
- несанкционированное развертывание или изменение политики;
- закрепление через дрейф конфигурации RBAC или контроля допуска;
- извлечение секретов и продвижение атакующего внутри инфраструктуры.

## 3. Области ревью и проверки

### 3.1 Кто может выполнять развертывание

**Что проверять:**
- кто имеет `create/update/patch/delete` на ресурсы рабочих нагрузок (`deployments`, `statefulsets`, `daemonsets`, `jobs`, `cronjobs`, `pods`);
- кто имеет права на `pods/exec`, `pods/ephemeralcontainers`, `pods/attach`, `pods/portforward`;
- кто может менять `roles`, `clusterroles`, `rolebindings`, `clusterrolebindings`;
- кто имеет доступ к `nodes/proxy` (широкий доступ к Kubelet API на уровне узла);
- кто имеет доступ к подресурсам Kubelet API с детальным разграничением прав: `nodes/metrics`, `nodes/stats`, `nodes/log`, `nodes/spec`, `nodes/checkpoint`, `nodes/configz`, `nodes/healthz`, `nodes/pods`;
- какие машинные учетные записи реально выполняют развертывание в рабочую среду (контроллеры CD, боты CI).

**Сигналы риска:**
- пользователи или группы с `cluster-admin`, не предназначенные для аварийного доступа;
- права с подстановочным символом (`resources: ["*"]`, `verbs: ["*"]`) в защищенных namespace;
- возможность развертывания в рабочую среду напрямую от учетной записи пользователя, минуя процесс CD;
- доступ к `nodes/proxy`, `escalate`, `bind`, `impersonate` без отдельного согласования безопасности;
- агенты мониторинга и сбора журналов, которым выдан `nodes/proxy`, хотя для их функций достаточно отдельных подресурсов Kubelet API.

**Рекомендация для рабочих сред:**
- развертывание в рабочую среду только через выделенные ServiceAccount для CI/CD;
- пользователи не выполняют развертывание напрямую, кроме ролей аварийного доступа с владельцем и сроком действия;
- ревью всех ClusterRole/ClusterRoleBinding каждые `30d`;
- автоматическое отклонение политик с опасными правами RBAC вне списка разрешенных (`escalate`, `bind`, `impersonate`, `serviceaccounts/token`, `nodes/proxy`);
- для Kubernetes `v1.36+`: `KubeletFineGrainedAuthz` общедоступен (GA), флаг функции включен и зафиксирован в этом состоянии, поэтому рабочие нагрузки наблюдаемости должны использовать минимально необходимые подресурсы (`nodes/metrics`, `nodes/stats`, `nodes/pods` и другие нужные эндпоинты), а не общий `nodes/proxy`;
- запрещайте новые привязки RBAC к `nodes/proxy` для рабочих нагрузок наблюдаемости, если их сценарий сбора метрик или журналов kubelet покрывается детальными правами;
- основные подтверждения для сокращения `nodes/proxy`: `kubectl auth can-i get nodes/metrics|nodes/stats|nodes/pods --as=<subject>` и аналогичные проверки фактически нужных эндпоинтов kubelet;
- дополнительные подтверждения: версия Kubernetes, документация провайдера управляемого сервиса, конфигурация авторизации kubelet и примечания поставщика к выпуску для точной минорной версии кластера;
- если подресурсы с детальным разграничением прав недоступны или заблокированы в конкретной поставке кластера, `nodes/proxy` допустим только как исключение с владельцем, сроком действия, минимальным кругом субъектов и отдельной оценкой зоны поражения.

**Минимальные команды для подтверждения:**
```bash
kubectl get clusterrolebindings,rolebindings -A
kubectl get clusterroles,roles -A -o yaml
kubectl get validatingadmissionpolicy,validatingadmissionpolicybinding -o yaml
kubectl auth can-i create deployments --as=<subject> -n <ns>
kubectl auth can-i get nodes/proxy --as=<subject>
kubectl auth can-i get nodes/metrics --as=<subject>
kubectl auth can-i get nodes/stats --as=<subject>
kubectl auth can-i get nodes/pods --as=<subject>
kubectl get clusterroles -o yaml | grep -n 'nodes/proxy'
# Дополнительные подтверждения зависят от провайдера и способа развертывания:
# соберите минорную версию Kubernetes, конфигурацию авторизации kubelet и примечания провайдера к выпуску
```

### 3.2 Цепочка развертывания

**Что проверять:**
- что инициирует развертывание (слияние PR, тег релиза, ручное применение);
- где выполняется сборка и кто подписывает артефакты;
- как выбирается образ в манифесте (дайджест или изменяемый тег);
- кто имеет право менять описание конвейера, проекты CD и окружения;
- есть ли разделение обязанностей между автором кода и теми, кто согласует и выпускает релиз.

**Сигналы риска:**
- развертывание из локального `kubectl apply` в рабочей среде;
- ссылки на образы только по тегу в рабочей среде, включая теги, похожие на версии, например `:v1.2.3`;
- один и тот же субъект одновременно пишет код, меняет конвейер и проводит релиз;
- отсутствие provenance артефакта и его проверки перед развертыванием.

**Рекомендация для рабочих сред:**
- развертывание только из CI/CD; изменения кластера из конвейера должны допускать аудит и повторное воспроизведение;
- образы для рабочей среды только по дайджесту `@sha256`;
- защита веток и обязательное ревью IaC, манифестов и конфигураций конвейера;
- отдельные роли автора, согласующего и выпускающего релиз.

### 3.3 Внешние и внутренние сервисы

**Что проверять:**
- все точки входа в кластер: `Ingress`, `Gateway`, `LoadBalancer`, `NodePort`;
- какие контроллеры Ingress и реализации Gateway API установлены, кто владеет их `IngressClass`/`GatewayClass` и какие namespace могут прикреплять маршруты;
- объекты Service с заполненным `spec.externalIPs`;
- зависимости рабочих нагрузок по исходящим соединениям (SaaS, облачные API, внутренние сервисы);
- какие namespace и сервисы могут общаться между собой по сети;
- есть ли актуальный реестр сервисов и потоков данных для рабочих сред.

**Сигналы риска:**
- неизвестные публичные эндпоинты;
- внешний доступ к рабочей среде строится на снятом с поддержки контроллере сообщества `ingress-nginx`, особенно без утвержденного исключения и срока миграции;
- использование `Service.spec.externalIPs` в рабочих кластерах или кластерах с несколькими арендаторами;
- отсутствие запрета по умолчанию в NetworkPolicy;
- критичные рабочие нагрузки с неограниченными исходящими соединениями;
- отсутствие владельца у внешних интеграций.

**Рекомендация для рабочих сред:**
- реестр потоков между кластером и внешними системами, а также внутри кластера обновляется не реже `30d`;
- для защищенных namespace действует запрет по умолчанию с явными разрешающими правилами;
- каждый публичный эндпоинт имеет владельца, классификацию данных и SLA по уязвимостям;
- не считайте Ingress API устаревшим: ресурс Ingress остается поддерживаемым, но набор его возможностей заморожен. Для новых сложных сценариев пограничного доступа L7/L4 и долгосрочного развития предпочитайте Gateway API с явно выбранной реализацией и проверкой безопасности;
- разделяйте ресурс `Ingress` и конкретный контроллер. CVE и исправления безопасности обычно относятся к реализации контроллера, webhook, плоскости передачи данных или механизму допуска, а не к самому объекту API `Ingress`. Для контроллера сообщества Kubernetes `ingress-nginx` фиксируйте явное решение о жизненном цикле: инвентаризацию IngressClass и развертываний контроллера, владельцев публичных эндпоинтов, критичные аннотации, пользовательские фрагменты конфигурации, поведение аутентификации и TLS, статус поддержки разработчиками, периодичность исправлений и целевую замену. Поддержка исходного проекта завершилась в марте 2026 года: для контроллера сообщества больше не выпускаются новые версии, исправления ошибок и обновления безопасности. Переходите на поддерживаемую реализацию Gateway API или контроллер Ingress. Продолжение использования требует исключения с владельцем, сроком действия, компенсирующими мерами и сроком миграции; план установки исправлений не восстанавливает поддержку исходного проекта. Не выбирайте этот контроллер для новых развертываний в рабочей среде;
- для Gateway API используйте отдельные базовые требования безопасности ниже. Namespace не должен иметь возможность прикрепить маршрут к общему или публичному Gateway либо сослаться на серверный сервис или TLS-секрет другого namespace без явного разрешения владельца соответствующего ресурса;
- запрещайте новые `Service.spec.externalIPs` через политику допуска: `DenyServiceExternalIPs`, `ValidatingAdmissionPolicy` или проверенный механизм политик. В Kubernetes `v1.36+` это поле объявлено устаревшим; исторически оно небезопасно по умолчанию, потому что пользователь с правом создавать или менять Service может перехватывать трафик к выбранному IP при выполнении условий CVE-2020-8554;
- для существующих `externalIPs` заведите план миграции с владельцем и сроком. Предпочтительные целевые варианты: управляемый `type: LoadBalancer`, Ingress или Gateway API для входящего HTTP(S)/L4-трафика либо `NodePort` только за внешним балансировщиком или межсетевым экраном с явно установленными владельцами IP-адресов и сетевых ACL;
- не заменяйте `externalIPs` ручным изменением `status.loadBalancer.ingress` без отдельной модели прав: изменение `services/status` должно оставаться привилегированной операцией, недоступной обычным учетным записям развертывания.

**Базовые требования безопасности Gateway API:**
- `GatewayClass` считается объектом платформенной команды. Право создавать или изменять `GatewayClass` и параметры контроллера должно быть доступно только владельцам платформы и безопасности, поскольку оно определяет реализацию контроллера и границу доверия.
- `Gateway` для общего или публичного пограничного доступа должен находиться в namespace платформенной команды. Namespace приложений получают право прикреплять `HTTPRoute`/`GRPCRoute`/`TCPRoute` только через явно настроенный `allowedRoutes` на нужном listener.
- `allowedRoutes` должен быть максимально узким: `Same` для Gateway одного арендатора, `Selector` только с управляемыми метками и защитой от их самовольной смены через контроль допуска; `All` недопустим для общего или публичного Gateway без отдельного принятия риска.
- Ссылки между namespace требуют `ReferenceGrant` в namespace владельца целевого ресурса. Это относится к серверным сервисам, TLS-секретам и другим целевым ресурсам; отсутствие `ReferenceGrant` должно делать маршрут или ссылку недействительными, а не приводить к неявному резервному поведению.
- Политика завершения TLS фиксирует, где завершается TLS, какие источники сертификатов разрешены, кто может ссылаться на TLS Secret, какие протоколы, шифры и минимальная версия TLS применяются в реализации контроллера и как выполняется ротация.
- Имена хостов и область действия listener должны быть ограничены: маршрут из namespace приложения не должен захватывать имя хоста с подстановочным символом, чужой домен, привилегированный префикс пути или listener другого арендатора без согласования владельца Gateway.
- Условия состояния маршрута должны отслеживаться как сигналы безопасности: `Accepted=False`, `ResolvedRefs=False`, неожиданная смена `parentRefs`, `backendRefs` или `hostnames` требуют ревью до подачи рабочего трафика.
- Привязка политик (аутентификация и авторизация, WAF, ограничение частоты запросов, нормализация заголовков, CORS, размер запросов, тайм-ауты, повторные попытки) должна иметь владельца и модель приоритетов. Не полагайтесь на настройки конкретного контроллера по умолчанию без явного подтверждения.
- При миграции с `ingress-nginx` не переносите аннотации механически. Для каждой критичной аннотации (`auth`, `rewrite`, `configuration-snippet`, размер тела, буферизация, заголовки прокси, TLS, перенаправления) фиксируйте эквивалент в Gateway API, неподдерживаемое поведение или компенсирующую меру.

**Минимальные команды для подтверждения:**
```bash
kubectl get services -A -o jsonpath='{range .items[?(@.spec.externalIPs)]}{.metadata.namespace}{"/"}{.metadata.name}{" "}{.spec.externalIPs}{"\n"}{end}'
kubectl auth can-i patch services/status --as=<subject> -n <ns>
kubectl get ingressclass,gatewayclass
kubectl get ingress -A
kubectl get gateway,httproute,tcproute,tlsroute,referencegrant -A
kubectl get gateway -A -o yaml
kubectl get httproute,grpcroutes,tcproutes,tlsroutes -A -o yaml
kubectl auth can-i create gatewayclass --as=<subject>
kubectl auth can-i create referencegrant --as=<subject> -n <target-ns>
```

### 3.4 Наблюдаемость для реагирования на инциденты

**Что проверять:**
- включено ли журналирование аудита Kubernetes на уровне `kube-apiserver`;
- есть ли централизованный сбор журналов аудита, журналов плоскости управления и событий среды выполнения;
- охватываются ли события изменения RBAC, контроля допуска, меток namespace и развертываний;
- есть ли корреляция между событием выпуска в CI/CD и фактическими действиями через API.

**Сигналы риска:**
- аудит включен частично или хранится только локально на узле плоскости управления;
- нет событий для критичных операций (`rolebindings`, `clusterrolebindings`, `validatingwebhookconfigurations`, `mutatingwebhookconfigurations`, `namespaces`);
- срок хранения меньше обычной продолжительности жизненного цикла инцидента в вашей организации.

**Рекомендация для рабочих сред:**
- централизованный неизменяемый аудит со сроком хранения минимум `90d` (или дольше по требованиям регулятора);
- для высокорисковых API-операций логируйте не ниже `Request`/`RequestResponse` уровня с учетом утечки чувствительных данных;
- обнаружение событий изменения RBAC, конфигураций webhook, меток безопасности namespace и массового чтения объектов Secret;
- дополняйте аудит API поведенческой телеметрией среды выполнения и сети (например, средствами наблюдаемости CNI и инструментами eBPF), чтобы видеть не только факт развертывания, но и аномальное поведение во время работы;
- проводите учения по восстановлению хронологии инцидента минимум раз в `90d`.

### 3.5 Границы контроля допуска, RBAC и ServiceAccount

**Что проверять:**
- что критичные правила безопасности принудительно применяются через контроль допуска, а не существуют только в документации;
- что RBAC покрывает операции чтения чувствительных ресурсов (контроль допуска не блокирует `get/list/watch`);
- что изменение меток namespace ограничено и не позволяет ослабить границы PSA/NetworkPolicy;
- что `automountServiceAccountToken` отключен по умолчанию для рабочих нагрузок без доступа к API;
- что в рабочей среде не используется ServiceAccount `default` соответствующего namespace;
- используются ли проецируемые токены ServiceAccount для межсервисной аутентификации и внешних интеграций доверия только с явным `audience` конкретного приложения и ограниченным сроком жизни;
- какие рабочие нагрузки могут создавать `tokenreviews` и `subjectaccessreviews` и действительно ли им нужны оба права.

**Сигналы риска:**
- использование только изменяющего webhook без проверяющей политики;
- роли разработчиков могут менять `validatingwebhookconfigurations`/`mutatingwebhookconfigurations`;
- приложение может менять метки namespace и ослаблять принудительно применяемую политику;
- ServiceAccount используется несколькими несвязанными рабочими нагрузками;
- принимающий сервис проверяет токен ServiceAccount без `TokenReview.spec.audiences` или доверяет любому аутентифицированному ServiceAccount;
- рабочая нагрузка приложения привязана к `system:auth-delegator`, хотя ей требуется только TokenReview.

**Рекомендация для рабочих сред:**
- разделяйте ответственность: RBAC отвечает за «кто может», контроль допуска отвечает за «с какими параметрами»;
- для принудительного применения политик используйте `ValidatingAdmissionPolicy` (Kubernetes `v1.30+`) или эквивалент на основе webhook;
- для защищенных namespace политика допуска должна блокировать нарушения, а не только записывать их в аудит или выдавать предупреждения: `ValidatingAdmissionPolicyBinding.validationActions` включает `Deny`, `failurePolicy` остается `Fail`, а параметризованные политики используют `parameterNotFoundAction: Deny`, если отсутствие параметра должно блокировать небезопасное поведение по умолчанию;
- запретите доступ к `escalate` / `bind` / `impersonate` / `serviceaccounts/token` по умолчанию;
- для усиления защиты плоскости управления отдельно оцените `AlwaysPullImages` с учетом эксплуатационных последствий, если он применим в вашем окружении. Он снижает вероятность повторного использования локально кешированного образа без повторной проверки прав на скачивание, но усиливает зависимость от доступности реестра и может нарушать работу изолированных сред или работу при отказе реестра. Он не заменяет закрепление дайджеста и проверку подписи и provenance: повторное скачивание по изменяемому тегу все равно может получить нежелательный артефакт;
- рассматривайте `EventRateLimit` с учетом версии и способа поставки кластера: в исходном Kubernetes это альфа-версия контроллера допуска, отключенная по умолчанию; если плагины допуска в альфа-стадии неприемлемы, предпочитайте ограничение частоты обращений к API и событий, поддерживаемое провайдером, или проверенную собственную политику;
- требуйте отдельный ServiceAccount для каждой рабочей нагрузки и ежеквартальный пересмотр прав;
- для потребителя, которому нужен только TokenReview, создавайте отдельную ClusterRole с единственным правом `create` на `tokenreviews.authentication.k8s.io`; встроенная `system:auth-delegator` также разрешает `subjectaccessreviews` и не является минимальным профилем для такого случая;
- политика допуска для согласованной схемы межсервисной аутентификации должна требовать явный `audience`, ограниченный `expirationSeconds`, монтирование только для чтения и запрет ServiceAccount `default` соответствующего namespace; значение `expirationSeconds` не должно быть ниже установленного Kubernetes минимума `600` секунд;
- проверяйте, что принимающий сервис отказывает в доступе при тайм-ауте, ограничении частоты запросов и недоступности TokenReview, а также оценивайте нагрузку этой схемы на плоскость управления;
- если вместо TokenReview используется локальная проверка OIDC/JWKS, документируйте принятие задержки отзыва: удаление связанного Pod или ServiceAccount не аннулирует токен до `exp`.

### 3.6 Поток секретов

**Что проверять:**
- где создается секрет и находится его авторитетный источник, как он попадает в среду выполнения, где выполняется его ротация;
- есть ли в Git секреты в открытом виде или base64 в манифестах;
- включено ли шифрование данных Secret при хранении в etcd;
- кто имеет `get/list/watch` к Secret в рабочей среде;
- где хранятся учетные данные для скачивания образов из реестра, какие ServiceAccount подключают `imagePullSecrets` и ограничены ли учетные данные нужной областью и правом только на скачивание;
- какой TTL у токенов и секретов и как проходит их отзыв.

**Сигналы риска:**
- секреты в открытом виде или base64 хранятся в репозитории, файлах значений, итоговых манифестах или артефактах CI;
- Kubernetes Secret используется для особо ценных секретов среды выполнения без подтвержденного шифрования etcd при хранении, строгого RBAC, аудита и владельца;
- External Secrets Operator или другой процесс синхронизации создает Kubernetes Secret без реальной необходимости совместимости;
- Secret с долгоживущими токенами ServiceAccount используются как основной механизм;
- широкое право `list/watch` на Secret для пользователей или учетных записей CI;
- учетные данные реестра с широкими правами или правом загрузки образов в реестр подключены как `imagePullSecrets`, особенно к общим ServiceAccount или ServiceAccount по умолчанию;
- нет подтверждаемого процесса ротации и аварийного отзыва.

**Рекомендация для рабочих сред:**
- для особо ценных секретов среды выполнения предпочитайте доставку только файлами из внешнего хранилища секретов (например, Vault Agent Injector или Secrets Store CSI), чтобы не синхронизировать значения в объекты Kubernetes Secret;
- используйте встроенный Kubernetes Secret для секретов низкой или средней ценности только при включенном шифровании etcd при хранении, строгом RBAC, аудите и безопасной модели доставки;
- если приложение или платформа требуют объект Kubernetes Secret через External Secrets Operator или похожий механизм синхронизации, считайте это повышенным риском раскрытия и применяйте те же проверки, что для встроенного Secret;
- включите шифрование etcd при хранении и проверяйте его состояние после изменений плоскости управления;
- ограничьте ACL для Secret минимально необходимым набором учетных записей рабочих нагрузок;
- применяйте краткоживущие токены и регулярную ротацию секретов;
- ограничивайте учетные данные для скачивания образов минимальным набором репозиториев и правом только на скачивание; где возможно, предпочитайте поддерживаемые платформой провайдеры учетных данных вместо долгоживущих `imagePullSecrets`;
- если по эксплуатационным причинам используется модель отправки секретов с шифрованием в исходниках (например, `sops`/`helm-secrets`), требуйте контролируемые ключи, ревью и запрет расшифровки вне доверенного контура CI/CD;
- периодически проверяйте, что журналирование не раскрывает чувствительные значения.

### 3.7 Проверка атакующих сценариев

**Что проверять:**
- проверены ли ключевые пути атаки из рабочей нагрузки с низким уровнем доверия: обнаружение сервисов, сетевая доступность внутри кластера, права ServiceAccount, доступность `NodePort`, `exec` и эфемерные контейнеры;
- есть ли подтверждения до и после устранения, а не только список YAML-настроек;
- используются ли тестовые сценарии обнаружения и политик для проверки аудита, телеметрии среды выполнения и мер контроля допуска.

**Рекомендация для рабочих сред:**
- проводите проверки имитацией действий атакующего в окружениях, близких к рабочим, после крупных изменений RBAC, CNI, политик допуска, средств защиты среды выполнения и цепочки развертывания;
- разрушительные проверки, проверки отказа в обслуживании и выхода из контейнера выполняйте только в изолированной среде или namespace с заранее утвержденной областью;
- используйте отдельный плейбук для сопоставления сценариев и мер защиты: [kubernetes/adversarial-validation/playbook.ru.md](/Product-security-playbook/ru/platform-security/kubernetes/adversarial-validation/playbook/).

### 3.8 Компоненты узла без root-привилегий (rootless)

`KubeletInUserNamespace` позволяет запускать kubelet и среду выполнения в пользовательском пространстве имен Linux, ограничивая их привилегии относительно хоста. В Kubernetes `v1.37` механизм перешел в стадию бета-тестирования, а флаг включения функции (feature gate) включен по умолчанию. Сам флаг не переводит существующие узлы в режим rootless: способ запуска компонентов настраивается отдельно.

**Что проверять:**
- поддерживает ли поставщик дистрибутива или управляемого сервиса такой режим для конкретных версий Kubernetes, ядра и среды выполнения; документированы ли использование cgroup v2, делегирование дерева cgroup и сопоставления UID/GID с идентификаторами на хосте;
- подтверждают ли режим поле `runningInUserNamespace` в выводе `kubectl get nodes -o yaml`, настройки запуска kubelet и среды выполнения, а также их сопоставления UID/GID с идентификаторами на хосте; одного включенного флага недостаточно;
- работают ли CNI, CSI и системные DaemonSet в выбранной конфигурации; компоненты, которым нужны root-привилегии хоста, должны размещаться на совместимых узлах с помощью управляемых меток, ограничений узлов (taints) и правил размещения.

**Рекомендация для рабочих сред:**
- рассматривайте rootless как дополнительную меру для поддерживаемых конфигураций, а не как обязательное условие допуска любого кластера; начните с отдельной группы узлов и назначьте ответственного, определите критерии успешного внедрения и план отката;
- перед развертыванием на остальных узлах проверьте связь между узлами, DNS, работу сервисов (Service), применение политик NetworkPolicy, подключение и повторное подключение томов рабочих нагрузок, ограничения ресурсов, сбор журналов и работу средств защиты; повторите проверки после перезагрузки и обновления узла, отработайте откат;
- проверьте, какие ограничения затрагивают AppArmor/SELinux и сбор диагностических данных ядра, а также как применяются необходимые параметры sysctl на хосте: kubelet в этом режиме может игнорировать ошибки настройки отдельных sysctl и доступа к `/dev/kmsg`. Если запуск требует отключения действующих мер защиты, сначала проведите отдельную оценку рисков и оформите исключение;
- сохраняйте RBAC, контроль допуска и требования [Pod Security](/Product-security-playbook/ru/platform-security/kubernetes/pod-security/playbook/): rootless не устраняет риски, связанные с совместным использованием ядра и доступом через Kubernetes API.

## 4. Минимальные обязательные проверки политик для рабочих сред

Минимальный набор обязательных проверок:
- запрет прямого развертывания пользователями в защищенных namespace;
- запрет ссылок на образы только по тегу в рабочей среде и требование закрепленного дайджеста (`@sha256:...`); формат `tag@sha256` допустим для читаемости, но развертывание должно использовать именно дайджест;
- блокировка опасных прав RBAC вне явного списка разрешенных;
- обязательная NetworkPolicy с запретом по умолчанию для входящих и исходящих соединений в защищенных namespace либо документированная эквивалентная политика CNI с проверенным принудительным применением;
- блокировка новых объектов Service с `spec.externalIPs`; существующие использования допускаются только как миграционное исключение с `owner`, `expiry`, подтвержденным владением внешним IP и планом перехода на `LoadBalancer`, Gateway API/Ingress или контролируемый `NodePort`;
- инвентаризация контроллеров Ingress и реализаций Gateway API; дальнейшее использование каждого экземпляра контроллера сообщества `ingress-nginx` требует утвержденного исключения с владельцем, сроком действия и сроком миграции; новые развертывания на нем блокируются. Для Gateway API обязательны проверки `allowedRoutes`, межпространственных ссылок через `ReferenceGrant`, владельцев TLS-секретов и прикрепления маршрутов к общему Gateway;
- обязательное журналирование аудита Kubernetes с охватом изменений RBAC, контроля допуска и webhook, меток безопасности namespace, чтения Secret, `exec`, attach/port-forward и обновления эфемерных контейнеров;
- ограничение и периодическое повторное подтверждение доступа `get/list/watch` к Secret в рабочей среде;
- `automountServiceAccountToken: false` по умолчанию, если у рабочей нагрузки нет документированной необходимости обращаться к Kubernetes API;
- блокировка использования ServiceAccount `default` соответствующего namespace для рабочих нагрузок приложений;
- для защищенных namespace по умолчанию принудительно применяйте Pod Security Standards `restricted`:
  - `pod-security.kubernetes.io/enforce: restricted`
  - `pod-security.kubernetes.io/enforce-version: <pinned Kubernetes minor version>`
  - `pod-security.kubernetes.io/audit: restricted`
  - `pod-security.kubernetes.io/audit-version: <same pinned version>`
  - `pod-security.kubernetes.io/warn: restricted`
  - `pod-security.kubernetes.io/warn-version: <same pinned version>`;
- требуйте подтверждения фактически применяемого профиля seccomp, а не только меток namespace: контроль допуска с принудительным применением `restricted` должен отклонять рабочие нагрузки без явного `RuntimeDefault` или утвержденного `Localhost`; namespace с `baseline`, собственной политикой или временными исключениями должны либо требовать явные поля seccomp, либо подтверждать настройку kubelet `--seccomp-default` / `seccompDefault`, чтобы неуказанные профили становились `RuntimeDefault`;
- не считайте этот список полным набором базовых требований к `securityContext` рабочей нагрузки; детальные требования к capabilities, AppArmor/SELinux, sysctl, группам, томам и user namespaces ведите по [плейбуку Kubernetes Pod Security](/Product-security-playbook/ru/platform-security/kubernetes/pod-security/playbook/);
- используйте `warn`/`audit=restricted` без `enforce=restricted` только во время документированного внедрения или периода миграции с владельцем, сроком действия исключения и датой включения блокировки нарушений;
- отслеживайте дрейф меток Pod Security и блокируйте развертывание, если метки рабочей среды ослаблены, удалены или указывают на неутвержденную версию;
- проверяйте тестами политики допуска, что рабочие нагрузки без дайджеста образа отклоняются, включая `:latest`, теги, похожие на версии, и имена образов без явного тега;
- проверка шифрования Secret при хранении в etcd там, где команда владеет плоскостью управления или может ее настраивать;
- исключения только через оформленный объект с `owner`, `justification`, `expiry`.

## 5. Выходные артефакты ревью

Ревью считается завершенным, когда есть:
- список всех субъектов развертывания и их фактических прав;
- схема цепочки развертывания с границами доверия и контрольными точками;
- инвентарь внешних/внутренних сервисных взаимодействий;
- карта покрытия наблюдаемости для реагирования на инциденты (что журналируется и где хранится);
- матрица ответственности за контроль допуска, RBAC и ServiceAccount;
- карта движения секретов с TTL, ротацией, отзывом и владельцами.

## 6. Антипаттерны

- Одна общая учетная запись `cluster-admin` для команды.
- Релизное развертывание через локальный kubeconfig разработчика.
- Правила допуска без контроля прав чтения чувствительных ресурсов через RBAC.
- Минимальные привилегии RBAC без защиты конфигураций допуска и webhook.
- `Service.spec.externalIPs` как штатный способ публикации сервиса наружу.
- Новые развертывания в рабочей среде на снятом с поддержки контроллере сообщества `ingress-nginx`.
- Общий ServiceAccount на все приложения namespace.
- Секреты в Git (включая base64 в YAML) как штатный процесс.
- Отсутствие проверяемой хронологии инцидента по данным аудита и журналирования.
