## 1. Область и цель

Этот плейбук описывает, как превращать пути атаки на Kubernetes в безопасные проверки для рабочих сред. Основа метода состоит в следующем цикле:
- подтвердить доступ и границу доверия;
- перечислить доступную поверхность атаки;
- доказать один контролируемый путь злоупотребления;
- объяснить первопричину;
- применить меру защиты и повторить тот же тест.

**Цель:**
- проверить, что Kubernetes-меры контроля закрывают реальные пути атаки, а не только выглядят корректно в YAML;
- получить подтверждения для проверки безопасности, устранения проблем и повторной проверки;
- связать лабораторные сценарии атак с защитными мерами рабочих сред: RBAC, контролем допуска, NetworkPolicy, усилением защиты среды выполнения, цепочкой поставки и наблюдаемостью.

## 2. Метод ревью

### 2.1 Минимальный цикл проверки

Каждый сценарий должен проходить один и тот же цикл:
- **Проверить:** подтвердить, что целевая рабочая нагрузка, сервис, учетная запись или политика действительно существуют.
- **Перечислить:** собрать контекст с минимальным воздействием: pod, сервисы, маршруты, точки монтирования, переменные окружения, ServiceAccount, RBAC, метаданные образов.
- **Доказать:** выполнить минимальное действие, которое доказывает риск, без расширения воздействия.
- **Объяснить:** зафиксировать первопричину в терминах нарушенной границы доверия.
- **Исправить и перепроверить:** применить меру защиты и повторить тот же тестовый сценарий, чтобы доказать закрытие пути.

Успешный результат проверки должен содержать конкретное подтверждение: доступный `NodePort`, избыточное право ServiceAccount, внутренний сервис, доступный через SSRF, примонтированный сокет среды выполнения, чтение Secret через API, оповещение средства обнаружения угроз во время выполнения или отказ политики допуска.

### 2.2 Безопасные ограничения

Для рабочих сред и общих сред подготовки к выпуску:
- выполняйте разрушительные проверки, проверки отказа в обслуживании и выхода из среды выполнения только в изолированном namespace или копии окружения;
- заранее фиксируйте область: namespace, рабочие нагрузки, учетные записи, диапазоны IP-адресов и временное окно;
- не читайте реальные секретные значения без отдельного согласования; достаточно доказать наличие права `get/list/watch` или факт выдачи токена;
- не запускайте массовое сканирование по CIDR pod без ограничений частоты и параллелизма;
- для доказательства исправления используйте тот же минимальный тестовый сценарий, а не более сильную технику.

Команды подтверждения классифицируются так:
- `безопасно в рабочей среде`: проверки метаданных или политик только на чтение, которые не раскрывают значения секретов;
- `только в тестовой среде`: команды, которые исследуют артефакты или выполняют активные проверки и должны использовать копию окружения, контрольный экземпляр либо изолированный namespace;
- `требует согласования`: команды, которые могут раскрыть чувствительные данные, сканировать инфраструктуру или затронуть реальные рабочие нагрузки.

## 3. Матрица сценариев и мер контроля

### 3.1 Раскрытый исходный код и секреты

**Что проверять:**
- веб-приложение не отдает `.git`, `.svn`, резервные копии, метаданные сборки и локальные файлы переменных окружения;
- слои образа контейнера не содержат удаленные секреты, `.env`, облачные учетные данные или внутренние конфигурации;
- сканирование Git и реестра срабатывает до слияния и выпуска;
- для найденных ранее секретов выполняется ротация, а не только удаление из текущей ветки.

**Рекомендация для рабочих сред:**
- блокируйте служебные пути системы контроля версий и сборки на уровне веб-сервера и при упаковке артефактов;
- запрещайте секреты в открытом виде или base64 в Git и слоях образа;
- включите поиск секретов перед слиянием и выпуском;
- любой секрет, попавший в Git или слой образа, считается скомпрометированным и требует ротации.

**Подтверждение:**
Классификация: `безопасно в рабочей среде` для проверки заголовков и статуса сканирования; `только в тестовой среде` для экспорта образа или исследования слоев; `требует согласования` перед экспортом релизных образов.

```bash
curl -I https://<app>/.git/config
docker history --no-trunc <image>
# Только в тестовой среде и с согласованием: команда может экспортировать чувствительные слои для локального сканирования.
docker save <image> -o image.tar
trufflehog git file://<repo>
```

### 3.2 Сокет среды выполнения и доступ к хосту

**Что проверять:**
- рабочие нагрузки не монтируют `docker.sock`, `containerd.sock`, сокеты CRI, `/proc` и `/sys` хоста, а также широкие `hostPath`;
- рабочие нагрузки сборки и CI не получают доступ к управлению средой выполнения хоста ради удобства;
- `privileged: true`, `hostPID`, `hostNetwork`, `hostIPC` и опасные capabilities имеют владельца, обоснование и срок действия исключения.

**Рекомендация для рабочих сред:**
- запрещайте монтирование сокетов среды выполнения через политику допуска;
- используйте сборщики без root-привилегий, изолированные сборщики или выделенные узлы сборки вместо общего доступа к сокету хоста;
- для исключений требуйте отдельный namespace, строгий RBAC, NetworkPolicy, обнаружение угроз во время выполнения и срок пересмотра не более `30d`.

**Подтверждение:**
```bash
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" "}{.spec.volumes}{"\n"}{end}' | grep -E 'docker.sock|containerd.sock|hostPath'
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" privileged="}{.spec.containers[*].securityContext.privileged}{" hostPID="}{.spec.hostPID}{" hostNetwork="}{.spec.hostNetwork}{"\n"}{end}'
```

### 3.3 SSRF и обнаружение внутренних сервисов

**Что проверять:**
- серверные компоненты загрузки по URL не могут обращаться к произвольным внутренним URL;
- чувствительные внутренние сервисы требуют аутентификации и не доверяют запросам только на основании их происхождения из кластера;
- эндпоинты облачных метаданных защищены средствами соответствующего провайдера;
- исходящие соединения из namespace интерфейсных сервисов и рабочих нагрузок ограничены явным списком разрешенных.

**Рекомендация для рабочих сред:**
- компоненты загрузки по URL используют список разрешенных схем, доменов и портов;
- запретите доступ к диапазонам IP-адресов метаданных и чувствительным внутренним сервисам кластера для рабочих нагрузок, которым он не нужен;
- никогда не запрашивайте пути с учетными данными в облачных метаданных во время проверки; доказывайте защиту через подтверждения блокировки, контрольные ресурсы без чувствительных данных или средства защиты метаданных соответствующего провайдера;
- отслеживайте неожиданные HTTP-запросы из pod интерфейсных сервисов к DNS-именам внутренних сервисов и эндпоинтам метаданных.

**Подтверждение:**
Классификация: `безопасно в рабочей среде` для журналов блокировки политиками и контрольных ресурсов без чувствительных данных; `только в тестовой среде` для активных проверок доступности сервисов; `требует согласования` перед проверкой эндпоинтов метаданных рабочей среды.

```bash
kubectl run -n <ns> --rm -it netcheck --image=curlimages/curl -- sh
curl -m 2 http://<sensitive-service>.<namespace>.svc.cluster.local
# Безопасная проверка метаданных: предпочтительны журналы блокировки или контрольный ресурс без чувствительных данных.
curl -m 2 -I http://169.254.169.254/
# AWS IMDSv2 должен отклонять обращения к метаданным без токена; не запрашивайте /latest/meta-data/iam/security-credentials/.
curl -m 2 -s -o /dev/null -w "%{http_code}\n" http://169.254.169.254/latest/meta-data/
# GCP/Azure: проверяйте запрет исходящих соединений или средства защиты метаданных провайдера без запроса путей с токенами и учетными данными.
kubectl logs -n <network-policy-or-runtime-security-ns> <policy-or-sensor-pod>
```

### 3.4 NodePort и внешняя доступность сервисов

**Что проверять:**
- все `NodePort`, `LoadBalancer`, `Ingress` и `Gateway` имеют владельца, назначение и ожидаемую аудиторию;
- группы безопасности и межсетевые экраны узлов не открывают диапазон NodePort наружу без необходимости;
- доступность из интернета проверяется фактическим подключением, а не только чтением YAML объекта Service.

**Рекомендация для рабочих сред:**
- для внутренних сервисов используйте `ClusterIP` или внутренний балансировщик нагрузки;
- настройте оповещение о новом `NodePort` в защищенном namespace;
- обновляйте реестр публичных точек входа минимум каждые `30d`.

**Подтверждение:**
Классификация: `безопасно в рабочей среде` для инвентаризации сервисов; `требует согласования` для внешнего сканирования доступности по IP-адресам узлов.

```bash
kubectl get svc -A -o wide
kubectl get svc -A --field-selector spec.type=NodePort
# Требуются утвержденная область, отдельное временное окно, список целей, ограничения частоты и согласование владельца.
nmap -Pn -p 30000-32767 <node-external-ip>
```

### 3.5 Обход границ namespace и сетевая изоляция

**Что проверять:**
- namespace не воспринимаются как сетевая граница без NetworkPolicy или эквивалентного принудительного применения правил CNI;
- в чувствительных namespace входящие и исходящие соединения запрещены по умолчанию;
- разрешенные потоки внутри кластера документированы и тестируются из pod с низким уровнем доверия.

**Рекомендация для рабочих сред:**
- включите запрет по умолчанию для рабочих сред и namespace с особо ценными данными или нагрузками;
- явно разрешайте только необходимые межсервисные пути;
- повторно проверяйте NetworkPolicy после изменений CNI, меток namespace и селекторов сервисов.

**Подтверждение:**
```bash
kubectl get networkpolicy -A
kubectl run -n <low-trust-ns> --rm -it netcheck --image=curlimages/curl -- sh
curl -m 2 http://<target-service>.<target-ns>.svc.cluster.local
```

### 3.6 Злоупотребление ServiceAccount и RBAC

**Что проверять:**
- учетная запись рабочей нагрузки не может читать Secret, менять рабочие нагрузки, создавать pod, выполнять `exec`, добавлять эфемерные контейнеры или изменять RBAC без необходимости;
- `automountServiceAccountToken` выключен для рабочих нагрузок без доступа к Kubernetes API;
- ServiceAccount по умолчанию не используется рабочими нагрузками приложений.

**Рекомендация для рабочих сред:**
- один ServiceAccount на рабочую нагрузку, права выдаются по функции, а не ради удобства работы с namespace;
- `get/list/watch secrets`, `pods/exec`, `pods/ephemeralcontainers`, `escalate`, `bind`, `impersonate`, `serviceaccounts/token` требуют отдельного согласования;
- ежеквартальный пересмотр прав ServiceAccount в рабочей среде.

**Подтверждение:**
```bash
kubectl auth can-i list secrets --as=system:serviceaccount:<ns>:<sa> -n <ns>
kubectl auth can-i create pods/exec --as=system:serviceaccount:<ns>:<sa> -n <ns>
kubectl auth can-i update pods/ephemeralcontainers --as=system:serviceaccount:<ns>:<sa> -n <ns>
kubectl get rolebindings,clusterrolebindings -A
```

### 3.7 Исчерпание ресурсов

**Что проверять:**
- каждый контейнер в рабочей среде имеет `resources.requests` для CPU и памяти, чтобы планирование отражало реальные потребности рабочей нагрузки;
- каждый контейнер в рабочей среде имеет лимит памяти, чтобы ограничить отказ в обслуживании на уровне узла и влияние соседних нагрузок с чрезмерным потреблением ресурсов;
- лимиты CPU определяются рисками, а не универсальным требованием; требуйте их, когда риск отказа в обслуживании или влияния соседних нагрузок выше риска ограничения CPU и задержек либо когда этого требует политика платформы;
- рабочие нагрузки, которые записывают временные файлы, кеш, журналы, загруженные файлы, сгенерированные артефакты или результаты пакетной обработки, имеют requests и limits для `ephemeral-storage`;
- namespace имеют `ResourceQuota` и, где нужно, `LimitRange`;
- оповещения охватывают всплески потребления CPU и памяти, OOMKilled, ограничение CPU и циклические перезапуски.

**Рекомендация для рабочих сред:**
- используйте плейбук Pod Security как основной источник политики ограничений ресурсов и исключений;
- запрещайте pod класса BestEffort в защищенных namespace;
- задавайте квоты на уровне namespace для общих кластеров;
- проверки отказа в обслуживании выполняйте только в изолированной среде нагрузочного тестирования или подготовки к выпуску.

**Подтверждение:**
```bash
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" "}{.spec.containers[*].resources}{"\n"}{end}'
kubectl get resourcequota,limitrange -A
kubectl top pods -A
```

### 3.8 Реестр образов и цепочка поставки

**Что проверять:**
- закрытый реестр требует аутентификации, авторизации и сетевых ограничений;
- API реестра не раскрывает каталог и манифесты широкому кругу субъектов;
- релизное развертывание идет по дайджесту и проходит проверку политики provenance и подписей;
- история образа не содержит подозрительной последовательности загрузки и выполнения;
- задания пакетной обработки и вспомогательные задания не запускают образы из неутвержденных реестров без владельца и provenance.

**Рекомендация для рабочих сред:**
- эндпоинты реестра не должны быть доступны из сетей общего назначения;
- журналирование аудита событий реестра обязательно для релизных артефактов;
- проверка допуска к развертыванию должна проверять дайджест, учетную запись доверенного сборщика, provenance, подпись и результат применения политики;
- блокируйте образы, которые скачивают и выполняют удаленное содержимое во время сборки или запуска без отдельного ревью.

**Подтверждение:**
```bash
curl -I https://<registry>/v2/
curl https://<registry>/v2/_catalog
cosign verify <image>@sha256:<digest>
docker history --no-trunc <image>
kubectl get jobs -A -o wide
```

### 3.9 Средства отладки: exec и эфемерные контейнеры

**Что проверять:**
- кто может выполнять `pods/exec`, `pods/attach`, `pods/portforward`, `pods/ephemeralcontainers`;
- отладочные контейнеры не обходят ожидаемые ограничения Pod Security и RBAC;
- отладка на уровне узла через `kubectl debug node/...` разрешена только ролям аварийного доступа.

**Рекомендация для рабочих сред:**
- `exec` в чувствительных namespace должен быть ограничен и доступен для аудита;
- эфемерные контейнеры разрешайте только ролям поддержки или SRE на короткий срок и с отдельным журналированием;
- применяйте политику допуска для запрета средств отладки в namespace с особо ценными данными или нагрузками, где это допустимо по условиям эксплуатации.

**Подтверждение:**
```bash
kubectl auth can-i create pods/exec --as=<subject> -n <ns>
kubectl auth can-i update pods/ephemeralcontainers --as=<subject> -n <ns>
# События Kubernetes не являются надежным подтверждением exec. Проверяйте журналы аудита или SIEM:
# verb=create resource=pods subresource=exec|attach|portforward
# verb=update resource=pods subresource=ephemeralcontainers
kubectl get events -A --field-selector involvedObject.kind=Pod | grep -Ei 'ephemeral|debug'
```

### 3.10 Обнаружение и проверка политик

**Что проверять:**
- журналы аудита покрывают изменения RBAC, чтение Secret, `exec`, эфемерные контейнеры, отказы контроля допуска и дрейф меток namespace;
- телеметрия среды выполнения видит чтение чувствительных путей, запуск командной оболочки, подозрительные сетевые инструменты, `nsenter` и доступ к путям хоста;
- политика допуска блокирует известные небезопасные конфигурации до развертывания.

**Рекомендация для рабочих сред:**
- используйте лабораторные сценарии атак как тестовые случаи обнаружения, адаптируя их для безопасной среды подготовки к выпуску;
- для Falco/Tetragon или эквивалентных датчиков среды выполнения должно быть настроено приемлемое соотношение полезных сигналов и шума;
- политики Kyverno/Gatekeeper/ValidatingAdmissionPolicy должны иметь владельца, тестовые сценарии и жизненный цикл исключений.

**Подтверждение:**
```bash
kubectl get validatingadmissionpolicies,validatingadmissionpolicybindings
kubectl get clusterpolicies -A
kubectl logs -n <runtime-security-ns> -l app.kubernetes.io/name=<sensor>
kubectl logs -n kube-system -l app.kubernetes.io/name=tetragon -c export-stdout
kubectl --namespace <sensitive-ns> exec -it <pod> -- sh
```

### 3.11 Определение контекста и окружения среды выполнения

**Что проверять:**
- рабочая нагрузка не раскрывает особо ценные секреты через переменные окружения, отладочные эндпоинты, доступ к командной оболочке или подробный вывод ошибок;
- в контейнере нет неожиданных точек монтирования, доступных для записи чувствительных путей, широкой видимости `/proc` и токена сервисной учетной записи там, где Kubernetes API не нужен;
- вспомогательные образы общего назначения и наборы инструментов безопасности не появляются в защищенном namespace без зарегистрированного изменения и владельца.

**Рекомендация для рабочих сред:**
- не помещайте долгоживущие секреты в переменные окружения рабочих нагрузок приложений; используйте менеджер секретов, идентификацию рабочей нагрузки или краткоживущие учетные данные в примонтированных файлах;
- выключайте `automountServiceAccountToken` и отладочную командную оболочку там, где они не нужны для работы приложения;
- настройте оповещения о запуске образов с наборами инструментов, неожиданных процессов командной оболочки, менеджеров пакетов и сетевых сканеров в защищенных namespace.

**Подтверждение:**
Классификация: `безопасно в рабочей среде` для инвентаризации метаданных через Kubernetes API; `только в тестовой среде` для исследования через командную оболочку; `требует согласования` перед выполнением команд в pod рабочей среды.

```bash
# Не выводите значения переменных окружения. Проверяйте только имена и классы через согласованный механизм отладки.
kubectl exec -n <ns> <pod> -- sh -c 'env | cut -d= -f1 | grep -Ei "TOKEN|SECRET|KEY|PASSWORD|CREDENTIAL|AWS_|GOOGLE_|AZURE_"'
# Только в тестовой среде и с согласованием: исследование через командную оболочку затрагивает рабочую нагрузку.
kubectl exec -n <ns> <pod> -- mount
kubectl exec -n <ns> <pod> -- cat /proc/self/cgroup
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" sa="}{.spec.serviceAccountName}{" automount="}{.spec.automountServiceAccountToken}{" image="}{.spec.containers[*].image}{"\n"}{end}'
```

### 3.12 Проверка по эталонным требованиям и ревью профиля защищенности

**Что проверять:**
- Docker или другая среда выполнения контейнеров, kubelet, API server, RBAC, аудит и усиление защиты узла проверяются средствами оценки соответствия эталонным требованиям, а не только ручным чтением YAML;
- профиль kube-bench/CIS выбран под фактическую версию Kubernetes и вариант поставки провайдера; ограничения управляемого сервиса отмечены как исключение или неприменимые требования;
- kubeaudit/Popeye или эквивалентные сканеры находят привилегированные pod, отсутствующие лимиты, слабый security context, устаревшие ссылки и накопленные недочеты конфигурации;
- замечания проверки по эталонным требованиям переводятся в очередь устранения с владельцем, критичностью и подтверждением повторной проверки.

**Рекомендация для рабочих сред:**
- запускайте сканирование профиля защищенности регулярно и после обновлений платформы;
- отделяйте ошибки конфигурации, которые можно эксплуатировать, от недочетов поддержания конфигурации, чтобы не перегружать очередь устранения;
- не считайте необработанный вывод сканера достаточной гарантией безопасности: подтверждайте критичные меры контроля целевыми тестами из этого плейбука.

**Подтверждение:**
```bash
kubectl logs -n <audit-ns> job/<kube-bench-job>
kubeaudit all
popeye
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" privileged="}{.spec.containers[*].securityContext.privileged}{" limits="}{.spec.containers[*].resources.limits}{"\n"}{end}'
```

### 3.13 Устаревшие сервисы плоскости управления

**Что проверять:**
- в кластере нет Helm v2 Tiller, старых панелей управления и административных сервисов, заброшенных операторов или компонентов управления пакетами с широкими правами RBAC;
- сервисы плоскости управления недоступны из namespace приложений и pod с низким уровнем доверия;
- сервисные учетные записи инструментов развертывания не имеют `cluster-admin` по умолчанию и не могут читать Secret без необходимости.

**Рекомендация для рабочих сред:**
- Helm v2/Tiller должен быть выведен из эксплуатации; для Helm v3 храните состояние релиза и учетные данные развертывания с минимально необходимыми правами;
- любые административные сервисы внутри кластера требуют явно назначенного владельца, сетевой изоляции, аутентификации, журналирования аудита и срока действия исключения;
- проверяйте устаревшие компоненты после миграции, устранения последствий инцидента и обновления кластера.

**Подтверждение:**
```bash
kubectl get svc,deploy,sa,rolebinding,clusterrolebinding -A | grep -Ei 'tiller|dashboard|admin|operator'
kubectl auth can-i '*' '*' --as=system:serviceaccount:<ns>:<deploy-sa>
kubectl get clusterrolebinding -A -o wide
```

### 3.14 Дрейф `securityContext` рабочих нагрузок

**Что проверять:**
- рабочие нагрузки приложений на узлах Linux с AppArmor не запускаются с `appArmorProfile.type: Unconfined` и имеют подтверждение использования `RuntimeDefault` или утвержденного профиля `Localhost`;
- рабочие нагрузки не задают небезопасные `spec.securityContext.sysctls` в обычных namespace приложений;
- `fsGroup`, `supplementalGroups` и `supplementalGroupsPolicy` не выдают широкое членство в группах без модели ответственности за общее хранилище;
- чувствительные рабочие нагрузки на Kubernetes `v1.33+` используют `supplementalGroupsPolicy: Strict`, если им нужна строгая модель групп.

**Рекомендация для рабочих сред:**
- проверяйте эти поля тестами политики допуска, а не только ручным ревью YAML;
- запрещайте AppArmor `Unconfined` и небезопасные sysctl по умолчанию; исключения оформляйте с владельцем, сроком действия, выделенным пулом узлов там, где это нужно, и планом отката;
- для доступа к томам на основе групп фиксируйте правила: какой GID нужен, какие пути доступны на запись, какие рабочие нагрузки разделяют хранилище и почему это допустимо.

**Подтверждение:**
Классификация: `безопасно в рабочей среде` для инвентаризации и пробной проверки допуска без применения изменений; `только в тестовой среде` для проверок среды выполнения через `exec` в чувствительных рабочих нагрузках.

```bash
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" appArmorPod="}{.spec.securityContext.appArmorProfile.type}{" sysctls="}{.spec.securityContext.sysctls}{"\n"}{end}'
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" appArmorContainers="}{.spec.containers[*].securityContext.appArmorProfile.type}{"\n"}{end}'
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" appArmorInit="}{.spec.initContainers[*].securityContext.appArmorProfile.type}{" appArmorEphemeral="}{.spec.ephemeralContainers[*].securityContext.appArmorProfile.type}{"\n"}{end}'
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{" fsGroup="}{.spec.securityContext.fsGroup}{" supplementalGroups="}{.spec.securityContext.supplementalGroups}{" supplementalGroupsPolicy="}{.spec.securityContext.supplementalGroupsPolicy}{"\n"}{end}'
kubectl exec -n <ns> <pod> -- id
kubectl exec -n <ns> <pod> -- stat -c '%u:%g %a %n' <mounted-path>
```

## 4. Выходные артефакты ревью

Проверка имитацией действий атакующего считается завершенной, когда есть:
- матрица сценариев и мер контроля для проверенных путей атаки;
- подтверждение каждой проверяемой цели до и после устранения;
- список остаточных рисков и исключений с владельцами и сроками действия;
- сопоставление замечаний с профильными плейбуками: ревью кластера, Pod Security, выход из контейнера, seccomp, SLSA и Vault;
- журнал повторных проверок, показывающий, что исправление закрыло исходный путь злоупотребления.
