`prompt-guard` — самостоятельная Python-библиотека и CLI для проверки недоверенного текста UTF-8 и сообщений JSON по правилам поиска точных строк и сопоставления с регулярными выражениями с учетом источника данных. Версия 0.2.0 требует Python 3.11+ на Linux или macOS; во время работы используются только модули стандартной библиотеки. Проверка через CLI выполняется без обращения к сети.

[Исходники и руководство](https://github.com/defrixx/Product-security-skills/tree/main/tools/prompt-guard) | [Скиллы и инструменты](/Product-security-playbook/ru/ai-automation/security-skills/overview/)

## Режимы и решения о допуске

По умолчанию используется `strict`: совпадение с блокирующим правилом отклоняет входные данные целиком, сохраняя оригинал. Явно выбранный режим `sanitize` выполняет только разрешенные политикой замены в отдельной копии, затем повторно проверяет весь результат. Блокирующее правило без разрешенной замены по-прежнему блокирует запрос; несовместимые пересекающиеся замены также приводят к блокировке. Замены выполняются за один проход. Инструмент не одобряет результат автоматически и не повторяет удаление фрагментов до получения допуска.

| Решение | Код завершения CLI | Действие приложения |
| --- | --- | --- |
| `allow` | 0 | Отправить только возвращенные данные. |
| `block` | 1 | Остановить отправку. |
| `review` | 2 | Остановить автоматическую отправку и разобрать результат проверки по правилам приложения. |
| `error` | 3 | Остановить отправку и устранить ошибку, указанную диагностическим кодом. |

`allow` означает, что настроенные правила допускают этот ввод. Такой результат не гарантирует, что содержимое безопасно по смыслу, и не дает разрешения на предложенное моделью действие. Очистка может изменить смысл задачи; перед включением замен проверьте как допустимые задачи, так и сценарии атак.

## Установка и первая проверка

Установите пакет в окружение приложения:

```sh
python -m pip install /path/to/Product-security-skills/tools/prompt-guard
```

Используйте существующие каталоги и абсолютные пути без символических ссылок. CLI проверяет один файл, а не каталог. Для первой проверки без обращения к сети подойдет встроенный профиль:

```sh
prompt-guard --profile user-input \
  --input /path/to/input/sample.txt --input-root /path/to/input --source user
```

Для очистки выберите защищенную политику с разрешенными заменами и новый файл для результата за пределами каталогов ввода и конфигурации:

```sh
prompt-guard --policy /path/to/config/policy.json --config-root /path/to/config \
  --input /path/to/input/sample.txt --input-root /path/to/input --source user \
  --mode sanitize --output /path/to/results/new-clean.txt --output-root /path/to/results
```

Копия записывается только при `allow`, с правами `0600` и без перезаписи существующего файла. Без `--output` инструмент проверяет результат очистки, но не выдает его содержимое. Ошибка записи возвращает `error` и может оставить частично записанный файл с ограниченными правами доступа; отправлять его модели нельзя.

## Источники, профили и охват обнаружения

Для JSON укажите `--format json` без `--source`. Формат входных данных:

```json
{"messages": [{"source": "user", "text": "Public request"}, {"source": "retrieval", "text": "Public document"}]}
```

Поддерживаются источники `user`, `retrieval`, `file`, `tool` и `assistant`. Приложение назначает источник по доверенному маршруту получения данных; значение источника не должно задаваться недоверенным содержимым. Эти поля отличаются от ролей сообщений в API модели. Неизвестные поля, повторяющиеся ключи, некорректный Unicode и пустой список сообщений отклоняются.

| Встроенный профиль | Охват |
| --- | --- |
| `user-input` | Ввод пользователя; отдельные шаблоны атак требуют повелительной конструкции в начале текста. |
| `retrieval`, `tool-results` | Полученные документы или текст результатов инструментов; правила обнаружения внедренных инструкций без привязки к началу текста. |
| `security` | Шаблоны атак в разных источниках данных и собранном контексте. |
| `restricted-topics` | Строгие лексические ограничения по темам. |
| `security-and-topics` | Правила обнаружения атак и ограничения по темам. |

Профили содержат примеры выражений на английском, испанском, русском и японском языках. Это образцы политик: перед применением проверьте, подходят ли они вашему приложению. Правила с широким охватом могут блокировать даже цитаты с текстом атак. Тематические правила блокируют любое упоминание, совпавшее с шаблоном, в том числе в учебных материалах, рекомендациях по профилактике, новостях и цитатах. Контекстные исключения и очистка для таких совпадений не предусмотрены. Перед выбором профиля измерьте ложные блокировки на реальных допустимых материалах.

Схема v2 добавляет представление `normalized` и правила `assembled`. При подготовке нормализованного текста для проверки удаляются форматирующие символы Unicode, применяется NFKC, а для правил без учета регистра — приведение регистра (casefold). Участки для замены сопоставляются с исходным текстом. Base64 не декодируется, визуально похожие символы разных алфавитов не приводятся к общему алфавиту. Правила собранного контекста проверяют сообщения выбранных источников по порядку с разделителем `assembly_separator`; укажите разделитель, который приложение использует при сборке текста. Такие правила могут блокировать или требовать проверки, но не могут заменять фрагменты, охватывающие несколько сообщений.

## Подключение к приложению и защита политики

1. Проверяйте входные данные и каждый новый набор документов или результатов инструментов, назначая источник доверенным кодом. Проверяйте собранный контекст там, где фрагменты могут сложиться в запрещенное выражение.
2. Собирайте запрос из допущенных данных. Статические инструкции и определения инструментов проверяйте через [prompt-integrity](/Product-security-playbook/ru/ai-automation/prompt-integrity/overview/) непосредственно перед отправкой.
3. До выполнения каждого предложенного вызова инструмента проверяйте аргументы, допустимый набор ресурсов и полномочия.

Функция `inspect` возвращает `payload` только при `allow`; отправляйте именно эти байты с учетом разрешенных изменений. При блокировке, необходимости проверки или ошибке нельзя отправлять непроверенный оригинал. Повторные попытки и резервные маршруты должны проходить те же проверки. Исходные объекты и загруженная политика остаются без изменений.

Защитите конфигурацию политики отдельно. Для загрузки заранее выбранной версии политики `load_policy` принимает `expected_id`, `expected_version` и `expected_sha256`; параметры CLI — `--expected-policy`, `--expected-version` и `--expected-sha256` вместе с `--policy`. Все ожидаемые значения должны поступать из отдельно защищенной конфигурации развертывания. Хеш привязан к точным байтам файла. Несовпадение останавливает загрузку; обновление и откат требуют совместного явного выбора утвержденных идентификатора, версии и хеша.

`prompt_guard.adapters.GuardedDispatch` поддерживает Ollama `/api/chat` и Chat Completions `/v1/chat/completions` с доверенным статическим шаблоном и явно заданным HTTP-адресом сервера с числовым IP-адресом обратной петли. Адаптер проверяет все сообщения с данными вместе и отправляет допущенный снимок запроса. Встроенный компонент отправки ограничивает размеры данных и время ожидания сокета, не использует прокси, перенаправления и повторные попытки. Приложение может подключить `prompt-integrity` через свою функцию `integrity_sender`. Проверка протокола, истории сообщений и разрешений на действия остается обязанностью приложения. Попытка очистить метаданные вызова инструмента в сообщении ассистента останавливает отправку.

## Ограничения выполнения и проверка интеграции

Предельные ограничения пакета: 1 МиБ для ввода и преобразованного результата, 128 сообщений JSON, 64 правила и 1 024 совпадения за проход проверки. Время проверки в рабочем процессе ограничено 2 000 мс, всей операции — 6 000 мс, память рабочего процесса — 256 МиБ. Политика может уменьшать эти пределы. Один интерпретатор допускает не более четырех рабочих процессов; при превышении этого числа проверка возвращает `worker_capacity_exhausted`, и отправка блокируется. Эти ограничения пакета не относятся к лимитам обращения к модели. На macOS периодический контроль памяти не ограничивает объем выделяемой памяти в каждый момент времени.

Диагностика содержит решения, коды, идентификаторы политики и правил, счетчики; исходный текст, совпавшие фрагменты, пути и хеши запросов в нее не включаются. Не помещайте чувствительные данные в идентификаторы. В допущенных данных могут остаться чувствительные значения, не охваченные выбранными правилами.

[Тесты пакета и набор синтетических примеров](https://github.com/defrixx/Product-security-skills/tree/main/tools/prompt-guard/tests) охватывают атаки, допустимые запросы и блокировки, предусмотренные тематическими правилами. Перед развертыванием проверьте отправку итоговых данных, все маршруты обращения к модели, ложные блокировки, исчерпание ресурсов и обработку несовпадения политики в своей интеграции.

[model-security-eval](/Product-security-playbook/ru/ai-automation/model-security-eval/overview/) поддерживает `--guard-profile`, `--guard-mode` и `--compare-guard`, если пакет установлен. Парные испытания отдельно фиксируют решения фильтра, нарушения со стороны модели и действия в тестовой среде, включая блокировки допустимых запросов. Заблокированный ввод получает `not_assessed_for_blocked_input`; это не свидетельство устойчивости модели к атаке. Результаты на синтетических данных не подтверждают, что инструмент обнаружит все атаки в реальных входных данных.
