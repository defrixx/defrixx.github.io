`prompt-guard` - самостоятельная Python-библиотека и CLI для проверки недоверенного входного контекста и ответов модели по отдельным политикам. Текст UTF-8 и сообщения JSON проверяются по точным строкам и регулярным выражениям с учетом источника данных. Версия 0.3.0 требует Python 3.11+ на Linux или macOS; во время работы используются только модули стандартной библиотеки. Проверка через CLI выполняется без обращения к сети.

[Исходники и руководство](https://github.com/defrixx/Product-security-skills/tree/main/tools/prompt-guard) | [Скиллы и инструменты](/Product-security-playbook/ru/ai-automation/security-skills/overview/)

## Режимы и решения о допуске

По умолчанию используется `strict`: совпадение с блокирующим правилом отклоняет входные данные целиком, сохраняя оригинал. Явно выбранный режим `sanitize` выполняет только разрешенные политикой замены в отдельной копии, затем повторно проверяет весь результат. Блокирующее правило без разрешенной замены по-прежнему блокирует проверяемые данные; несовместимые пересекающиеся замены также приводят к блокировке. Замены выполняются за один проход. Инструмент не одобряет результат автоматически и не повторяет удаление фрагментов до получения допуска.

| Решение | Код завершения CLI | Действие приложения |
| --- | --- | --- |
| `allow` | 0 | Отправить модели или выдать пользователю только возвращенные данные. |
| `block` | 1 | Остановить отправку. |
| `review` | 2 | Остановить автоматическую отправку и разобрать результат проверки по правилам приложения. |
| `error` | 3 | Остановить отправку и устранить ошибку, указанную диагностическим кодом. |

`allow` означает, что настроенные правила допускают этот ввод. Такой результат не гарантирует, что содержимое безопасно по смыслу, и не дает разрешения на предложенное моделью действие. Очистка может изменить смысл задачи; перед включением замен проверьте как допустимые задачи, так и сценарии атак.

## Установка и первая проверка

Установите пакет в окружение приложения:

```sh
python -m pip install /path/to/Product-security-skills/tools/prompt-guard
```

Используйте существующие каталоги и абсолютные пути без символических ссылок. CLI проверяет один файл, а не каталог. Для первой проверки без обращения к сети подойдет встроенный профиль:

```sh
prompt-guard --profile user-input \
  --input /path/to/input/sample.txt --input-root /path/to/input --source user
```

Для очистки выберите защищенную политику с разрешенными заменами и новый файл для результата за пределами каталогов ввода и конфигурации:

```sh
prompt-guard --policy /path/to/config/policy.json --config-root /path/to/config \
  --input /path/to/input/sample.txt --input-root /path/to/input --source user \
  --mode sanitize --output /path/to/results/new-clean.txt --output-root /path/to/results
```

Копия записывается только при `allow`, с правами `0600` и без перезаписи существующего файла. Без `--output` инструмент проверяет результат очистки, но не выдает его содержимое. Ошибка записи возвращает `error` и может оставить частично записанный файл с ограниченными правами доступа; отправлять его модели нельзя.

## Источники входных данных, профили и охват обнаружения

Для JSON укажите `--format json` без `--source`. Формат входных данных:

```json
{"messages": [{"source": "user", "text": "Public request"}, {"source": "retrieval", "text": "Public document"}]}
```

Поддерживаются источники `user`, `retrieval`, `file`, `tool` и `assistant`. Приложение назначает источник по доверенному маршруту получения данных; значение источника не должно задаваться недоверенным содержимым. Эти поля отличаются от ролей сообщений в API модели. Неизвестные поля, повторяющиеся ключи, некорректный Unicode и пустой список сообщений отклоняются.

| Встроенный профиль | Охват |
| --- | --- |
| `user-input` | Ввод пользователя; отдельные шаблоны атак требуют повелительной конструкции в начале текста. |
| `retrieval`, `tool-results` | Полученные документы или текст результатов инструментов; правила обнаружения внедренных инструкций без привязки к началу текста. |
| `security` | Шаблоны атак в разных источниках данных и собранном контексте. |
| `restricted-topics` | Строгие лексические ограничения по темам. |
| `security-and-topics` | Правила обнаружения атак и ограничения по темам. |

Профили содержат примеры выражений на английском, испанском, русском и японском языках. Это образцы политик: перед применением проверьте, подходят ли они вашему приложению. Правила с широким охватом могут блокировать даже цитаты с текстом атак. Тематические правила блокируют любое упоминание, совпавшее с шаблоном, в том числе в учебных материалах, рекомендациях по профилактике, новостях и цитатах. Контекстные исключения и очистка для таких совпадений не предусмотрены. Перед выбором профиля измерьте ложные блокировки на реальных допустимых материалах.

Схема v2 добавляет представление `normalized` и правила `assembled`. При подготовке нормализованного текста для проверки удаляются форматирующие символы Unicode, применяется NFKC, а для правил без учета регистра - приведение регистра (casefold). Участки для замены сопоставляются с исходным текстом. Base64 не декодируется, визуально похожие символы разных алфавитов не приводятся к общему алфавиту. Правила собранного контекста проверяют сообщения выбранных источников по порядку с разделителем `assembly_separator`; укажите разделитель, который приложение использует при сборке текста. Такие правила могут блокировать или требовать проверки, но не могут заменять фрагменты, охватывающие несколько сообщений.

## Подключение к приложению и защита политики

1. Проверяйте входные данные и каждый новый набор документов или результатов инструментов, назначая источник доверенным кодом. Проверяйте собранный контекст там, где фрагменты могут сложиться в запрещенное выражение.
2. Собирайте запрос из допущенных данных. Статические инструкции и определения инструментов проверяйте через [prompt-integrity](/Product-security-playbook/ru/ai-automation/prompt-integrity/overview/) непосредственно перед отправкой.
3. Проверяйте ответы модели по отдельной выходной политике до выдачи пользователю или выполнения предложенных вызовов инструментов.
4. До выполнения каждого предложенного вызова инструмента проверяйте аргументы, допустимый набор ресурсов и полномочия.

Функция `inspect` возвращает `payload` только при `allow`; отправляйте именно эти байты с учетом разрешенных изменений. При блокировке, необходимости проверки или ошибке нельзя отправлять непроверенный оригинал. Повторные попытки и резервные маршруты должны проходить те же проверки. Исходные объекты и загруженная политика остаются без изменений.

Защитите конфигурацию политики отдельно. Для загрузки заранее выбранной версии политики `load_policy` принимает `expected_id`, `expected_version` и `expected_sha256`; параметры CLI - `--expected-policy`, `--expected-version` и `--expected-sha256` вместе с `--policy`. Все ожидаемые значения должны поступать из отдельно защищенной конфигурации развертывания. Хеш привязан к точным байтам файла. Несовпадение останавливает загрузку; обновление и откат требуют совместного явного выбора утвержденных идентификатора, версии и хеша.

`prompt_guard.adapters.GuardedDispatch` поддерживает Ollama `/api/chat` и Chat Completions `/v1/chat/completions` с доверенным статическим шаблоном и явно заданным HTTP-адресом сервера с числовым IP-адресом обратной петли. Адаптер проверяет все сообщения с данными вместе и отправляет допущенный снимок запроса. Встроенный компонент отправки ограничивает размеры данных и время ожидания сокета, не использует прокси, перенаправления и повторные попытки. Приложение может подключить `prompt-integrity` через свою функцию `integrity_sender`. Проверка протокола, истории сообщений и разрешений на действия остается обязанностью приложения. Попытка очистить метаданные вызова инструмента в сообщении ассистента останавливает отправку.

## Проверка ответов модели

Выберите отдельную политику проверки ответов модели и храните ее в доверенной конфигурации приложения. Политики для входных данных и ответов настраиваются независимо; содержимое пользовательского запроса не должно определять их выбор. В собственной политике проверки ответов укажите источник `assistant`.

| Профиль проверки ответов | Что проверяет |
| --- | --- |
| `output-topics` | Упоминания тем, ограниченных политикой; совпадение блокирует выдачу в обоих режимах. |
| `output-secrets` | Блоки закрытых ключей, включая незавершенные, токены определенных форматов и записи с присваиванием учетных данных. |
| `output-security-and-topics` | Правила обнаружения секретов и ограничения по темам. |
| `output-personal-data` | Адреса электронной почты и международные телефонные номера; профиль выбирается явно. |

Профили проверяют текст по лексическим шаблонам и не определяют его смысл. Например, `output-personal-data` в режиме `strict` блокирует и общедоступные контактные данные, совпавшие с шаблоном. Конкретные защищаемые значения передаются через `protected=(...)`: совпадение всегда блокируется, даже в `sanitize`. Если нужно обнаруживать варианты значений в разных кодировках, перечислите их явно согласно требованиям приложения.

```python
from prompt_guard import OutputGuard, load_profile

boundary = OutputGuard.create(
    load_profile("output-security-and-topics"),
    mode="sanitize",
    protected=("SYNTHETIC_APPLICATION_CANARY",),
)
result = boundary.check_text("Public greeting API")
if result.decision == "allow":
    deliver(result.payload.decode("utf-8"))
else:
    deliver("Ответ заблокирован правилами приложения.")
```

`deliver` здесь - функция приложения, выдающая ответ пользователю. Содержимое доступно только при `allow`; оно не включается в диагностику и строковое представление результата. При отклонении используйте заранее подготовленный ответ приложения, без фрагментов заблокированного результата.

Для проверки сохраненного ответа через CLI:

```sh
prompt-guard --direction output --profile output-security-and-topics \
  --input /path/to/input/answer.txt --input-root /path/to/input
```

В этом режиме тексту назначается источник `assistant`, а `--format json` принимает сообщение с полями `content` и необязательным `tool_calls`, а не входной список `messages`. Параметр `--output-contract /path/to/config/contract.json` используется с `--format json` и `--config-root`; файл должен содержать ровно `{"schema": ..., "tools": ...}`. Отдельную копию, прошедшую проверку, можно записать через `--output` и `--output-root` как в `strict`, так и в `sanitize`.

## Структурированные ответы и вызовы инструментов

`OutputGuard.create(..., schema=..., tools={name: argument_schema})` задает фиксированные схемы содержимого и аргументов. Метод `check_message` принимает `{"content": text_or_json, "tool_calls": [{"id": ..., "name": ..., "arguments": ...}]}`. Проверяются строковые значения содержимого и аргументов, имена полей и метаданные маршрутизации; правила `assembled` также проверяют объединенные значения. Очистка может изменять значения, но не имена инструментов, ключи или идентификаторы. Исходный объект сохраняется, а после преобразования содержимое и аргументы должны повторно пройти проверку по своим схемам.

Инструменты, не указанные в конфигурации, запрещены. Весь набор вызовов проверяется до запуска первого обработчика. `execute_tools(message, executors)` вызывает доверенные обработчики приложения и возвращает `(diagnostics, results)`; при отклонении `results=None`. Если приложение выполняет вызовы самостоятельно, извлекайте их только из результата с `allow`, сохраняя изменения, прошедшие проверку. Реестр обработчиков задается приложением, а не данными модели.

Поддерживается ограниченный набор возможностей схем JSON: `type`, `enum`, закрытые объекты с `properties`, `required` и `additionalProperties: false`, массивы с `items`, `minItems` и обязательным `maxItems`, строки с `minLength` и обязательным `maxLength`, числа с `minimum` и `maximum`. Неизвестные ключевые слова, ссылки на схемы, проверки регулярными выражениями и приведение типов отклоняются. Глубина вложенности ограничена 16; логические значения не считаются числами. Для путей, получателей и команд, требующих строгого контроля, задавайте через `enum` только конкретные значения, разрешенные приложением.

Схема не заменяет проверку полномочий. Обработчики проверяют действующие полномочия, контролируют доступ к файловой системе, ограничивают время выполнения и обеспечивают транзакционность операций. Ошибка обработчика останавливает последующие вызовы с `tool_execution_failed`, но не откатывает уже выполненные действия. Результаты инструментов должны пройти входную проверку перед следующим обращением к модели.

## Ответы API и потоковая выдача

Передайте `output_guard=boundary` в `GuardedDispatch.create(...)`. При `stream: false` методы `send` и `send_user_text` возвращают безопасную диагностику и допущенное сообщение в едином внутреннем формате. Исходный ответ API не выдается. Отдельная проверка доступна через `check_provider(response, "openai" | "ollama")`. При наличии схемы содержимое ответа разбирается как JSON со строгой проверкой формата. Поддерживается один полный вариант ответа ассистента; усеченные ответы, неподдерживаемые поля сообщения ассистента или определения вызова инструмента и некорректный JSON аргументов блокируют выдачу. Для мультимодальных данных и дополнительных каналов API нужны отдельно заданные правила проверки.

Для доверенного шаблона с `stream: true` используйте `send_stream(request, emit, timeout=30)`. Адаптер собирает OpenAI-совместимые события SSE или Ollama NDJSON, включая фрагменты аргументов инструментов, проверяет наличие завершающего маркера протокола и проверяет полное сообщение. `emit` вызывается один раз только при `allow`; необработанные события не передаются вызывающему коду. Встроенный транспорт ограничивает объем данных, время ожидания при чтении и общую длительность обмена, не выполняет перенаправления и повторные попытки. Если потоковая отправка использует проверку целостности, явно задайте функцию `stream_sender`, которая проверяет байты окончательно сформированного запроса.

Для уже извлеченных текстовых фрагментов используйте `boundary.stream(chunks, emit, delivery="buffered")`. При буферизации весь ответ сохраняется до успешного завершения проверки и поддерживает оба режима, регулярные выражения, нормализацию и правила собранного контекста. По умолчанию установлены пределы: 4 096 фрагментов, 1 МиБ данных и 60 секунд на обработку потока от начала вызова. Общий срок проверяется между чтениями и перед выдачей; он не прерывает заблокированный вызов итератора. Если приложение использует собственный итератор, в нем нужно отдельно ограничить время блокирующего чтения.

`delivery="delayed"` выбирается явно и подходит только для текста с правилами поиска точных строк без нормализации и с учетом регистра. Проверяется накопленный текст. Конечный фрагмент, который может стать началом совпадения при поступлении следующих данных, пока не выдается. Регулярные выражения, нормализация, правила `assembled` и замены требуют буферизации; несовместимая политика возвращает `stream_policy_requires_buffering` до чтения данных. Уже выданную часть ответа отозвать нельзя: если любое тематическое совпадение должно блокировать весь ответ, выбирайте `buffered`. Ошибки итератора или функции выдачи останавливают передачу без перехода к резервному способу выдачи; функция выдачи должна атомарно передавать допущенный фрагмент. Диагностика содержит `emitted_characters`, но не выданный текст.

## Ограничения выполнения и проверка интеграции

Предельные ограничения пакета: 1 МиБ для ввода и преобразованного результата, 128 сообщений JSON, 64 правила и 1 024 совпадения за проход проверки. Время проверки в рабочем процессе ограничено 2 000 мс, всей операции - 6 000 мс, память рабочего процесса - 256 МиБ. Политика может уменьшать эти пределы. Один интерпретатор допускает не более четырех рабочих процессов; при превышении этого числа проверка возвращает `worker_capacity_exhausted`, и отправка блокируется. Эти ограничения пакета не относятся к лимитам обращения к модели. На macOS периодический контроль памяти не ограничивает объем выделяемой памяти в каждый момент времени.

Диагностика содержит решения, коды, идентификаторы политики и правил, счетчики; исходный текст, совпавшие фрагменты, пути и хеши запросов в нее не включаются. Не помещайте чувствительные данные в идентификаторы. В допущенных данных могут остаться чувствительные значения, не охваченные выбранными правилами.

[Тесты пакета и набор синтетических примеров](https://github.com/defrixx/Product-security-skills/tree/main/tools/prompt-guard/tests) охватывают атаки, допустимые запросы и блокировки, предусмотренные тематическими правилами. Перед развертыванием проверьте свою интеграцию: отправку именно проверенных данных на всех маршрутах обращения к модели, ложные блокировки, прекращение выдачи отклоненных ответов и повторную проверку по схемам после очистки. Отдельно проверьте обработку усеченных потоков, исчерпания ресурсов и несовпадения политики.

[model-security-eval](/Product-security-playbook/ru/ai-automation/model-security-eval/overview/) поддерживает `--guard-profile`, `--guard-mode` и `--compare-guard`, если пакет установлен. Парные испытания отдельно фиксируют решения фильтра, нарушения со стороны модели и действия в тестовой среде, включая блокировки допустимых запросов. Заблокированный ввод получает `not_assessed_for_blocked_input`; это не свидетельство устойчивости модели к атаке. Результаты на синтетических данных не подтверждают, что инструмент обнаружит все атаки в реальных входных данных.

Для парного сравнения с проверкой ответов и без нее используйте `--output-guard-profile output-security-and-topics --compare-guard`; при необходимости добавьте входной профиль. Отчеты отдельно сохраняют нарушения в исходном ответе модели в виде доказательств с замаскированными чувствительными значениями, выданные ответы, решения проверки ответов и действия в тестовой среде. Если проверка блокирует ответ с нарушением, испытание защитной меры приложения может пройти успешно, но нарушение модели остается в отчете. Блокировка допустимых контрольных запросов означает, что испытание не пройдено; ошибки при проверке ответов дают неопределенный результат.
