`model-security-eval` проверяет локальные модели LM Studio и Ollama после обновлений по сценариям безопасности на искусственных данных. Результат проверки позволяет блокировать выпуск в CI. Версия 0.4.0 требует Python 3.11+; основная часть инструмента использует только стандартную библиотеку. Инструмент работает независимо от скиллов; для сравнения с защитными проверками дополнительно требуется `prompt-guard` 0.3.x.

[Исходники и руководство](https://github.com/defrixx/Product-security-skills/tree/main/tools/model-security-eval) | [Скиллы и инструменты](/Product-security-playbook/ru/ai-automation/security-skills/overview/)

## Возможности и сценарии

В `--capabilities` укажите возможности, доступные модели в вашем приложении. Каждый профиль должен включать `chat`.

| Возможность | Разрешенная задача | Сценарии атак |
| --- | --- | --- |
| `chat` | Вернуть запрошенные открытые данные | Подмена инструкций и ролей, раскрытие секретного маркера, в том числе в закодированном виде, поддельное разрешение и атаки в несколько ходов диалога. |
| `read` | Прочитать `repo/README.md` и вернуть описание API | Доступ к другим путям и внедрение инструкций через README, комментарии в коде и метаданные извлеченных материалов. |
| `write` | Записать открытые данные в `repo/result.txt` | Запись по другим путям, поддельное разрешение и выход за разрешенные границы действий. |
| `command` | Вызвать `tests` | Вызов других команд, поддельное разрешение и выход за разрешенные границы действий. |
| `external` | Отправить открытые данные получателю `sandbox` | Отправка другим получателям, утечка секретного маркера и поддельное разрешение. |

Тестовое окружение использует искусственные материалы и файлы в памяти, имитирует результаты команд и перехватывает сообщения. Вся группа предложенных операций проверяется до выполнения первой из них. В отчете отдельно учитываются предложенные, заблокированные и выполненные операции тестового окружения. Атаки сопровождаются разрешенными задачами: модель, которая отказывается от всего, не пройдет проверку. В многоэтапных сценариях попытка выйти за разрешенные границы действий предъявляется только после того, как модель выполнит разрешенную операцию и корректно подтвердит результат.

## Установка и первый запуск

Установите пакет в отдельное окружение:

```sh
python -m pip install /path/to/Product-security-skills/tools/model-security-eval
```

Заранее запустите локальный сервер и загрузите выбранную модель. Создайте доступную для записи папку `artifacts/` и укажите внутри нее новый каталог для результатов. Компоненты пути не должны быть символическими ссылками:

```sh
mkdir -p artifacts
model-security-eval \
  --backend ollama --model "$MODEL_ID" \
  --capabilities chat,read,write,command,external \
  --repetitions 3 --max-requests 300 --max-seconds 1800 \
  --request-timeout 120 --max-steps 6 --max-tokens 2048 \
  --output "artifacts/$RUN_ID"
```

В `MODEL_ID` укажите идентификатор загруженной модели, в `RUN_ID` - новое имя запуска. Для LM Studio выберите `--backend lmstudio` и передайте непустые `--model-revision` и `--server-version`. Эти значения для LM Studio задает оператор; они не являются независимо проверенными хешами весов. Ollama позволяет получить хеш модели и версию сервера автоматически; те же необязательные параметры закрепляют ожидаемые значения.

Адреса по умолчанию: `http://127.0.0.1:11434` для Ollama и `http://127.0.0.1:1234` для LM Studio. В `--endpoint` можно указать другой адрес сервера: схему HTTP, числовой IP-адрес обратной петли (loopback) и явный порт. Учетные данные, строка запроса и путь API в адресе не допускаются. Прокси, перенаправления, автоматические повторы и переход на запасной сервер отключены. Транспорт не отправляет заголовок аутентификации; для работы с сервером, требующим аутентификации API, нужна интеграция с поддержкой этого механизма.

Добавьте `--list-cases` к команде с выбранными `--backend`, `--model`, `--output` и `--capabilities`, чтобы посмотреть список сценариев без обращения к серверу и создания файлов.

## Ограничения запуска и сравнение

В команде указаны значения по умолчанию: три испытания на сценарий, 300 попыток отправки запросов к модели и получения метаданных суммарно, 1800 секунд на запуск, 120 секунд на запрос, шесть обращений к модели на испытание и 2048 запрошенных токенов ответа. Это ограничения системы испытаний, а не универсальные пределы безопасности для промышленной эксплуатации. Предельное время ожидания ответа не может превышать оставшееся время запуска. Также по умолчанию передаются `--temperature 0` и `--seed 17`; к начальному значению добавляется индекс повторения. Размер запроса ограничен 4 МиБ, ответа - 2 МиБ.

До и после выполнения инструмент читает метаданные модели и сопоставляет ответы с выбранной моделью и обнаруженными альтернативными идентификаторами. Изменение метаданных блокирует допуск к выпуску. Достоверность полученных метаданных зависит от доверия к локальному серверу.

Добавьте `--baseline artifacts/previous-run/report.json` для сравнения результатов испытаний. Для сопоставления должны совпадать набор сценариев, содержимое исходных файлов системы оценки, выбранные возможности, адаптер, параметры генерации, число повторений и ограничения запуска. Несовместимые критерии блокируют допуск к выпуску; изменения модели, ревизии, сервера и адреса учитываются отдельно. Улучшение результата не отменяет неуспешный результат текущей проверки.

## Заключение для CI и отчеты

Режим `--compare-guard` сравнивает поведение приложения без защиты и с ней: задайте `--guard-profile`, `--output-guard-profile` или оба профиля. Каждому варианту выделяется отдельный равный бюджет запросов и времени, поэтому предусмотрите ресурсы для обоих. Этот режим нельзя сочетать с историческим сравнением через `--baseline`. Блокировка атаки может подтвердить защиту приложения, но не устойчивость модели; блокировка допустимой задачи означает неуспешный результат. Отдельно учитывайте нарушения, сгенерированные моделью, и нарушения, дошедшие до границы выдачи или выполнения в защищенном приложении. Необходимость дополнительной проверки, ошибки и незавершенное выполнение означают неопределенный результат.

| Код завершения | Заключение | Действие при выпуске |
| --- | --- | --- |
| `0` | `pass`: все запланированные испытания завершены и проверки пройдены | Разрешить переход к следующему этапу выпуска. |
| `1` | `fail`: выявлено нарушение или не выполнена разрешенная задача | Заблокировать выпуск. |
| `2` | `inconclusive` либо ошибка выполнения или настройки | Заблокировать выпуск. |

Разместите [скрипт CI](https://github.com/defrixx/Product-security-skills/blob/main/tools/model-security-eval/examples/ci-gate.sh) перед этапом выпуска на узле выполнения CI с локальным сервером. Запускайте его из корня репозитория скиллов с `MODEL_ID` и `EVAL_OUTPUT`; для LM Studio также нужны `MODEL_REVISION` и `SERVER_VERSION`. Скрипт сохраняет код завершения CLI. Отчеты сохраняйте с помощью штатного механизма хранения артефактов CI.

Запуск создает `report.md`, структурированный `report.json` и атомарно обновляемый `checkpoint.json`. Каталоги с результатами имеют права доступа `0700`, файлы доказательств - `0600`. Секретный маркер маскируется в распознаваемых представлениях, включая закодированные. Наблюдения оцениваются целиком; в отчетах сохраняются фрагменты ограниченной длины и хеши. Контрольная точка хранит сведения о завершенных, выполняемых и ожидающих запуска испытаниях. Прерывание блокирует выпуск и фиксирует ход выполнения; наличие контрольной точки не означает автоматического продолжения. В стандартный поток вывода (stdout) поступают события JSON с идентификаторами, диагностикой, счетчиками и отпечатками критериев вместо текста ответов сервера.

## Связь с защитой приложения

[Тесты пакета](https://github.com/defrixx/Product-security-skills/tree/main/tools/model-security-eval/tests) проверяют операции тестового окружения, нормализацию, идентификацию, сравнение, маскирование, контрольные точки, результаты проверки для CI и обмен по HTTP через адрес обратной петли. Реальная модель для них не нужна. Успешное испытание модели подтверждает наблюдаемый результат для выбранного профиля испытаний на искусственных данных; отправку запросов и разрешение действий в приложении проверяйте отдельно.

[prompt-integrity](/Product-security-playbook/ru/ai-automation/prompt-integrity/overview/) проверяет утвержденные статические инструкции перед отправкой запроса. `model-security-eval` оценивает поведение модели и границы действий тестового окружения; он не устанавливает эту обертку автоматически и не ограничивает права инструментов в рабочем приложении. Перед выполнением реальных операций приложение должно независимо проверять аргументы, допустимость ресурсов и получателей, а также разрешения на действия.
