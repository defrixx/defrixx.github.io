Каждый из пяти скиллов работает самостоятельно. Для задачи с несколькими этапами их можно объединить: разбор отчета или ревью кода, реализация исправлений, проверка результата и при необходимости очистка материалов перед передачей.

Это порядок работы ассистента с единым форматом передачи результатов между этапами. Отдельного движка автоматизации или обязательного запуска всех скиллов нет. [prompt-integrity](/ru/ai-automation/prompt-integrity/overview/) подключается к приложению отдельно и не управляет этим процессом.

## Выбор этапов

| Задача этапа | Скилл | Передаваемый результат |
| --- | --- | --- |
| Разобрать готовый отчет сканера | [security-report-triage](/ru/ai-automation/security-skills/security-report-triage/overview/) | Учтенные исходные сигналы, замечания, доказательства и приоритетный список действий. |
| Оценить код PR или репозитория | [security-review](/ru/ai-automation/security-skills/security-review/overview/) | Подтвержденные замечания, гипотезы и критерии исправления. |
| Реализовать выбранные исправления | [secure-development](/ru/ai-automation/security-skills/secure-development/overview/) | Предложенные или примененные изменения, новая ревизия и результаты проверок. |
| Проверить конкретные исправления | [security-fix-verification](/ru/ai-automation/security-skills/security-fix-verification/overview/) | Заключение по каждому замечанию с проверкой исходной атаки, способов обхода защиты и допустимых операций. |
| Подготовить выбранные материалы к передаче | [sensitive-data-cleanup](/ru/ai-automation/security-skills/sensitive-data-cleanup/overview/) | Отдельная обработанная копия и отчет о заменах, пропусках и ограничениях. |

Разбор отчета и ревью кода - альтернативные точки входа. Можно сразу начать с исправления известного замечания или проверки готового исправления. Очистка материалов необязательна и не меняет доказательства в исходном отчете.

## Передача результатов

[Контракт передачи замечаний](https://github.com/defrixx/Product-security-skills/blob/main/skills/security-report-triage/references/handoff-contract.md) входит в комплект `security-report-triage` и `security-fix-verification` в виде локальных копий. Для ручной работы достаточно эквивалентных полей в обычном отчете; JSON необязателен.

Между этапами сохраняются идентификатор исходной оценки вместе с идентификатором замечания, ссылки на доказательства, ревизия и локальные изменения, область задачи, допущения и ограничения. При объединении замечаний старые идентификаторы остаются как дополнительные обозначения; при разделении новые замечания связаны с исходным.

Для глобального идентификатора и дополнительных обозначений используйте пару `(origin_assessment_id, finding_id)`: отдельный идентификатор замечания может совпадать в независимых оценках. Отклоняйте неизвестные основные версии схемы передачи, не считая их совместимыми. Дополнительные поля сохраняйте как данные без исполнения; вложения с доказательствами должны оставаться внутри выбранного каталога передачи и проходить проверку на чувствительное содержимое.

| Поле | Что фиксирует |
| --- | --- |
| `assessment_status` | Подтверждение, гипотезу или опровержение на исходной ревизии. |
| `severity` и `confidence` | Последствия и уверенность в доказательствах независимо друг от друга. |
| `implementation_state` | Состояние исправления: неизвестно, работа не начата, изменение предложено или применено. |
| `verification_status` | Отсутствие проверки либо заключение `fixed`, `partially_fixed`, `not_fixed`, `inconclusive` для проверенной ревизии. |

Примененное изменение не получает автоматически статус `fixed`. Подтвержденная уязвимость в старой ревизии сохраняется в истории после успешного исправления. Отсутствующие сведения означают неизвестность, а не успешную проверку.

Шаблоны отчетов отдельных скиллов содержат единый реестр действий. Передавайте его между этапами, сохраняя исходные идентификаторы замечаний, историю оценок, доказательства, состояние реализации, заключение о проверке и оставшиеся задачи. Начинайте итоговый отчет с задач, которые еще предстоит выполнить; создание патча не закрывает замечание. Самопроверку фиксируйте только тогда, когда один ассистент действительно реализовал и проверил изменение.

## Пример общей задачи

> Используй security-report-triage для приложенного SARIF и текущей ревизии. Через secure-development исправь подтвержденные замечания в согласованных компонентах, затем проверь их с security-fix-verification. Сохрани идентификаторы, исходные доказательства и отдельные статусы оценки, реализации и проверки. Изменения и проверки выполняй локально; в итоговом отчете укажи непроверенные условия.

Для оценки кода без готового отчета замените первый этап на `security-review`. При необходимости явно добавьте `sensitive-data-cleanup` для выбранных итоговых материалов.

## Продолжение и границы задачи

В рамках уже согласованной общей задачи ассистент переходит между выбранными этапами без повторного согласования каждого шага. Разбор или проверка, заказанные отдельно, не разрешают автоматически вносить исправления. Публикация, изменения во внешних системах и установка не входят в процесс по умолчанию.

После перерыва сверяются контрольные характеристики входных данных, ревизии, рабочая копия, область задачи и завершенные этапы. При изменении исходных условий затронутые доказательства перепроверяются. Противоречия разрешаются по данным конкретных ревизий либо отмечаются как неразрешенные. Исправление и проверка одним ассистентом обозначаются как самопроверка.

## Что проверено в исходном проекте

В репозитории есть проверки структуры автономных пакетов, вспомогательных скриптов, контракта передачи и примеры совместной работы на искусственных тестовых данных. Скрипт запуска регрессионных тестов также выполняет отдельный набор `evals/tests/`, для которого не нужен сервер модели. Дополнительные [испытания поведения моделей](https://github.com/defrixx/Product-security-skills/blob/main/evals/README.md) сравнивают выполнение выбранных сценариев на искусственных данных с инструкциями скилла и без них. Успешное выполнение тестов системы испытаний не подтверждает соблюдение инструкций моделью или надежность решений ассистента на произвольном проекте. Охват и ограничения приведены в [описании тестов](https://github.com/defrixx/Product-security-skills/blob/main/tests/README.md); интеграционные проверки приложений выполняются отдельно. Скрипты испытаний и локальные материалы не входят в копируемые скиллы.
