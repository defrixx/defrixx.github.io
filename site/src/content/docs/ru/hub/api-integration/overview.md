Готовый учебный маршрут для сервиса заказов, подключающего доставку. Вы получите схему доверия, требования, матрицу проверок и запись решения. Материалы и ожидаемые результаты синтетические; проверку своего проекта вы выполняете локально.

## Когда применять

Есть несколько арендаторов (tenant), корпоративный вход сотрудников, OAuth-доступ к API партнера и входящие webhook. Нужны описание потоков, модель членства и ролей, контракт OAuth/webhook партнера, правила изменения заказов и выбранная ревизия кода. Если контракт партнера неизвестен, пометьте соответствующие требования как не проверенные и сначала получите контракт.

## Зафиксировать контракт до проверки

Опишите клиента OIDC и серверного клиента OAuth отдельно: доверенные издатели, метаданные и конечные точки, URI перенаправления, способ аутентификации серверного клиента и разрешения. Адреса серверов и API не берут из параметров пользователя или webhook; перенаправление запроса не должно раскрывать токен другому источнику. Не предполагайте, что токен доступа партнера является JWT или ID Token.

Зафиксируйте срок и одноразовость OAuth-транзакции, версию интеграции, состояния подключения, правила отзыва и повторов. Для исходящего API нужны контракт идемпотентности и способ сверки неизвестного результата, для webhook - точные подписанные байты и правила повторов. Числа учебного примера не заменяют контракт поставщика.

## Три независимых решения

| Граница | Что устанавливается | Что проверять отдельно |
| --- | --- | --- |
| Корпоративный OIDC | Кто вошел: пара issuer/subject и действующая сессия | Членство в организации арендатора и право подключить доставку |
| Полномочия сотрудника | Может ли этот сотрудник менять интеграцию выбранного арендатора | Актуальное право на старте и при завершении подключения |
| OAuth партнера | К каким ресурсам внешнего API выдан доступ серверу приложения | Аккаунт партнера, полномочия OAuth (scopes), срок действия и отзыв |

ID Token не используют как токен доставки. Полученное согласие OAuth не дает сотруднику внутренних административных прав. Идентификатор арендатора из URL, формы или webhook не является доверенным источником членства.

## Последовательность

1. Опишите активы, стороны и границы доверия в [примере ревью](/ru/hub/reviews/delivery-api/overview/). Зафиксируйте связь арендатора, интеграции, аккаунта партнера и заказа.
2. Пройдите [API-плейбук](/ru/application-security/api/api-security-patterns/playbook/) и [OIDC/OAuth](/ru/application-security/identity/oidc-oauth/playbook/); выберите применимые требования API-001 - API-009 из примера. Это ID учебного сценария, а не номера стандарта или универсальная корпоративная политика.
3. Согласуйте конкретный контракт webhook. Синтетический контракт из примера нельзя подставлять вместо документации реального поставщика.
4. Заполните шаблон и матрицу: положительные, отрицательные, повторные и параллельные запросы, отзыв прав и токенов. Для каждой проверки сохраните ревизию, наблюдение и итог. До исполнения статус `not-run`.
5. При необходимости используйте [каталог скиллов](/ru/hub/catalogue/overview/): security-review для оценки, secure-development для отдельно разрешенных исправлений, security-fix-verification для повторной проверки. Сохраняйте ID замечаний между этапами.
6. Передайте человеку результат и оставшиеся вопросы. Решение по реальному выпуску принимает ответственный человек по правилам своей команды.

## Применимость и передача результата

Для каждого API-001 - API-009 укажите применимость и обоснование. `not-applicable` требует подтвержденной причины и ответственного: отсутствие реализации или теста не означает неприменимость. Применимая неисполненная проверка остается `not-run`; недостаточные или противоречивые наблюдения дают `inconclusive`. `pass`/`fail` требуют фактического наблюдения на указанной ревизии.

Свяжите требование с `test_id`, ID замечания, исходной ревизией, ревизией исправления и отдельным результатом повторной проверки. Каждый новый прогон получает свою запись, сохраняя историю. Неприменимость и принятое исключение учитываются отдельно. Исключение ограничивают областью, сроком, ответственным, компенсирующими мерами и решением человека; оно не превращает чужую подпись или нарушенную привязку арендатора в успешную проверку. Без проверенной безопасной альтернативы соответствующая операция остается заблокированной.
