# Плейбук мер защиты веб-приложений: сопоставление с OWASP Top 10:2021 и 2025

## 1. Область

Документ сохраняет детальную структуру OWASP Top 10:2021 ради стабильности ссылок из ревью и добавляет явное соответствие OWASP Top 10:2025, актуальному выпуску OWASP для рисков веб-приложений. Используйте тематические разделы как базовый профиль мер контроля; для отчетности по 2025 используйте сопоставление ниже.

Границы документа:
- Этот плейбук задает решение по результатам ревью веб-приложений, критичность и минимальные негативные тесты по категориям OWASP Top 10.
- Детальные требования к авторизации API, GraphQL, webhook и gRPC находятся в [плейбуке безопасности API](../../api/api-security-patterns/playbook.ru.md).
- Браузерные меры контроля CSP, CORS, cookie, встроенного содержимого и цепочки поставки клиентской части находятся в [плейбуке безопасности браузера и клиентской части](../browser-security/playbook.ru.md).
- Детали безопасной разработки по валидации, контекстному кодированию вывода, инъекциям, обработке файлов и неправильному использованию криптографии находятся в [плейбуке безопасной разработки и ревью кода](../../secure-coding/code-review/playbook.ru.md).
- SAST, SCA и поиск секретов в тематических разделах ниже описаны применительно к рискам веб-приложений. Их общую конфигурацию, обязательные запуски, обработку результатов и подтверждение закрытия определяет плейбук безопасной разработки и ревью кода.
- Меры защиты цепочки поставки ПО и образов контейнеров находятся в профильных плейбуках; здесь они учитываются только при принятии решения о выпуске веб-приложения.

## 2. A01:2021 Broken Access Control

### 2.1 Угроза, описание и цель атаки

Нарушение контроля доступа возникает, когда пользователь или сервис может читать, менять или удалять данные вне своей роли и области владения. Цель атакующего: выйти за пределы разрешений, получить доступ к чужим объектам и выполнить привилегированные операции.

### 2.2 Виды и типовой ход эксплуатации

Типы:
- `IDOR` (Insecure Direct Object Reference, небезопасная прямая ссылка на объект): пользователь меняет идентификатор ресурса и получает чужие данные. Пример: `GET /api/orders/1002` заменяется на `GET /api/orders/1003`, и сервер отдает заказ другого клиента.
- `BOLA` (Broken Object Level Authorization, отсутствие проверки прав на уровне объекта): API проверяет факт логина, но не проверяет владение объектом. Пример: в GraphQL-запросе `invoice(id: "inv_778")` атакующий подставляет чужой `id` и видит чужой инвойс.
- Прямой вызов скрытых эндпоинтов (forced browsing): обращение к маршруту вручную по URL, минуя интерфейс. Пример: обычный пользователь открывает `/admin/export` напрямую и получает выгрузку.
- Повышение привилегий: выполнение административных действий с ролью пользователя. Пример: `PATCH /api/users/me` с полем `role=admin` принимается без серверной проверки.
- Подмена атрибутов токена или cookie: изменение роли или идентификатора в токене либо cookie. Пример: подмена claim `role:user -> role:admin` в неверно проверяемом JWT.
- Злоупотребление `CORS` (Cross-Origin Resource Sharing): небезопасная политика позволяет чужому origin читать ответы API с учетными данными пользователя. Пример: сервер отражает любой `Origin` и ставит `Access-Control-Allow-Credentials: true`, из-за чего вредоносный сайт читает данные пользователя.
- Цепочка `SSRF` (Server-Side Request Forgery): приложение по пользовательскому URL обращается во внутреннюю сеть. Пример: параметр `image_url=http://169.254.169.254/latest/meta-data/` позволяет читать облачные метаданные.

Типовой ход:
- Разведка API и параметров (`user_id`, `order_id`, `tenant_id`)
- Подмена идентификатора или роли в запросе
- Поиск отсутствующих серверных проверок авторизации
- Массовый перебор объектов и сбор данных
- Переход к операциям изменения/удаления

Что задевается:
- Изоляция данных между пользователями и арендаторами
- Административные функции и служебные панели
- Внутренние сервисы и API управления

Последствия:
- Утечка данных, несанкционированные изменения, полный захват бизнес-функций

### 2.3 Практическая защита

- `deny-by-default` и проверка прав на каждый запрос и объект
- Централизованный механизм политик (`RBAC`/`ABAC`/`ReBAC`)
- Обязательная проверка владельца (`resource.owner_id == caller.subject_id`)
- Строгая сегментация внешних и внутренних API, mTLS между сервисами
- Ограничение `CORS` строго согласованными origin, методами и заголовками
- Дополнительная аутентификация для операций высокого риска
- Проверка:
  - негативные интеграционные тесты на горизонтальный и вертикальный обход
  - тесты прямого вызова скрытых эндпоинтов
  - мониторинг аномалий `401/403` и перебора идентификаторов

### 2.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical`, если обход контроля доступа затрагивает административные функции, изоляцию арендаторов, состояние платежей, массовый экспорт или секреты.

Рабочие настройки:
- Каждая операция пользователя, арендатора, поддержки, администратора и сервиса имеет явную запись политики: субъект, действие, ресурс, арендатор и контекст (`context`).
- Авторизация принудительно применяется на уровне сервиса или доменной логики, а не только в интерфейсе, шлюзе, промежуточном обработчике маршрута или директивах схемы GraphQL.
- Новые эндпоинты, методы, мутации и задания массовой обработки или экспорта запрещены по умолчанию, пока нет политики и негативных тестов.
- CORS для браузерных процессов с учетными данными использует точный список разрешенных origin; origin с подстановочным символом при передаче учетных данных отклоняется.

Подтверждения:
- Матрица политик или эквивалентные политики в виде кода для чувствительных операций.
- Результаты негативных тестов авторизации на уровне объекта, свойства и функции.
- Примеры событий аудита разрешения и запрета чувствительных действий.
- Реестр маршрутов и API с владельцем, моделью внешней доступности и классификацией данных.

Негативные тесты:
- Пользователь A не может читать, менять, удалять, экспортировать или определять существование объекта пользователя B.
- Пользователь с низкими привилегиями не может вызывать административные эндпоинты напрямую.
- Доступ к идентификаторам объектов других арендаторов, вложенным узлам GraphQL, пакетным эндпоинтам и массовому экспорту отклоняется.
- Недоверенные origin не могут читать ответы на запросы с учетными данными.

Ложные срабатывания / пропуски:
- Ответ `403` сам по себе недостаточен; проверяйте применение серверной политики, а не только поведение шлюза.
- Замечания сканера по маршрутам часто пропускают авторизацию бизнес-объектов и резолверов GraphQL.
- Маскирование ответом `404` допустимо, но тесты должны доказать отсутствие неавторизованного доступа к данным и утечки через время ответа.

## 3. A05:2021 Security Misconfiguration

### 3.1 Угроза, описание и цель атаки

Ошибки конфигурации появляются, когда приложение, сервер, контейнер или облачный сервис развернуты с небезопасными настройками. Цель атакующего: использовать дефолтные и избыточные настройки для входа, закрепления и расширения доступа.

### 3.2 Виды и типовой ход эксплуатации

Типы:
- Отладочный режим и трассировки стека в рабочей среде: раскрываются внутренние пути, версии и переменные окружения. Пример: при ошибке сервер показывает трассировку с `DB_HOST` и именем таблицы.
- Учетные записи и пароли по умолчанию: вход с заводскими учетными данными. Пример: панель администратора принимает `admin/admin`.
- Лишние HTTP-методы и открытые административные маршруты расширяют поверхность атаки. Пример: эндпоинт принимает `PUT`/`DELETE`, хотя должен поддерживать только `GET`.
- Небезопасный XML-парсер приводит к `XXE` (XML External Entity): парсер разрешает внешние сущности. Пример: XML с `<!ENTITY xxe SYSTEM "file:///etc/passwd">` возвращает содержимое файла.
- Отсутствие критичных заголовков безопасности (`CSP`, `HSTS`): браузер не получает ограничения на скрипты и транспорт. Пример: без CSP внедренный встроенный скрипт успешно выполняется.
- Избыточные права сервисных учетных записей, bucket, PVC и хранилищ секретов: локальная уязвимость быстро расширяет последствия. Пример: веб-сервис с правами `s3:*` читает все bucket по одному SSRF-запросу.

Типовой ход:
- Сканирование открытых панелей, отладочных эндпоинтов и версий компонентов
- Проверка учетных данных по умолчанию
- Тесты XML-парсера на внешние сущности
- Поиск ошибок конфигурации прокси, CORS и политик заголовков
- Переход к чтению файлов, продвижение атакующего внутри инфраструктуры, закреплению

Что задевается:
- Конфиденциальные данные и секреты
- Плоскость администрирования
- Межсервисные границы доверия

Последствия:
- Быстрый первоначальный доступ, ускоренное повышение привилегий, устойчивое присутствие

### 3.3 Практическая защита

- Усиленные базовые настройки для всех окружений и автоматическая проверка дрейфа
- Контроль конфигурации через политики в виде кода и обязательное ревью
- Безопасный профиль XML-парсера с запретом DTD и внешних сущностей, где возможно
- Обязательный набор HTTP заголовки безопасности
- Регулярный аудит конфигурации и ревью внешней поверхности атаки
- Проверка:
  - проверки соответствия IaC и среды выполнения
  - тесты на безопасную деградацию конфигов
  - контроль отклонений от эталонной конфигурации

### 3.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `Medium`; повышайте до `High`, если ошибка конфигурации открывает административные интерфейсы, секреты, облачные метаданные, выполнение отладочного кода или небезопасные настройки по умолчанию, доступные из интернета.

Рабочие настройки:
- Отладочный режим, подробные трассировки стека, демонстрационные приложения, учетные данные по умолчанию, публичные административные консоли и просмотр содержимого каталогов отключены в рабочей среде.
- Заголовки безопасности заданы по классу приложения; для браузерных приложений как минимум принято решение по HSTS, CSP, защите от встраивания во фрейм, определению типа содержимого, политике Referer и атрибутам cookie.
- XML-парсеры отключают DTD, внешние сущности, небезопасные резолверы и неограниченное расширение сущностей, если нет документированного исключения для устаревшей интеграции.
- Дрейф конфигурации проверяется при развертывании и не реже каждых `24h` для доступных из интернета и особо ценных сервисов.

Подтверждения:
- Результаты сканирования IaC и конфигурации среды выполнения для развернутого окружения.
- Реестр внешней поверхности атаки с владельцем и причиной доступности.
- Результаты проверки заголовков и сканирования TLS для эндпоинтов, доступных браузерам.
- Реестр исключений для отладки, устаревших парсеров, публичного администрирования и ослабленных заголовков.

Негативные тесты:
- Учетные данные по умолчанию не работают на всех доступных интерфейсах управления.
- Отладочные эндпоинты и трассировки стека недоступны без утвержденного административного доступа.
- XXE и XML-бомбы завершаются безопасным отказом там, где принимается XML.
- Публичные эндпоинты не раскрывают внутренние баннеры версий, переменные окружения или чувствительные метаданные.

Ложные срабатывания / пропуски:
- Сканеры заголовков могут завышать риск для API без браузерных клиентов; классифицируйте риск по фактическому клиенту и доступности.
- Успешных проверок IaC недостаточно, если изменения во время выполнения, значения Helm или экстренные правки создают дрейф после развертывания.
- Некоторым устаревшим интеграциям нужны более слабые настройки; оформляйте их как исключения с владельцем, компенсирующими мерами и сроком действия.

## 4. A06:2021 Vulnerable and Outdated Components

### 4.1 Угроза, описание и цель атаки

Эта категория охватывает уязвимые, неподдерживаемые или недоверенные компоненты в коде приложения, образах среды выполнения, плагинах, клиентских пакетах и инструментах сборки. Цель атакующего: использовать известное слабое место или внедрить вредоносный код через доверенную зависимость.

### 4.2 Виды и типовой ход эксплуатации

Типы:
- Зависимость или фреймворк с известной уязвимостью: приложение поставляется с компонентом, имеющим эксплуатируемую CVE или завершенную поддержку. Пример: опубликованный пример эксплуатации RCE работает против развернутого парсера или веб-фреймворка.
- Подмена зависимости через путаницу реестров (dependency confusion): система сборки берет пакет из публичного реестра вместо внутреннего. Пример: внутренний `corp-utils` загружается из npm/PyPI, где атакующий опубликовал одноименный пакет.
- Typosquatting: установка пакета с похожим именем, но вредоносным содержимым. Пример: вместо `requests` устанавливается `reqeusts`, который отправляет токены наружу.
- Компрометация исполнителя или плагина CI: вредоносный шаг выполняется в доверенной сборке. Пример: зараженный плагин CI читает `CI_SECRET` и отправляет его на внешний URL.
- Подмена артефакта между сборкой и развертыванием: в реестр попадает измененный образ или пакет. Пример: тег `v1.4.2` переписывается образом с бэкдором.
- Неподдерживаемый базовый образ или среда выполнения: пакеты ОС и среды выполнения языков больше не получают исправлений безопасности. Пример: образ контейнера сохраняет среду выполнения с завершенной поддержкой, потому что приложение все еще на ней собирается.

Типовой ход:
- Поиск доступных компонентов с известными уязвимостями или неподдерживаемыми версиями
- Поиск зависимостей без закрепления версии и проверки источника
- Внедрение вредоносного пакета или обновления плагина
- Захват токена или секрета CI
- Публикация подмененного артефакта в реестре
- Доставка вредоносного кода в рабочую среду через легитимный конвейер

Что задевается:
- Код продукта и артефакты сборки
- Секреты CI/CD и доверенные учетные данные при злоупотреблении обновлениями компонентов или плагинами сборки
- Система выпуска и зависимые сервисы

Последствия:
- Эксплуатация известных слабых мест, массовая компрометация релизов и закрепление на уровне цепочки поставки

### 4.3 Практическая защита

- `SBOM` (Software Bill of Materials) и инвентаризация транзитивных зависимостей
- Подпись артефактов и проверка подписи при развертывании
- Внутренние доверенные зеркала и запрет неутвержденных источников
- `SCA` (Software Composition Analysis) как обязательная проверка известных уязвимых, неподдерживаемых и запрещенных политикой компонентов
- Отслеживание владельцев, пути обновления и срока действия исключений для зависимостей, базовых образов и плагинов
- Краткоживущие учетные данные CI, изоляция исполнителя, запрет общих секретов
- Проверка:
  - provenance/attestation в CD
  - мониторинг аномальных публикаций и установок
  - штабные учения по инцидентам цепочки поставки

### 4.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical`, если доступная для эксплуатации уязвимость компонента позволяет RCE, обход аутентификации, компрометацию арендатора или данных, подписанного релизного артефакта, раскрытие секрета CI или учетных данных развертывания в рабочей среде, компрометацию широко используемых пакетов или образов.

Рабочие настройки:
- Релизное развертывание использует поддерживаемые компоненты и неизменяемые ссылки на артефакты (дайджест `sha256` для образов), а также отклоняет изменяемые теги вроде `latest`.
- Релизные артефакты подписаны или сопровождаются проверенными provenance/attestation от доверенного сборщика.
- Учетные данные CI краткоживущие, ограничены конкретным конвейером и недоступны сборкам из недоверенных pull request или форков.
- Источники зависимостей закреплены за одобренными реестрами или зеркалами; для имен закрытых пакетов есть защита от подмены зависимости через путаницу реестров.
- Фреймворки, среды выполнения, базовые образы и критичные библиотеки с завершенным сроком поддержки требуют владельца миграции, срока, компенсирующих мер и явного принятия риска.

Подтверждения:
- SBOM или реестр зависимостей релизных артефактов, включая компоненты среды выполнения и базового образа, где это доступно.
- Результаты SCA с решением политики, контекстом доступности для эксплуатации и риска, обработкой исключений.
- Результат проверки provenance и подписи при допуске к развертыванию.
- Ревью прав CI/CD для исполнителей, файлов процессов, релизных токенов и доступа к реестру артефактов.

Негативные тесты:
- Развертывание по изменяемому тегу или из неподдерживаемого базового образа отклоняется в рабочей среде.
- Неподписанный артефакт, неверная учетная запись сборщика, неверный репозиторий или неверная идентичность процесса сборки не проходят проверку допуска.
- Сборка из fork или недоверенной ветки не имеет доступа к подписи для рабочей среды или учетным данным развертывания.
- Зависимость из неутвержденного источника или публичный пакет с именем закрытого пакета блокируются.

Ложные срабатывания / пропуски:
- SBOM без проверки политики при развертывании обеспечивает инвентаризацию, но не принудительное применение правил.
- SCA может пропустить вредоносные пакеты без CVE и завысить критичность недостижимых уязвимостей; сочетайте его с закреплением источника, provenance, проверкой доступности для эксплуатации и поведения.
- Корректной подписи самой по себе недостаточно; проверяйте идентичность подписанта и сборщика, источник, параметры и дайджест объекта подписи.

## 5. A02:2021 Cryptographic Failures

### 5.1 Угроза, описание и цель атаки

Криптографические ошибки позволяют атакующему читать, подменять или повторно использовать защищенные данные. Цель: компрометация каналов связи, хранилищ, ключей и токенов.

### 5.2 Виды и типовой ход эксплуатации

Типы:
- Отсутствие или ослабленный `TLS` (Transport Layer Security): данные передаются без надежной защиты канала. Пример: логин и пароль уходят по HTTP в открытом Wi-Fi.
- Слабые/устаревшие алгоритмы и режимы шифрования: криптозащита формально есть, но практической стойкости нет. Пример: использование устаревшего шифра позволяет дешифровать перехваченный трафик.
- Неправильное хранение паролей: пароли хранятся в открытом виде или с использованием быстрого хеша без соли. Пример: после утечки БД пароли быстро восстанавливаются по словарю.
- Утечки ключей и секретов из кода и CI: ключи попадают в Git, артефакты или журналы сборки. Пример: `AWS_SECRET_ACCESS_KEY` найден в публичном коммите.
- Повторный `IV` (Initialization Vector) или nonce: нарушается безопасность симметричного шифрования. Пример: повторный nonce в токенах позволяет анализировать и подделывать данные.

Типовой ход:
- Перехват трафика и поиск пути понижения версии протокола
- Эксплуатация слабой криптоконфигурации
- Получение дампа БД/бэкапа
- Локальный подбор учетных данных и их повторное использование
- Доступ к сервисам через скомпрометированные токены

Что задевается:
- Пароли, токены, персональные и платежные данные
- Ключевая инфраструктура
- Доверие между сервисами

Последствия:
- Массовая утечка, перехват сессий, долгосрочный компромат ключей

### 5.3 Практическая защита

- TLS 1.2+ (предпочтительно 1.3), HSTS
- Хранение ключей в `HSM`/`KMS`
- Пароли хранятся только с применением адаптивного хеширования (Argon2id/scrypt/bcrypt/PBKDF2)
- Ротация ключей и секретов (плановая + аварийная)
- Шифрование данных при хранении в соответствии с классификацией
- Проверка:
  - крипто-инвентаризация и контроль сроков ключей
  - TLS-сканирование
  - поиск секретов в репозиториях/контейнерах

### 5.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical` для учетных данных в открытом виде, эксплуатируемой слабости хранения паролей, раскрытия платежных или персональных данных, компрометации ключа подписи или возможности подделывать токены.

Рабочие настройки:
- Предпочтителен TLS 1.3; TLS 1.2 разрешен только с современными наборами шифров и без возврата к устаревшим протоколам.
- HTTPS для браузерных клиентов использует HSTS после проверки безопасности внедрения; включение в preload требует отдельного решения по риску.
- Пароли хешируются через Argon2id, scrypt, bcrypt или PBKDF2 с параметрами, проверенными с учетом вычислительной стоимости на текущей платформе; открытый текст, обратимое шифрование и быстрые хеши отклоняются.
- Ключи находятся в KMS/HSM или утвержденной системе управления секретами; аварийный отзыв и ротация тестируются для особо ценных ключей.
- Шифрование чувствительных данных согласовано с классификацией данных, контролем доступа, обработкой резервных копий и разделением ключей.

Подтверждения:
- Сканирование TLS и конфигурация для всех публичных и особо ценных внутренних эндпоинтов.
- Настройки хеширования паролей и план миграции устаревших хешей.
- Реестр ключей с владельцем, местом хранения, периодичностью ротации и аварийной процедурой.
- Результаты поиска секретов в репозиториях, образах, журналах и артефактах CI.

Негативные тесты:
- HTTP и попытки понижения версии TLS не раскрывают сессии или учетные данные.
- Слабые алгоритмы JWT, неизвестные `kid` или источники JWKS и просроченные ключи отклоняются там, где используются токены.
- Известные тестовые секреты, имитирующие утечку, обнаруживаются в CI и при сканировании образов.
- Восстановление из резервной копии не обходит шифрование или политику доступа к ключам.

Ложные срабатывания / пропуски:
- Оценка сканера TLS не доказывает безопасность прикладных токенов или жизненного цикла ключей.
- Утверждение «зашифровано при хранении» неполно без владельцев ключей, путей доступа и охвата резервных копий.
- Стойкость хеша пароля зависит от параметров и стоимости вычислений на оборудовании, а не только от названия алгоритма.

## 6. A03:2021 Injection

### 6.1 Угроза, описание и цель атаки

Инъекции возникают, когда пользовательский ввод попадает в интерпретатор SQL, командную оболочку, шаблонизатор или браузерный контекст без безопасной обработки. Цель атакующего: извлечение данных, обход авторизации и выполнение произвольного кода.

### 6.2 Виды и типовой ход эксплуатации

Типы:
- `SQLi` (SQL Injection): пользовательский ввод меняет SQL-логику запроса. Пример: `id=1 OR 1=1` возвращает все записи; в слепом варианте с анализом времени ответа используется `SLEEP(5)` для подтверждения.
- Внедрение команд (command injection): пользовательский ввод попадает в команду оболочки. Пример: в параметр `filename` подставляется `report.txt; cat /etc/passwd`.
- `SSTI` (Server-Side Template Injection): ввод интерпретируется как выражение шаблонизатора. Пример: `{{7*7}}` возвращает `49`, что подтверждает выполнение кода шаблона.
- `XSS` (Cross-Site Scripting): вредоносный JavaScript выполняется в браузере жертвы. Пример: содержимое `<script>fetch('/api/me')</script>` в комментарии крадет данные сессии.
- `XXE` (XML External Entity): внешняя сущность в XML читает локальный файл или инициирует SSRF. Пример: XML-поле с сущностью на `file:///etc/hosts` возвращает содержимое файла.

Типовой ход:
- Поиск входной точки (параметр/заголовок/cookie/тело)
- Валидация интерпретации полезной нагрузки
- Подтверждение через ошибки, время ответа или реакцию по внешнему каналу
- Извлечение данных или выполнение команд
- Закрепление через кражу сессии/учетных данных

Что задевается:
- Базы данных и бизнес-данные
- Сервер приложений и ОС
- Браузерные сессии пользователей

Последствия:
- Полный контроль над данными, RCE, массовая компрометация аккаунтов

### 6.3 Практическая защита

- Параметризованные запросы и ORM для SQL
- Запрет конкатенации строк для SQL и команд
- Фильтрация входных данных и список разрешенных значений
- CSP как дополнительный слой защиты
- Избегайте запуска командной оболочки; используйте встроенные API языка или среды выполнения вместо команд оболочки
- Контекстное экранирование на выводе
- Если выполнение команды ОС неизбежно, используйте фиксированный путь к исполняемому файлу, API с массивом аргументов без раскрытия выражений оболочкой, небольшой список разрешенных операций, строгую валидацию аргументов и запрет имен команд, управляемых пользователем
- Экранирование метасимволов оболочки является лишь крайней компенсирующей мерой, а не основной защитой; отдельно тестируйте метасимволы и инъекцию аргументов.
- Изоляция процесса формирования вывода или интерпретации в песочнице либо контейнере
- Для SSTI: обновление шаблонизаторов, запрет пользовательских шаблонов, очистка содержимого, шаблоны без логики
- Для SSRF: список разрешенных доверенных адресов, фильтрация параметров, учет DNS rebinding
- Для XSS/PHP-инъекций: htmlspecialchars, фильтрация/экранирование, отключение лишних функций
- `SAST`, `DAST` и фаззинг обязательны в CI
- Проверка:
  - набор регрессионных тестов с атакующим содержимым
  - проверки слепых сценариев и сценариев с анализом времени ответа
  - аудит всех новых точек ввода

### 6.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical` для RCE без аутентификации, инъекции в хранилища рабочей среды, выполнения команд или извлечения данных других арендаторов.

Рабочие настройки:
- Для опасных операций SQL, NoSQL, LDAP, команд ОС, шаблонов, XML, URL и браузера определены одобренные безопасные API и правила ревью кода.
- Управляемый пользователем ввод никогда не выбирает имена исполняемых файлов, файлы шаблонов, классы десериализации, фрагменты SQL или сетевые адреса назначения без строгого списка разрешенных значений.
- CSP используется как дополнительный слой защиты от XSS; контекстное кодирование вывода и очистка содержимого остаются основными мерами на стороне браузера.
- Загрузчики по URL используют списки разрешенных схем, хостов и портов, защиту от DNS rebinding, блокировку IP метаданных и политику исходящих соединений.

Подтверждения:
- Реестр опасных операций интерпретаторов высокого риска и вызовов зависимых систем.
- Набор регрессионных атакующих данных для SQLi, внедрения команд, SSTI, XSS, XXE, SSRF и инъекции аргументов, где применимо.
- Результаты SAST, DAST и фаззинга с выводами разбора достижимых опасных операций.
- Подтверждения ревью кода любых функций запуска оболочки, обработки шаблонов, десериализации или загрузки по URL.

Негативные тесты:
- Метасимволы SQL и атакующие данные с логическими выражениями или задержками не меняют смысл запроса.
- Метасимволы оболочки и инъекция аргументов не меняют поведение команды.
- Недоверенный ввод шаблона не может выполнять серверные выражения.
- Контрольные ресурсы SSRF, IP метаданных, localhost, частные диапазоны и попытки DNS rebinding блокируются.
- Атакующее содержимое XSS кодируется или очищается в каждом контексте вывода.

Ложные срабатывания / пропуски:
- Блокировка WAF не доказывает устранение проблемы; проверяйте безопасность опасной операции в приложении.
- SAST может завышать риск недостижимых опасных операций и пропускать пути инъекции, специфичные для фреймворка.
- Экранирование зависит от контекста и ненадежно при его изменении; предпочитайте параметризацию, безопасные API и списки разрешенных значений.

## 7. A04:2021 Insecure Design

### 7.1 Угроза, описание и цель атаки

Небезопасное проектирование означает, что критичные защитные механизмы не предусмотрены в архитектуре и бизнес-логике. Цель атакующего: использовать системные пробелы, которые невозможно быстро закрыть исправлением в одном месте.

### 7.2 Виды и типовой ход эксплуатации

Типы:
- Небезопасные сценарии восстановления или резервного поведения: в упрощенном режиме система пропускает необходимые проверки. Пример: при сбое SMS-сервиса подтверждение операции автоматически отключается.
- Неправильная обработка исключительных условий: отсутствующий ввод, частичный сбой зависимости, тайм-аут, повторный обратный вызов или ошибка проверки привилегий оставляют систему в неизвестном состоянии либо разрешают действие при сбое. Пример: платежный процесс списывает средства в одном учетном регистре, падает при зачислении получателю и повторяется без полного отката или защиты идемпотентности.
- Отсутствие ограничений критичных действий (лимита, скорости, подтверждения): нет барьеров против злоупотреблений. Пример: пользователь может сделать 1000 переводов подряд без ограничения частоты.
- Слабая изоляция арендаторов: данные арендаторов разделены только логикой UI. Пример: подмена `tenant_id` в API показывает объекты другого клиента.
- Ошибки конечного автомата: разрешены недопустимые переходы состояния. Пример: заказ переводится в `paid` напрямую из `draft`, минуя проверку оплаты.
- Логические состояния гонки: конкурирующие запросы обходят бизнес-инвариант. Пример: двойной вызов `withdraw` списывает баланс дважды.

Типовой ход:
- Анализ бизнес-процесса и пользовательских переходов
- Поиск неконтролируемого перехода состояния
- Провоцирование крайних состояний (повтор, гонка, отмена, частичный отказ)
- Принудительный переход к обработке исключений: тайм-ауты, некорректные необязательные параметры, ошибки зависимостей и прерванные транзакции
- Обход ожидаемого порядка выполнения
- Выполнение запрещенной операции без формального взлома кода

Что задевается:
- Денежные операции и операции смены прав
- Целостность бизнес-состояний
- Межтенантные границы

Последствия:
- Мошенничество и злоупотребления, необратимые бизнес-ошибки, системные инциденты

### 7.3 Практическая защита

- Моделирование угроз до разработки
- Сценарии злоупотребления и ненадлежащего использования для всех критичных процессов
- Явные требования безопасности в пользовательской истории
- Лимиты, защита от автоматизации, подтверждение по независимому каналу
- Независимое архитектурное ревью безопасности
- Проверка:
  - тесты конечного автомата
  - негативные бизнес-сценарии
  - пошаговый разбор с позиции атакующего

### 7.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `Medium`; повышайте до `High` или `Critical`, когда пробелы проектирования затрагивают движение денег, авторизацию, изоляцию арендаторов, физическую безопасность, приватность или необратимые операции.

Рабочие настройки:
- Критичные процессы имеют документированный конечный автомат, разрешенные переходы, модель идемпотентности, обработку повторов и поведение при отказе.
- Где применимо, меры противодействия злоупотреблениям предусмотрены для регистрации, входа, оплаты, перевода, возврата, экспорта, приглашения, поддержки и изменения привилегий.
- Операции с серьезными последствиями требуют дополнительной аутентификации, согласования, ограничений частоты или независимого контроля двумя участниками с учетом риска.
- Обработка исключительных условий спроектирована для каждого критичного процесса: отказ в доступе при сбое, откат частичного состояния, сохранение идемпотентности, событие безопасности и безопасное сообщение пользователю без внутренних деталей.
- Моделирование угроз обязательно до релиза для новых границ доверия, чувствительных данных, внешних интеграций, процессов с ИИ и агентами, платежных процессов и процессов безопасности.

Подтверждения:
- Модель угроз или таблица сценариев злоупотребления с остаточным риском и владельцем.
- Тесты переходов состояния и идемпотентности для критичных бизнес-операций.
- Настройки частоты операций, согласований и мониторинга для процессов, чувствительных к злоупотреблениям.
- Решение о выпуске с принятыми рисками и компенсирующими мерами.

Негативные тесты:
- Недопустимые переходы состояния отклоняются.
- Повторные, переотправленные, запоздалые, одновременные запросы и запросы с нарушением порядка не создают неавторизованное бизнес-состояние.
- Отказ зависимости не приводит к пропуску обязательных проверок.
- Отсутствующие параметры, некорректные необязательные поля, тайм-аут, частичный отказ зависимости и шквал повторных попыток не создают рассогласованное состояние, обход привилегий или раскрытие чувствительных данных в ошибке.
- Обычные пользователи не могут запускать операции поддержки, администрирования или бизнеса с высоким риском без обязательных мер контроля.

Ложные срабатывания / пропуски:
- Общий результат STRIDE может пропустить мошенничество и злоупотребления бизнес-состоянием; тестируйте реальные процессы.
- Модульные тесты отдельных сервисов могут пропустить распределенные гонки и повторные попытки.
- Поведение, утвержденное продуктовой командой, может оставаться риском безопасности, если не оценены экономика злоупотреблений и мониторинг.

### 7.5 A10:2025 Нештатные ситуации

Для каждой критичной операции определите, какие отказы запрещают действие, а какие допускают документированный ограниченный режим. Сохраняйте авторизацию и бизнес-инварианты при таймауте, отмене, переполнении очереди и отказе зависимости. Ограничивайте повторы общим временным бюджетом и увеличивающейся задержкой; применяйте обратное давление и квоты арендаторов до распространения перегрузки. Автоматическое размыкание цепи вызовов не должно обходить обязательные проверки безопасности.

Определите момент фиксации транзакции и условия ее отката, а также компенсацию частично завершенных операций. Перед повторной попыткой проверяйте, произошел ли побочный эффект; записи идемпотентности должны переживать период прерывания и восстановления операции. Возвращайте безопасные ошибки и сохраняйте внутренние идентификаторы для расследования.

Негативные тесты: прервите операцию до и после фиксации, исчерпайте очередь, вызовите таймаут зависимости, разомкните цепь вызовов и отправьте параллельные повторы. Проверьте отсутствие двойного платежа или выдачи привилегий, корректность отката или сверки состояния, сохранение квот, безопасные сообщения об ошибках и восстановление без неразрешенных переходов состояния.

## 8. A07:2021 Identification and Authentication Failures

### 8.1 Угроза, описание и цель атаки

Сбои аутентификации и управления сессией позволяют атакующему действовать от имени легитимного пользователя. Цель: захват учетной записи, обход MFA и длительное удержание сессии.

### 8.2 Виды и типовой ход эксплуатации

Типы:
- Подстановка утекших учетных данных (credential stuffing) и перебор распространенных паролей по многим учетным записям (password spraying). Пример: бот проверяет список `email:password` на `/login`.
- Перебор пароля конкретной учетной записи. Пример: 10 000 попыток для `admin@company.com` без жесткой блокировки.
- Фиксация или перехват сессии: навязывание или кража ее идентификатора. Пример: жертва входит с заранее выданным идентификатором сессии атакующего.
- Слабый процесс сброса пароля: восстановление учетной записи по легко угадываемым данным. Пример: токен сброса не истекает и может использоваться повторно.
- Отсутствующая/слабая `MFA` (Multi-Factor Authentication): второй фактор не обязателен для рисковых действий. Пример: перевод средств подтверждается только паролем.
- Некорректный выход или отзыв: токены остаются активными после выхода. Пример: украденный refresh token продолжает выпускать новые access token.

Типовой ход:
- Использование утекших учетных данных и автоматизированных попыток входа
- Поиск слабого процесса восстановления
- Захват или фиксация токена сессии
- Повторное использование токена после выхода
- Эскалация привилегий внутри захваченной сессии

Что задевается:
- Аккаунты пользователей и админов
- Сессионные токены
- Каналы восстановления доступа

Последствия:
- Массовый захват учетных записей, мошеннические операции, потеря доверия к учетной системе

### 8.3 Практическая защита

- MFA обязательна для ролей и действий высокого риска
- Проверка паролей на компрометацию
- Ротация идентификатора сессии после входа и изменения привилегий
- Тайм-аут бездействия и абсолютный срок сессии
- Надежные выход и отзыв
- Проверка:
  - тесты устойчивости к перебору
  - тесты фиксации/угона сессии
  - мониторинг аномалий входа и сброса пароля

### 8.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical` для захвата административной учетной записи, небезопасного сброса пароля, обхода MFA для действий с серьезными последствиями или компрометации многократно используемого refresh token либо токена сессии.

Рабочие настройки:
- Браузерные приложения используют серверные сессии или обработку токенов по схеме BFF; refresh token не хранится в хранилище браузера.
- Ротация идентификатора сессии выполняется после входа, повышения привилегий и завершения восстановления.
- Пользовательские сессии имеют тайм-аут бездействия и абсолютный срок; действия высокого риска требуют недавней аутентификации.
- Защита от подстановки утекших учетных данных включает проверку паролей по утечкам, ограничение частоты по учетной записи и источнику, признаки ботов и оповещения об аномалиях.
- Выход уничтожает локальную сессию и отзывает или аннулирует данные обновления и сессии там, где архитектура это поддерживает.

Подтверждения:
- Конфигурация IdP и сессий с TTL, атрибутами cookie, политикой MFA и дополнительной аутентификации, сроком действия токена сброса.
- Негативные тесты неверных issuer и audience, истекшего токена, фиксации сессии, повторного использования токена сброса, выхода и отзыва.
- Мониторинг ошибок входа, перебора паролей по учетным записям, злоупотребления сбросом, ошибок MFA, невозможных перемещений между входами и аномалий сессий.
- Реестр привилегированных ролей с MFA и процедурой аварийного доступа.

Негативные тесты:
- Украденный или навязанный до входа идентификатор сессии не сохраняется после аутентификации.
- Токен сброса одноразовый, быстро истекает и не используется повторно после смены пароля.
- Refresh token или токен сессии не продолжает работать бессрочно после выхода, обновления Not Before или события отзыва.
- Перебор распространенных паролей и подстановка утекших учетных данных вызывают ограничение частоты и оповещения.

Ложные срабатывания / пропуски:
- Наличие MFA не доказывает защиту, если восстановление или сценарии запомненного устройства обходят второй фактор.
- Блокировка учетной записи может стать вектором отказа в обслуживании; оценивайте адаптивное ограничение частоты и дополнительную аутентификацию, а не только жесткие блокировки.
- Тесты проверки JWT должны включать issuer, audience, временные claim, список разрешенных алгоритмов и доверие к ключам.

## 9. A08:2021 Software and Data Integrity Failures

### 9.1 Угроза, описание и цель атаки

Риск появляется, когда система доверяет данным, конфигам или коду без проверки происхождения и целостности. Цель атакующего: подмена обновлений/данных и внедрение опасных объектов через десериализацию.

### 9.2 Виды и типовой ход эксплуатации

Типы:
- Применение неподписанных обновлений и конфигураций: система доверяет файлам без проверки происхождения. Пример: сервис загружает ZIP с плагином без проверки подписи.
- Подмена политики или артефакта в канале доставки: атакующий меняет содержимое между этапами конвейера. Пример: в реестре под тем же тегом публикуется измененный образ контейнера.
- Небезопасная десериализация: объект из недоверенного источника десериализуется как доверенный. Пример: сериализованное содержимое вызывает выполнение нежелательного метода.
- Доверие к пользовательским cookie или объектам без `MAC` (Message Authentication Code, код аутентификации сообщения): клиент может менять критичные поля. Пример: cookie `{"role":"user"}` меняется на `{"role":"admin"}` и принимается сервером.

Типовой ход:
- Поиск точки загрузки обновления/конфига/объекта
- Подготовка подмененного содержимого
- Обход проверки источника/подписи
- Выполнение измененной логики или запуск цепочки гаджетов
- Закрепление через персистентную подмену данных

Что задевается:
- Канал обновлений и конфигурация
- Внутренние модели состояния приложения
- Меры контроля целостности бизнес-данных

Последствия:
- Неавторизованное изменение логики, RCE, долговременная компрометация

### 9.3 Практическая защита

- Подписывать и верифицировать обновления, артефакты, конфиги
- Запрет небезопасной десериализации недоверенного ввода
- Отделение доверенной плоскости управления от плоскости передачи данных, управляемой пользователем
- Проверка целостности всех критичных объектов
- Проверка:
  - тесты несанкционированного изменения
  - проверки цепочки доверия при запуске сервиса
  - оповещения о несовпадении подписи или хеша

### 9.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical`, если нарушение целостности приводит к RCE, компрометации релиза в рабочую среду, изменению платежей или учетного регистра либо обходу политики.

Рабочие настройки:
- Обновления, плагины, модели, конфигурации, правила и релизные артефакты проверяются перед использованием.
- Десериализация недоверенного ввода запрещена, если нет узкого формата, прошедшего ревью, и списка разрешенных значений.
- Состояние, управляемое клиентом, подписывается, защищается MAC или хранится на сервере; данные авторизации из изменяемых клиентом полей не считаются доверенными.
- Развертывание и запуск выполняют проверки цепочки доверия и при несовпадении прекращаются с отказом для особо ценных компонентов.

Подтверждения:
- Результаты проверки подписи артефакта или конфигурации и настройки политики.
- Реестр форматов десериализации и границ доверия.
- Тесты отклонения подмененных клиентских объектов, cookie, конфигураций и артефактов обновления.
- Примеры аудита и оповещений при несоответствии подписи, дайджеста или политики.

Негативные тесты:
- Измененный артефакт, неверный дайджест, неверный подписант или неподписанная конфигурация отклоняются до развертывания или запуска.
- Подготовленное сериализованное содержимое не может создавать экземпляры небезопасных типов или запускать опасные пути выполнения.
- Измененная cookie или клиентский объект не может изменить роль, арендатора, баланс, право доступа или состояние процесса.
- Обновление политики или правил из неутвержденного источника отклоняется.

Ложные срабатывания / пропуски:
- Проверки хеша без доверенного provenance или подписи обнаруживают повреждение, но не подтверждают разрешенное происхождение.
- Сканеры десериализации могут пропустить специфичные для фреймворка цепочки гаджетов и содержимое сообщений брокера.
- Подписанные данные все равно могут быть небезопасными при слабом контроле ключей подписи, канонизации или доверенных полей.

## 10. A09:2021 Security Logging and Monitoring Failures

### 10.1 Угроза, описание и цель атаки

Если события безопасности не журналируются или по ним нет своевременных оповещений, инцидент остается незамеченным. Цель атакующего: увеличить время присутствия и снизить вероятность блокировки.

### 10.2 Виды и типовой ход эксплуатации

Типы:
- Отсутствие журналов критичных событий безопасности: атака не оставляет сигналов для обнаружения. Пример: не журналируются неуспешные входы и смена ролей.
- Подмена/удаление локальных логов: злоумышленник стирает следы. Пример: после компрометации удаляется файл `app.log` на хосте.
- Нет корреляции в `SIEM` (Security Information and Event Management): отдельные события не складываются в инцидент. Пример: 50 ошибок авторизации и необычный доступ к API не объединяются в оповещение.
- Утечка персональных данных и секретов через журналы: они становятся источником компрометации. Пример: в журнал записывается `Authorization: Bearer ...`.
- Перегрузка `SOC` (Security Operations Center) шумом и ложноположительный результат: критичные сигналы теряются. Пример: тысячи низкоприоритетных алертов маскируют реальную атаку.

Типовой ход:
- Выполнение скрытой атаки с минимальным шумом
- Проверка отсутствия алерта на неуспешные логины/сканирование
- Сокрытие следов через изменение журналов
- Повторная эксплуатация без срабатывания обнаружения

Что задевается:
- Обнаружение и реагирование
- Форензика и аудит
- Регуляторная отчетность

Последствия:
- Позднее обнаружение компрометации и значительное увеличение ущерба

### 10.3 Практическая защита

- Фильтрация и экранирование пользовательского ввода (в т.ч. для безопасной записи/отображения)
- Обязательный каталог событий безопасности: аутентификация, доступ, конфигурация, привилегии и изменения данных
- Стандартизованный формат логов + идентификатор корреляции
- Журнал аудита с обнаружением изменений или записью только на добавление
- Централизованный сбор, оповещения и инструкция реагирования для каждого сценария высокой критичности
- Исключение секретов и чувствительных данных из логов
- Проверка:
  - DAST и тестирование на проникновение должны вызывать оповещения
  - регулярная проверка MTTD/MTTR
  - тесты качества обнаружения и эскалации

### 10.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `Medium`; повышайте до `High`, если отсутствие телеметрии затрагивает аутентификацию, авторизацию, административные действия, экспорт данных, платежные события, события безопасности или восстановление хронологии инцидента.

Рабочие настройки:
- Каталог событий безопасности покрывает аутентификацию, решения авторизации, административные действия, изменения привилегий, доступ к секретам и ключам, изменения конфигурации, экспорт данных, ограничения частоты, ошибки валидации и злоупотребление webhook или API.
- Журналы используют согласованную схему с временной меткой, субъектом, арендатором, клиентом, источником, действием, ресурсом, решением, причиной, идентификаторами корреляции и запроса, где применимо.
- Токены, учетные данные, секреты, полные платежные данные и чувствительное содержимое маскируются перед сохранением.
- Особо ценные журналы аудита централизованы, защищены контролем доступа, позволяют обнаруживать изменения или допускают только добавление и хранятся минимум `90d`, если нет более строгих требований.
- Оповещения имеют владельца, уровень критичности, инструкцию и целевой SLO реагирования.

Подтверждения:
- Примеры журналов разрешенных и запрещенных чувствительных действий.
- Правила обнаружения и инструкции реагирования для приоритетных сценариев злоупотребления.
- Настройки сроков хранения, неизменяемости и контроля доступа к хранилищу аудита.
- MTTD/MTTR или результаты учений по реалистичным путям атаки.

Негативные тесты:
- Всплеск неуспешных попыток входа, пробные попытки BOLA, неверный токен, смена привилегий, массовый экспорт, повторная отправка webhook и ошибка валидации схемы создают ожидаемые события.
- Секреты и токены на предъявителя отсутствуют в журналах приложения, прокси, заданий и CI.
- Удаление локальных журналов не удаляет централизованные подтверждения аудита.
- Оповещение доходит до ожидаемого владельца с достаточным контекстом для расследования.

Ложные срабатывания / пропуски:
- Большой объем журналов не означает качественного обнаружения; проверяйте оповещения, требующие действий, и инструкции реагирования.
- Маскирование может удалить контекст расследования; где полезно, сохраняйте стабильные хеши и идентификаторы корреляции.
- Оповещения от DAST могут не покрывать малозаметные пути злоупотребления бизнес-логикой без специальных тестов.

## 11. A10:2021 Server-Side Request Forgery

### 11.1 Угроза, описание и цель атаки

Подделка серверных запросов (Server-Side Request Forgery, SSRF) возникает, когда приложение выполняет запросы к URL, управляемому атакующим, или определяет управляемые атакующим адреса назначения из привилегированной инфраструктуры. Цель атакующего: заставить доверенный сервер обратиться к облачным метаданным, внутренним сервисам, плоскостям управления или чувствительным сетевым ресурсам, к которым у атакующего нет прямого доступа.

### 11.2 Виды и типовой ход эксплуатации

Типы:
- Загрузчики по URL и импортеры: приложение получает пользовательский URL для предпросмотра изображения, проверки webhook, импорта документа или раскрытия ссылки. Пример: `image_url=http://169.254.169.254/latest/meta-data/` обращается к облачным метаданным.
- Обратные вызовы парсера или конвертера: обработка PDF, XML, SVG, офисных документов или медиа разрешает внешние ссылки. Пример: задание преобразования документа переходит по внутреннему URL из содержимого атакующего.
- Функции проверки webhook и интеграций: пользователь настраивает эндпоинт обратного вызова, а сервис проверяет его из привилегированной сети. Пример: эндпоинт проверки обращается к внутренней административной панели.
- DNS rebinding и цепочки перенаправлений: исходный URL выглядит разрешенным, затем перенаправление или разрешение DNS ведет в частные диапазоны. Пример: разрешенный публичный хост перенаправляет на `http://127.0.0.1:8080/admin`.
- Доступ к облачным метаданным: рабочая нагрузка может обращаться к сервису метаданных провайдера и получать токены идентификации или учетные данные, если отсутствуют защита метаданных и политика исходящих соединений.

Типовой ход:
- Поиск функций серверной загрузки, предпросмотра, webhook, импорта или разбора содержимого
- Передача URL или содержимого, которое обращается к частным сетям, loopback, link-local, метаданным или внутренним DNS-именам
- Обход простых запрещающих правил через перенаправления, DNS rebinding, альтернативную запись IP, IPv6 или особенности парсера
- Использование времени ответа, ошибок, обратных вызовов или сохраненного вывода для косвенного получения или утечки внутренних данных

Что задевается:
- Учетные данные облачной рабочей нагрузки и сервисы метаданных
- Внутренние административные панели, API сервисов и плоскости управления
- Сетевая сегментация и границы арендаторов и сервисов

Последствия:
- Разведка внутренней сети, кража учетных данных, неавторизованные внутренние действия и продвижение атакующего через доверенный сервер

### 11.3 Практическая защита

- Разрешайте точные адреса исходящих соединений по бизнес-назначению; избегайте универсальных загрузчиков «любого URL» в рабочей среде.
- Проверяйте конечный адрес после перенаправлений, канонизации, разрешения DNS и нормализации IP; блокируйте частные диапазоны, loopback, link-local, multicast и диапазоны облачных метаданных, если нет явно утвержденного исключения.
- Применяйте сетевую политику исходящих соединений из namespace, VPC или подсети рабочей нагрузки, чтобы прикладная валидация не была единственной мерой контроля.
- Отключайте или строго настраивайте возможности парсеров, разрешающие внешние ссылки при обработке XML, SVG, PDF, офисных документов, медиа и архивов.
- Используйте выделенные сервисы загрузки с минимальными привилегиями, без неявно доступных облачных учетных данных и доступа к внутренним административным сетям, с ограничениями размера и времени ответа и проверяемой политикой адресов назначения.
- Для облачных метаданных требуйте защиту средствами провайдера: IMDSv2 и ограничения числа сетевых переходов, ограничение полномочий рабочей нагрузки, скрытие метаданных и правила блокировки исходящих соединений.
- Проверка:
  - тесты перенаправлений и DNS rebinding
  - негативные тесты частных адресов, link-local и IP метаданных
  - подтверждения политики исходящих соединений и запрета доступа к облачным метаданным

### 11.4 Базовый профиль ревью

Приоритет:
- Базовая критичность: `High`; повышайте до `Critical`, если SSRF позволяет получить учетные данные из облачных метаданных, обратиться к API плоскости управления, внутренним административным панелям, сервисам данных арендатора, учетным данным подписи или развертывания, внутренним эндпоинтам, изменяющим состояние.

Рабочие настройки:
- Управляемые пользователем адреса загрузки либо не поддерживаются, либо ограничены утвержденными схемами, хостами, портами, типами содержимого и размерами ответа.
- Фактический конечный адрес проверяется после перенаправлений и разрешения DNS; частные адреса, loopback, link-local, multicast и адреса метаданных блокируются прикладной политикой и сетевым контролем исходящих соединений.
- Загрузка выполняется от выделенной учетной записи без широкого доступа к облачным метаданным, администрированию service mesh, Kubernetes API, Vault, CI/CD или внутренним административным интерфейсам.
- Возможности парсера или конвертера, способные получать внешнее содержимое, отключены или направлены через тот же контролируемый сервис загрузки.
- Попытки SSRF создают события безопасности с исходным субъектом, функцией, классом запрошенного URL, классом разрешенного адреса назначения, решением и идентификатором корреляции.

Подтверждения:
- Реестр всех функций загрузки по URL, проверки webhook, импорта, предпросмотра, парсеров и конвертеров с владельцем и политикой адресов назначения.
- Подтверждения политики исходящих соединений, DNS, прокси и защиты облачных метаданных для развернутого окружения.
- Результаты негативных тестов перенаправлений, DNS rebinding, альтернативных форматов IP, IPv6, частных диапазонов и эндпоинтов метаданных.
- Примеры оповещений и аудита запрещенных и разрешенных загрузок.

Негативные тесты:
- `http://127.0.0.1`, `localhost`, RFC1918, link-local, IPv6 loopback, multicast и эндпоинты облачных метаданных отклоняются.
- Перенаправления к запрещенным адресам блокируются, даже если первый URL публичный и разрешенный.
- DNS rebinding с публичного на частный адрес отклоняется после повторного разрешения.
- Встроенные в обрабатываемое содержимое внешние ссылки не могут обращаться к внутренним сетям.

Ложные срабатывания / пропуски:
- Регулярного выражения для URL или списка запрещенных имен хостов недостаточно; проверяйте нормализованные URL, разрешенные адреса, перенаправления и фактический сетевой путь.
- Прокси может централизовать политику, но только если прямые исходящие соединения из рабочей нагрузки заблокированы.
- Слепая SSRF может не возвращать данные напрямую; проверяйте время ответа, обратные вызовы, журналы DNS и исходящих соединений, блокировку доступа к метаданным.
